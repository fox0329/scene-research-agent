> 日期：2026-11-03 ｜ 调研依据：`docs/技术调研-需求理解与反思生成.md`（含 2.5 竞品盘面，来源 15 条）

> 一句话：从问答与操作中维护一份**可追溯、可编辑的场景需求画像**，用它裁决「何时问」和「生成后查什么」，反思重写只在确定性比对发现必改项时触发、用户确认后才生效。

---

## 一、产品定位

### 1.1 为什么做

这类产品的核心痛点是「每一轮生成都像失忆」：用户说过的话、改过的格、划过的红线，下一轮生成又当没发生过，体验是「每次都要重新教一遍」。本模块把「说过的话」变成「记住的规则」，让输出质量随使用递增：第一轮产物是「行业通用的对」，纠偏两三轮后变成「你的对」；理想态是用户只说场景名，其余偏好已在画像里。

### 1.2 三级作用域，模块只管后两级

用户「定调」分三级（潜污泵项目实例，变更表 #349/#350）：

| 级 | 实例 | 去处 |
|---|---|---|
| **产品级规则**（跨场景恒定） | 「不管有没有内容，所有表格都建空表渲染表头」 | 走变更流程固化进确定性代码，**不经画像** |
| **用户级画像**（跨场景个人习惯） | 「总是关心成本」「习惯 2 页纸」「受众通常是运营口」 | `requirement_profile(scope=user)`，需跨场景重复 + 用户确认升级，新场景冷启动透明注入 |
| **场景级画像**（本项目/本报告特有） | 「这个客户特别在乎造价」「别提国产替代」 | `requirement_profile(scope=scene)`，默认级 |

模块不越权：识别出产品级定调时提示走变更流程；用户级条目不自动升级也不自动迁移（见 6.1）。

## 二、定位与边界

**做什么**：① 把问答与操作整理成结构化需求条目（显式要求 / 隐含偏好 / 负面约束，带检测锚点与来源）；② 生成产物后用锚点做符合度比对，有必改项自动重写一轮、差分预览等用户确认；③ 需求值得问时在右栏会话提一个澄清问题。

**不做什么（G-R4）**：不做生成中实时反思（V1 只做生成后一轮）；不做模态打断式追问；**不做场景画像自动迁移**（用户级条目必须跨场景重复 + 用户确认才升级，见 6.1）；不自动修改表格结构（维度缺口只记录、建议、上报，契约变更走变更流程）；不引入 embedding / 向量库 / 新中间件；不改变会话体系 v2 的任何交互；不覆盖用户已确认的内容（`confirmation.ts` 语义：用户确认/用户修改是基准）；空单元格的出路只有取证（检索/入库/用户手填），**不许填「行业通例（模型知识）」当来源**（用户定调 2026-10-21，postcheck 硬伤）。

## 三、已定决策（2026-11-03 用户确认）

| 决策点 | 定案 |
|---|---|
| 操作采集范围 | **五处 UI 埋点**：编辑单元格、确认、撤销、重写指令、建议卡采纳/拒绝；另复用 `operation_log`（模型写操作审计）的 undo 信号 |
| 画像粒度 | 场景级（`scenario_id` 作用域），每条带来源产物引用 |
| 反思时机 | 生成完成后自动跑一轮，产出差分预览，用户点「应用 / 忽略」 |
| 澄清形态 | 非模态，右栏会话普通消息 |
| 产物修改权限 | 画像更新直接生效（数据簿记）；产物修改**永不直接改**——过「确定性必改项 + 用户确认」两道门 |
| 用户级画像 | 加 `scope` 列（scene/user）；升级 = 同维度条目 ≥2 场景 active + 用户在画像卡确认；冷启动透明注入可移除（2026-11-03 二次确认） |

## 四、总体架构

```
表现层  画像卡（条目+来源，可编辑/删除，不藏太深）│ 重写差分预览 │ 澄清消息（右栏会话内）
   ↕
应用层  profile-extract（事件攒批回流抽取）      ← converse / edit_cell / undo / rewrite / 建议卡 后挂钩子
        refine-output（反思编排，参照 postcheck-pass.ts）
        maybe-clarify（澄清决策与注入）
   ↕
领域层  intent-profile   条目合并/冲突/时效/置信规则（纯函数）
        clarify-policy   何时问的确定性裁决（纯函数）
        reflection-loop  锚点比对规则、分轮与停止条件（纯函数）
   ↕
基础设施  event-recorder（interaction_event 唯一写入口，评审修订）
          requirement_profile / interaction_event 两张新表（sqlite-repo 增 repo）
          dsh-client（唯一 AI 出口，不变）
```

依赖方向不变：web → contract ← server → domain ← infra。判定全部在领域层，LLM 只做抽取、澄清问题生成、重写——不进判定路径。

## 五、数据模型（新增 2 表，DDL 草案）

```sql
-- 需求画像（属主：intent-profile）
CREATE TABLE requirement_profile (
  id TEXT PRIMARY KEY,
  scenario_id TEXT,              -- 场景级条目必填；用户级条目为 NULL（评审修订：消除 scope 与非空约束的矛盾）
  origin_scenario_id TEXT,       -- 用户级条目：升级发生时所在场景（溯源用）
  scope TEXT NOT NULL,           -- scene | user（用户级需升级确认，见 6.1）
  kind TEXT NOT NULL,            -- explicit | preference | constraint | dimension_gap
  text TEXT NOT NULL,            -- 一句话（G-R9 中栏口径）
  check_anchor TEXT,             -- 检测锚点 JSON（关键词/正则/数值条件）；NULL=仅提示级
  status TEXT NOT NULL,          -- active | superseded | dismissed
  confidence TEXT NOT NULL,      -- 用户原话 | 用户操作 | AI推断（沿用 confirmation 语义）
  source_json TEXT NOT NULL,     -- {type: message|operation|clarify, ref, snippet}（G-R0 溯源）
  artifact_refs TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX idx_req_scenario ON requirement_profile(scenario_id, status);

-- 交互事件（属主：intent-profile；与 operation_log 分表，后者有 undo 语义不混用）
CREATE TABLE interaction_event (
  id TEXT PRIMARY KEY,
  scenario_id TEXT,
  conversation_id TEXT,
  surface TEXT NOT NULL,         -- ui | conversation
  action TEXT NOT NULL,          -- edit_cell | confirm | undo | rewrite | suggest_accept | suggest_reject
  target TEXT,
  detail_json TEXT,
  created_at TEXT NOT NULL
);
CREATE INDEX idx_evt_scenario ON interaction_event(scenario_id, created_at);
```

`dismissed` 条目按文本指纹进黑名单，抽取管道不再抽回。画像卡在 UI 上不藏太深——画像会学错，需要用户偶尔看一眼，藏深了必然漂移。

## 六、领域层规则（可单测的判定明细）

### 6.1 intent-profile —— 条目合并

| 情形 | 规则 |
|---|---|
| 新条目与现行条目文本高度重合 | 合并：更新 `updated_at`、追加来源，不新增行（V1 用归一化后关键词重合率，不引入向量） |
| 新旧表态冲突 | 新条目置 `active`，旧条目置 `superseded`（保留可追溯，不删） |
| 表态来源优先级 | 用户原话 > 用户操作 > AI推断；低置信不得覆盖高置信 |
| 用户删除 | `dismissed` + 指纹黑名单 |
| **undo 信号（推演修正）** | **不直接抽条目**——只打「待复核」标记，下轮抽取时由 LLM 结合上下文判断要不要生成条目，置信上限「用户操作」级。理由：undo 有歧义（不认可内容 / 改错地方），直接固化会把噪音写进画像 |
| **用户级升级** | 同维度条目在 ≥2 个场景保持 active → 进「升级候选」列表，用户在画像卡确认后才置 `scope=user`；**不自动升级**（一次表态就跨场景迁移，错一次污染所有新场景）。用户级条目可一键降级/删除 |
| 抽取与手编并发 | 用户显式编辑永远赢（高置信）；抽取管道写入前重读最新状态，SQLite 单写者事务顺序保证 |
| **维度缺口（`dimension_gap`）** | 用户指出表格缺维度时记录条目；场景内以**补充建议**生效（写进该表备注/相关产物），**不自动加列**（列定义属 contract，改动是契约变更）；升级规则同上——≥2 场景重复 → 提示走变更流程固化进表格定义（同 #349「空表渲染表头」通路），智能体只有建议权 |

### 6.2 clarify-policy —— 何时问

```
shouldAsk = (存在冲突对 ≥ 1
             或 必填维度缺失 ≥ 2
             或 近 3 轮内 rewrite/undo 事件 ≥ 2)
            且 本会话已问 < 2 次
            且 用户未选「别再问」
```

命中后由 LLM 生成候选澄清问题 → **答案存在性检查**（确定性，评审修订）：问题关键词在画像条目与材料库全文索引中查一遍，答案已存在 → 丢弃候选不问（答案就在手边的提问比不问更糟）。通过后才作为普通消息进右栏会话，**至多 1 个**。阈值常量集中管理。用户连续纠偏（undo+rewrite）本身就是「我说的你没听懂」的信号，比维度缺失更值得问。

### 6.3 reflection-loop —— 锚点比对与分轮

```
第 0 步  确定性比对（产物文本/表格 vs 现行条目锚点）：
         - 违反 constraint（锚点命中）        → 必改
         - 漏掉 active 的 explicit（锚点未中）→ 必改
         - preference 未体现 / 无锚点条目     → 仅提示，不触发重写
第 1 轮  有必改项 → 偏差清单 + 原文交 LLM 重写（只改被点名处，同 postcheck 设计）
第 2 轮  复查：仍违反 → 停止，如实报告，不静默第三轮
         全过 → 输出差分预览
```

**锚点是整个机制的命门**（推演结论）：

- 锚点在抽取时由 LLM 顺手产出，反思比对是纯确定性匹配——**给文档造测试**（对标代码产品「测试驱动反思」的已验证形态，见调研 §2.5）。
- 部分需求只能抽**代理信号**（如「给运营口看」→「出现 ROI/万元 → 提示」），代理有误报风险，因此锚点不准的条目 `check_anchor=NULL` 降级为「仅提示」——**宁可漏改，不可误改**。
- **篇幅类锚点按导出口径折算**（推演修正）：「两页纸」→ 字数上限由确定性层集中管理的折算规则决定，不由抽取 LLM 随手写数。
- **锚点回归集是必须项**：从真实失败样例攒误报/漏报样本（潜污泵项目的真实生成就 started 提供），M2 验收以此为准，不是可选项。

### 6.4 缺口流转闭环（v1.1 新增：completeness 不只是报告）

现有 `completeness.ts` 已有缺口五分类（`缺表 | 缺必填列 | 覆盖度不足 | 缺来源 | 推断未标注`）与责任方分派（`userGaps` / `agentGaps`）。本模块把静态缺口报告变成闭环动作：

| 缺口 | 判定 | 流转动作 |
|---|---|---|
| 表达不准确 | 画像锚点比对 | 反思重写（6.3） |
| 细节不清楚 | 具体度检查（数值/型号/协议名实体密度，M2 可选项） | 查材料库全文索引：有料 → 点名展开重写；没料 → 取证出口 |
| 空单元格 | `缺必填列/覆盖度不足`（已有） | **agentGaps** → 自动取证：联网检索补证（0.9.7 四入口）→ 建议入库材料 → 仍无依据则保持空并说明；**userGaps** → 明确提醒「该你拍板」或转澄清 |
| 维度缺失 | `缺表`（已有）+ 列存在性比对 | 先区分：列存在没填（归上）→ 信息在别表（澄清引导）→ 真缺（`dimension_gap` 条目，见 6.1） |

铁律：空单元格的出路只有取证（检索/入库/用户手填），不许填「行业通例（模型知识）」当来源（用户定调 2026-10-21）。

### 6.5 检查管线与重写合并（v1.2 新增，评审修订）

生成后检查现在有两套：postcheck（G-R8 三问，对照材料库）与本模块 reflection（对照画像锚点）。编排定为**检查并行、修订合并**：

```
产物生成完成
  → 检查并行：postcheck（真实性/客观性） ∥ reflection（需求符合度） ∥ completeness（缺口）
  → 修订合并：三路必改项并入同一份偏差清单，LLM 重写一次（单轮）
  → 一次差分预览（三路点名标记合并展示），用户应用/忽略
  → 复查一轮（三路并行），仍违反 → 如实报告，不静默第三轮
```

原则：**用户永远只面对一次差分**，token 不翻倍。钩子顺序：converse 完成后 → profile-extract（攒批）→ maybe-clarify；产物生成完成后 → 检查管线。

## 七、应用层 command 与 API 契约（contract 升 v1.5）

| 项 | 说明 |
|---|---|
| `profile-extract` | 钩子触发：converse 每 3 条消息或空闲 30s、五处 UI 操作后。输入新事件与 completeness Gap 报告，按 6.1 出条目增改、按 6.4 出流转动作 |
| `event-recorder` | **`interaction_event` 唯一写入口**（评审修订：防五处 command 直写表违反规则 3）——server 内轻量设施，edit-cell/confirm/undo/rewrite/建议卡 command 只调 `record()`；intent-profile 为唯一读者与属主 |
| `refine-output` | 产物生成完成后自动触发；「按需求重写」按钮手动触发。编排 6.3+6.5，SSE 返回进度与差分；**单次重写 token 上限熔断**（超限转手动模式） |
| `maybe-clarify` | converse 每轮后检查 6.2，命中则生成澄清消息；`userGaps` 与「信息在别表」型缺口作为澄清输入 |
| `GET /api/v1/scenarios/:id/requirements` | 画像卡数据（含来源引用） |
| `PATCH /api/v1/requirements/:id` | 编辑文本 / 删除（dismissed） |
| `POST /api/v1/artifacts/:ref/refine` | 手动重写 |

所有入口参数校验、速率限制沿用现有 server 中间件；新表读写只经 intent-profile 的 repo；feature flag 一键整体关停（关闭后回到现状单轮生成）。

## 八、成本预算（单场景活跃使用一天估算）

| 环节 | 触发 | 模型档 | 估算 |
|---|---|---|---|
| 画像抽取 | 每 3 条消息 1 次 | 轻档 | ~1.5k token/次，日 <30 次 |
| 澄清 | 会话上限 2 次 | 轻档 | 可忽略 |
| 锚点比对 | 每次产物生成 | **0 token**（纯确定性） | — |
| 反思重写 | 仅必有改项，≤1 轮 | 重档 | **按产物分档**（评审修订）：表格类 ~3-5k、方案文档类 8-20k token/次，日 <10 次；单次上限熔断 |

画像注入按条检索（只给与当前产物相关的条目），不整表塞入（G-0.3）。整体增量约为现有生成成本的 10–20%。

## 九、对标分析（调研 §2.5 盘面结论）

| 机制 | 业界现状 | 本模块位置 |
|---|---|---|
| 画像 | Cursor「Rules+Memory」双轨已验证 | 照抄成熟形态：自动抽取（Memory）+ 画像卡手改（Rules）；创新不在此 |
| 反思 | 代码产品「测试驱动反思」（环境反馈）已验证；Huang et al. 证明纯自评不可靠 | **真迁移**：文档没有测试，锚点就是给文档造测试 |
| 澄清 | 研究 2025 年集中出成果，产品侧普遍最弱 | 真空白，差异化空间 |
| 三块闭环 + undo/rewrite 频次触发 | **未找到先例**（英文主流生态检索范围，中文产品未查，结论强度=未找到） | 本方案的组合点 |

明说：无新算法，属成熟做法的工程化组合应用；空白点在闭环组合与触发信号设计。

## 十、收敛指标（「更理想」必须可测，进 M2 验收）

| 指标 | 期望趋势（**均按产物数归一化**，评审修订：用量涨频次自然涨，不归一化趋势不可判） | 不降说明什么 |

| 反思必改项检出率（次/产物） | 随使用下降 | 画像抽取或锚点质量有问题 |
| undo/rewrite 频次（次/产物） | 下降 | 反思没接住该接的错 |
| 澄清问题重复率（同题重复次数） | 不重复问 | 画像没吸收澄清结果 |

指标不降就是机制有问题，不允许用「机制在跑」自我安慰。

## 十一、分期计划

| 期 | 内容 | 验收 |
