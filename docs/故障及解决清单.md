| 20 | 2026-10-02 | 分析跑到 60 秒就报「The operation was aborted due to timeout」 | 上一轮修「一直显示分析中」时，把连接超时写成了 `AbortSignal.timeout(60s)` **直接挂在 fetch 上**——这个信号到点会把**响应体读取**一起中止，于是任何超过 60 秒的分析都在第 60 秒被自己掐死（本步分析正常要 1–3 分钟）。实机：重算第 3 步到 62 秒整条断掉。 | 连接超时改为**只盖「等到响应头」**：手动 `setTimeout` + 响应头一到 `clearTimeout` 摘掉信号（与用户取消信号 composite），流中卡死交给已有的 idle 超时（120 秒无字节）。补回归用例：连接超时压到 40ms、流慢速吐 200ms 必须正常收完（去掉修复该用例即失败） | 已解决 |
| 21 | 2026-10-02 | 重算本步后数据被清空：界面显示「完成，共写入 0 条信息」 | 两个缺陷叠加：① 输出被供应商**长度上限截断**（finish_reason=length），而 `consumeStream` 只要看到 finish_reason 就当 `done`；② `parseDshOutput` 对截断 JSON 静默返回 `{rows:[]}`，而写入顺序是**先 `deleteByScenarioStage` 再 insert** → 旧的 30 行被删、新的 0 行写不进。实机：第 3 步重算把本步数据清零，且没有任何错误提示。 | ① 请求显式给 `max_tokens`（`LLM_MAX_TOKENS`，默认 32768，实测两家供应商均接受）；② `done` 事件透出 `finishReason`，`length` 一律按失败处理（不清库、报「被长度上限截断，请重试」）；③ 解析不出行 = 失败，**先判空再决定动不动旧数据**，报错并保留本步原有内容；④ 新增 `SCENE_DUMP_RAW_DIR` 留证开关（解析失败时能查模型到底吐了什么）。补两个回归用例（非法 JSON / length 截断均不得调用 delete 与 insert） | 已解决 |

#### 路线① npm 发布版 — **不可行**

| 日期 | 尝试 | 结论 |
|---|---|---|
| 2026-09-22 | `npm info @deepseek-ai/dsh-api-remotes`：包存在，latest=0.0.1-rc.1，next=0.1.5-rc.3，共 25 个版本。临时目录 `npm install @deepseek-ai/dsh-api-remotes` 失败：传递依赖 `@deepseek-ai/dsh-type-meta@^0.0.1-rc.1` 返回 404（未发布到 npm registry）。错误链：remotes → dsh-goal → dsh-type-meta(404)。 | **不可行**。原因与故障 #1 一致：DSH 的传递依赖链不完整，npm registry 上缺失关键包。 |

- **优势**：最简单，一条 `npm install` 搞定
- **风险**：依赖链断裂无法绕过；上游何时补发不确定；即使 future 版本修复也无法锁定兼容版本

#### 路线② vendor workspace 挂载 — **有条件可行（推荐优先尝试）**

| 日期 | 尝试 | 结论 |
|---|---|---|
| 2026-09-22 | 确认源码路径 `vendor/deepseek-harness/packages/api/remotes/`，`package.json` name=`@deepseek-ai/dsh-api-remotes` v0.1.7-alpha.1；`lib/` 目录已构建（含 index.js、client.js、types/）；exports 配置了 `.`、`./client`、`./types` 三个入口。依赖均为 `workspace:^` 协议（dsh-deque、dsh-session、dsh-util-values 等）。项目 pnpm-workspace.yaml 目前只声明 `apps/*` 和 `packages/*`，不覆盖 vendor 路径。 | **有条件可行**。需要将 `vendor/deepseek-harness/packages/api/*` 加入项目 pnpm-workspace.yaml 的 packages 列表（或仅声明 `remotes` 的精确路径），然后用 `workspace:@deepseek-ai/dsh-api-remotes` 引用。前置条件：(1) 项目改用 pnpm 且 workspace 包含 vendor 子树；(2) remotes 的传递 workspace 依赖需一并纳入（至少 dsh-deque、dsh-session、dsh-util-values、dsh-scope、cordis）。 |

- **优势**：与项目已有的 vendor 源码路线一致（故障 #1 的解法）；版本与本地 DSH 实例完全同步；无网络依赖
- **风险**：(1) workspace 引入面广——remotes 的 deps/peerDeps/devDeps 合计 30+ 个 workspace 包，全量引入会增加 node_modules 体积；(2) pnpm workspace overrides 与 DSH 上游的 `pnpm-workspace.yaml`（含 allowBuilds、patchedDependencies）可能冲突；(3) DSH 源码已在 .gitignore 排除，CI 环境需额外 clone 步骤
- **缓解**：只引 remotes + 3 个 runtime deps（deque、session、util-values），devDeps 不进生产；用 `pnpm.overrides` 锁定 workspace 协议解析

#### 路线③ 直连 OpenAI 兼容 API（兜底） — **可行**

| 日期 | 尝试 | 结论 |
|---|---|---|
| 2026-09-22 | 读取 `~/.dsh/settings.yaml`（用户本地，项目 .dsh/ 无独立 settings.yaml，仅 settings.yaml.imported）。已配置 3 个 provider：talkweb（baseURL=https://llm.talkweb.com.cn/v1，apiKeyEnv=TALKWEB_API_KEY，6 模型含 deepseek-v4-pro/flash）、zai-coding-cn（apiKeyEnv=ZAI_CODING_CN_API_KEY，glm-5.3 系列）、xiaomi-token-plan-cn（apiKeyEnv=XIAOMI_TOKEN_PLAN_CN_API_KEY，mimo-v2.5 系列）。默认模型 zai-coding-cn/glm-5.3-flash。api 字段为 `openai-completions`，标准 OpenAI 兼容格式。 | **可行**。三个供应商均使用 OpenAI 兼容 API，base_url + apiKeyEnv 格式标准。场景通可直接用 `openai` SDK 或任何 OpenAI 兼容客户端直连，绕过 DSH Agent 会话层。 |

- **优势**：零依赖，不依赖 DSH 构建链；接口标准成熟，SDK 生态丰富；三个供应商互为冗余
- **风险**：(1) 失去 DSH Agent 会话能力（工具调用、插件编排、上下文管理需自行实现）；(2) API Key 管理需场景通自行处理环境变量注入；(3) 与技术方案中"调用单元是 Agent 会话而非裸 LLM"的设计意图冲突

---

#### 最终结论

**推荐优先路线：② vendor workspace 挂载 → ③ 直连兜底**。

| 优先级 | 路线 | 理由 |
|---|---|---|
| **首选** | ② vendor workspace | 与项目现有 vendor 构建路线一致；保持 Agent 会话能力；版本与本地 DSH 同步。实施步骤：修改 pnpm-workspace.yaml 加入 remotes 路径 → pnpm install → 在应用层 `import` 测试 |
| **兜底** | ③ 直连 API | 如果 ② 的 workspace 依赖冲突难以收敛（30+ 包引入），可先用直连 API 快速跑通 M0 核心流程（阶段 1-2 的 LLM 调用），后续再切回 ② |
| **放弃** | ① npm 发布 | 传递依赖链 404，与故障 #1 同根因，短期无解 |
