## #25 按表并发后整步报「完成」，但最后几张表的数据没落库

**现象**：第 2 步重算返回 `done`（无任何告警），中栏却少了「表2-3 分层架构表」「表2-4 要素间关系表」的内容；
原始输出留证里也找不到这两张表的文件。实测一次只落了 5 张表 60 行。

**原因**：调度循环的退出条件写成了「**全部开始**」——`while (started.size < coveredCodes.length)`。
并发下"开始"和"结束"不再同步：最后起始的依赖表（表2-3/表2-4 要等表2-2）刚被起跑，
循环就判定收工返回，两张表还在飞的任务被丢下。更糟的是它们连 `results` 都没有条目，
于是"失败表"统计也漏了它们——**报成功、静默丢数据**。

**解决**：
1. 退出条件改为「全部**结束**」（`settledCount`），另加"没有在跑的任务就收工"的兜底，绝不空转；
2. 任务用 `.catch()` 兜住异常并写入 `results`（失败的依赖不能让下游干等，也不能从统计里消失）；
3. 单表失败当场用 `⚠️` 进度事件说出来（只在收尾汇总里提一句，用户看不到是哪张表卡住的）；
4. 补回归用例「最后才起始的依赖表也必须落库」——故意让依赖表最慢，断言它的行必须落库。

**同一处踩到的第二个坑**：「就绪」原来只判依赖**已开始**（`started.has(dep)`）。
依赖还在跑时下游就被放行，注入的上游上下文是空的，口径照样对不上（表2-4 拿不到表2-2 的要素名）。
改为只判依赖**已完成**（`finished.has(dep)`），并把死锁兜底收紧为"没有任何在跑的任务且一个都起不来"
——否则正常等待也会被兜底误放行。

**教训**：并发的调度条件里，「已开始」和「已完成」是两个必须分开的事实；退出条件审查一遍
"我等的到底是开始还是结束"。
## #26 「阶段 N 补填」的列永远填不上（跨阶段补填是死设计）

- **现象**：表2-5 物理与合规约束的「实现路径 / 责任人」在界面上一直空着（线上 13 行全空）；表3-8 的「排序 / 多源验证 / 对应预算科目」同样全空。用户问「为什么没填」。
- **原因**：契约里这几列标了列级 `filledInStages`（表2-5 标 `[4]`、表3-8 标 `[3]`），写入时 `filterRowByStage` 会把「不属于本阶段」的列**主动剥掉**；但后续阶段不会回头更新上游表（阶段 4 只跑表5-1/5-3/5-4/5-5，阶段 3 只跑表4-1..4-5）——全仓没有任何回填逻辑（`crossStageTables()` 只被一个单测引用）。于是「以后再填」变成「永远不填」，界面上是一列永远空着的表头，用户只会以为是模型偷懒。
- **解决**：① 表2-5 删掉「实现路径 / 责任人 / 状态」（责任人本就有家：表5-3 实施计划的「负责人」）；② 表3-8 三列改为阶段 2 自己填；③ **整个跨阶段补填机制删除**（`TableDef/TableColumn.filledInStages`、`filterRowByStage`、`crossStageTables`、提示词的「跨阶段填写」标注、文档徽标），防止再次出现同类死列。
- **教训**：跨阶段补填只有在「后面那一步真的会更新上游表」时才成立；本产品的生成单位是**本步的表集**，列必须落在生成本表的那个阶段，否则就是死列。

## #27 枚举列大量非法取值：提示词只给了枚举名，没给取值

- **现象**：真实数据里 61 处枚举列取值落在注册表枚举之外——表3-8「痛到什么程度」写成 high/mid/low，表1-3「门槛类型」写成「资质门槛/认证门槛/资金门槛」，「行业通行处置」写成整句解释，表1-2「来源权威性」写成「中」。行校验会报「枚举非法」，但按设计不阻断入库，所以用户直接看到脏值。

- **解决**：两处都改成带取值：`枚举 level_hml，只能取：高 / 中 / 低`（取值由 `enumValues()` 从注册表取，不手写）。副本复跑同一阶段：非法枚举值 0 处。
- **教训**：契约里的枚举只有**同时出现在提示词里**才对模型有效；只给名字等于没约束。

## 28 · 多子块表「块」选不动 / 被冲回第一块

- **现象**：① 演示态（后端不可达时）点「接口块」不生效，视图始终停在「架构块」；② 联真态把「表 + 块」合成一个芯片后（v1.26 起一次点击同时切表和切块），点「成本汇总」会被打回「硬件块」。
- **原因**：`useEffect(() => { setBlock(blocks[0]) }, [blocks])` 这种"默认值重置"写法。演示态的 `blocks` 是每次渲染新建的数组（非 `useMemo`），依赖恒变 → **每次渲染都执行**，用户的选择下一帧就被冲掉；联真态虽然 `blocks` 记忆化了，但"切表"会换掉 `blocks` 引用 → 同样触发重置，把同一帧里刚设好的块冲掉。
- **解决**：改成**条件回落**——`if (block === null || !blocks.includes(block)) setBlock(blocks[0] ?? null)`；演示态的 `blocks` / `categories` 一并 `useMemo`（`activeTable` 为依赖）。实机验证：联真态第 5 步一行 8 个芯片，从「方案架构」直接点「成本汇总」即切到表5-5 汇总块；演示态点「接口清单」换到接口块表头。
- **教训**：**"默认值"不要用"每次渲染重置"实现**，要写成"当前值不合法才回落"。依赖是新建数组/对象的 `useEffect` 等价于每次渲染都跑。

## 29 · 加一个 useMemo 就让第 5 步整页白屏（React #310）

- **现象**：第 5 步点进去整页报错，控制台 `Minified React error #310`（"Rendered more hooks than during the previous render"），中栏渲染不出任何东西。
- **原因**：新加的 `activeRows` useMemo 写在了 `if (status === "loading") return …` / `if (status === "error") return …` **之后**。首屏 loading 分支不执行该 hook，数据到达后走渲染分支才执行 → hook 数量变化，React 直接抛错。
- **解决**：把该 useMemo 挪到所有早返回之前（hook 一律写在组件顶部、早返回之前）。
- **教训**：组件里的 `useState/useMemo/useEffect` 必须全在早返回之前；E2E 只在"点开就有数据"的路径上跑，`tsc` 与单测都抓不到这类错误——**改动视图层后必须在真实链路点开那一步看一眼**（本次是脚本抓控制台错误发现的）。

## 30 · 「核实」上线第一版：模型把行业行情也判成「无法核实」，一个阶段 87 条全进"作废"桶

- **现象**：v1.27 第一次实跑（隔离副本重跑第 2 步）后，87 行的 `verification_verdict` **全部是「无法核实」**，阶段总结的「核实结论」显示「无法核实 87 条——不能当结论用」，等于把整阶段的行情信息一次性作废，比改之前更糟。
- **原因**：判定口径里有「不是本客户事实就写无法核实」的隐含语义，而本阶段信息绝大多数是行业通例（`source_type="AI推断"`、`source="行业通例（模型知识）"`）。模型于是把"不是本客户台账"直接等同于"无法核实"——**把"信息性质"和"核实状态"混成了一档**。
- **解决**：枚举补一档 `行业通例`（行业公开常识/通行做法：**可自证**——公开可查、无利益相关方，但不是本客户事实），并把「无法核实」收窄为**只有两种**：本客户具体事实缺材料、材料冲突到判不了；提示词写死「按行业通例口径写的信息一律给 `行业通例`，不许写无法核实」。重跑：87/87 = 行业通例，无法核实 0，有反证 0。
- **教训**：给模型一档"不确定"时，必须同时说清**什么不算不确定**，否则它会拿这一档当默认值；「信息的性质」与「核实的结论」要分开建维度。

## 31 · 交付物自称「不含任何建议或判断」，表格里却在给策略

- **现象**：内部调研报告/对外材料的页脚写着「本文档只做信息摘要，**不含任何建议或判断**；判断由用户自己做」，而表4-4 细分优先级的内容是「以近场联控作为入口级单点切入，先做单会议室样板再复制」「作为设备层附属能力打包，不单独立项」——**没有依据的、隐形的建议**。
- **原因**：早期定调「不产出判断」只落实到文案（页脚、提示词一句话），没有落到数据模型：判断类的列（`策略`/`对我方含义`/评分）照样存在，却没有任何核实与依据要求。
- **解决**：把判断显性化并加证据责任——口径改为「**不给决策建议**（该不该进由用户定），但**每条信息必须由模型自己核实**」：35 张表统一追加 `核实结论` + `核实说明（准确·客观·为什么）`；阶段总结给核实分布与无法核实/有反证清单；交付物页脚改成同一口径。策略类内容仍在表里，但每行都要交代"凭什么"。
- **教训**：**只改文案不改数据模型的"约束"等于没约束**；声称"不判断"的产品只要还有判断类字段，就一定会输出无依据的判断。

## 33 · 「整理成定义」报 Failed to fetch：不是功能坏了，是那一瞬间服务已经死了

- **现象**：用户新建场景「有限空间安全作业」，对话正常（两次 `POST /definition/messages` 都 200），随后点「整理成定义」弹出 `Failed to fetch`。
- **排查**：① 服务端日志最后一条是 09:31:23 的 messages 200，**之后没有任何 `/definition/consolidate` 的入站请求行**——Fastify 是收到请求先记 `incoming request`，一行都没有说明请求根本没到服务端；② 进程已不存在、端口无人监听，日志里也没有任何异常堆栈（被信号杀，不是代码抛错）；③ 把用户这份库复制到隔离副本（:46191）后，用**同一个场景 id** 调 `POST /definition/consolidate`，7.9 秒正常返回 6 项（场景名称／场景边界／生产对象／核心生产系统／买方类型／采购特征）——端点本身没问题。
- **原因**：应用进程在用户点击前后被外部信号杀掉（无堆栈、无退出码，无法从现场确定是谁发的信号）。浏览器 fetch 拿不到任何响应时只能报 `Failed to fetch`——**这个报错名很容易被误读成"接口错了"**，实际是"服务不在了"。
- **解决**：① 重启应用（`nohup node apps/server/dist/index.js &` + `disown`；注意 macOS 没有 `setsid`，第一次尝试就是被这个坑住的）；② 加自动拉起看护（每 5 秒探端口，掉了自动重启，并**故意 kill 掉验证过**：10 秒内自动回来）；③ 长期建议由用户在自己终端 `npm start`（进程归用户、日志可见），或改用 `launchctl` 托管。
- **教训**：`Failed to fetch` 的第一动作是**看服务端有没有收到请求**（有没有 incoming request 行 + 端口是否在听），而不是去看接口代码；"日志停在哪个请求上"本身就是最强的证据。

## 35 · 迁移脚本的 dry-run 与「自动备份」都漏读了 WAL 里还没落盘的数据

- **现象**：写表3-7 存量迁移脚本（v1.29）时，dry-run 报告「表3-7 总行数 10」，而同一时刻用只读连接查真库是 **18 行**（8 行属另一个场景）。
- **原因**：项目库跑在 **WAL 模式**，最近的写入先落 `<db>-wal`，checkpoint 之后才进主文件。脚本用 `copyFileSync(db, 副本)` 做 dry-run、用 `copyFileSync(db, 备份)` 做备份——**只拷了主文件**。那 8 行是当天 11:05 刚写进去的，还在 WAL 里，于是副本里看不到。
- **影响面**：不止新脚本——`scripts/migrate-anchor-v119.mjs`、`scripts/migrate-info-model.mjs` 用的是同一套写法，**它们的 dry-run 报告会少算，`--apply` 前的「自动备份」也会少掉最新数据**（备份看起来成功了，其实不完整）。
- **修法**：新增 `scripts/lib/sqlite-snapshot.mjs`，统一用 SQLite 自己的 **`VACUUM INTO`** 产出单文件快照——它读的是当前一致的库视图（含 WAL 中已提交的事务），不用关心 checkpoint 时机，也不用去拼 `-wal`/`-shm` 三个文件；三个迁移脚本全部改用它。修完复跑：**18 行**，与真库一致。
- **教训**：凡是「拷贝 SQLite 库文件」的地方都要先问一句「这是 WAL 模式吗」；备份的完整性不能靠"文件拷过去了"来判断，要用**能读出多少行**来验证。顺带记一条路径坑：仓库路径含中文，`new URL(...).pathname` 会做百分号编码导致 `require.resolve` 失败，必须用 `fileURLToPath`。
