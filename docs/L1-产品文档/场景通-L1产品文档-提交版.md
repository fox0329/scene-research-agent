**产品名称**：场景通

**提交人**：李忠良

## 摘要

场景通是给解决方案架构师用的桌面 AI 智能体：接一个客户场景，从材料入库、场景定义，到 6 步分析、26 张信息表，最后产出可讲的《解决方案》和 PPT 大纲，把“这场景能不能进、怎么进、值不值”的调研从几周压到几天。

它不是“帮你写文档”的聊天框，而是把售前调研拆成可执行步骤、把信息结构化和可溯源、最后自动收口成可交付文件的垂直产品。核心产出由 AI 生成，确定性层只做来源、数字、结构和质量门禁；去掉 AI，产品只剩空表和空文档。

本文档按 L1 产品文档的 6 条要求组织：产品介绍与目标用户、需求背景与痛点、价值量化、竞品分析与商业模式、AI 原生设计、AI 能力落点与工程实现。

## 一、产品介绍与目标用户

### 1.1 一句话

**场景通是给解决方案架构师用的桌面 AI 智能体：接一个客户场景，从材料入库、场景定义，到 6 步分析、26 张信息表，最后产出可讲的《解决方案》和 PPT 大纲，把“这场景能不能进、怎么进、值不值”的调研从几周压到几天。**

它不是一个“帮你写文档”的聊天框，而是把售前调研这件事拆成可执行步骤、把每一步的信息结构化和可溯源、最后自动收口成可交付文件的垂直产品。

### 1.2 产品是什么

| 维度    | 说明                                                    |
| ----- | ----------------------------------------------------- |
| 形态    | macOS / Windows 桌面应用，安装后本机运行；不是网页 SaaS                |
| AI 底座 | DeepSeek Harness（DSH）Agent 会话 + 可切换的模型供应商；模型负责内容生成与推理 |
| 数据    | 场景、资料、交付物存本机；不建云端知识库，模型调用只发送必要片段                   |
| 核心工作流 | 6 步：场景定义与边界 → 认识场景 → 理解商业 → 能力匹配 → 方案与实现 → 交付物        |
| 信息载体  | 26 张结构化信息表；逐格可编辑、每行可标来源                               |
| 交付物   | 《XX场景解决方案》＋ PPT 大纲；可导出 Word / PPT / Markdown          |
| 常驻资产  | 产品资料库（产品清单、规格书、能力、边界、报价、认证/案例等）；跨场景复用                 |

### 1.3 目标用户

#### 主用户：解决方案架构师 / 售前方案工程师

| 项    | 说明                                     |
| ---- | -------------------------------------- |
| 角色   | 系统集成商、设备厂商、行业解决方案公司的售前/方案架构师           |
| 日常任务 | 接客户场景 → 判断能不能做 → 组织调研 → 写方案 → 给客户/领导汇报 |
| 使用场景 | 新客户/新行业场景的前期调研；投标前方案准备；存量客户的新场景扩展      |
| 团队规模 | 以 5–50 人的售前/方案团队为主；单团队通常 3–20 名架构师（视行业与公司规模而定） |
| 最痛的点 | 信息散、调研维度容易漏、来源说不清、每次重做、方案写作耗时          |

#### 次用户：售前负责人 / 部门管理者

- 看团队产出的《解决方案》是否客观、有依据、能直接对客户讲；
- 决定是否投入某个场景，而不是自己从零做调研；
- 关心团队复用率、交付周期和方案质量的一致性。

#### 不在目标范围内

- 个人日常写作、会议纪要、通用问答等“个人提效工具”；
- 替客户做最终商业决策的“决策系统”；
- 只做知识库检索、不产出结构化调研与交付物的问答机器人。

### 1.4 典型使用场景（一条完整故事）

1. 架构师接到客户“智慧会议室”需求，手里有客户招标文件、我方产品白皮书、历史案例；
2. 打开场景通，把客户材料上传到当前场景，把我方产品资料放进产品资料库；
3. 新建场景，AI 先讲清这类场景的行业背景，再问 2–3 个关键问题，整理成场景定义；
4. 按 6 步推进：AI 联网调研 + 生成各步信息表，架构师逐格校对、补来源；
5. 每一步右栏有一份阶段总结，随时能看“这一步到底得出了什么”；
6. 最后生成《解决方案》和 PPT 大纲，架构师改完直接导出 Word/PPT，拿去汇报。

### 1.5 核心能力

1. **场景化，不是通用问答**：所有分析围绕一个具体客户场景和一套方法论展开，不靠用户自己想 prompt。
2. **结构化信息**：26 张表把“该看什么”固定下来，避免漏掉合规、竞争、能力边界、交付运维等维度。
3. **来源可追溯**：每条结论可标来源（文件/页码/URL）、权威性 T1–T4、证据等级 A–D；查不到就写“未知”，不编。
4. **AI 原生闭环**：AI 承担场景理解、调研、表格生成、方案与大纲撰写；确定性层只做质量门禁，不替代内容生成。
5. **交付物收口**：不是停在表格，最后产出解决方案 + PPT 大纲，并能导出 Word/PPT/Markdown。
6. **本地与复用**：产品资料库跨场景复用；业务数据存本机、不建云端知识库，适合客户材料不便整包上云的售前场景。

### 1.6 和通用 AI / 通用知识库的区别

| 对比  | 通用大模型/Agent | 通用知识库   | 场景通                    |
| --- | ----------- | ------- | ---------------------- |
| 输入  | 用户自己描述问题    | 上传文档后问答 | 客户场景 + 我方产品资料          |
| 过程  | 一次性对话       | 检索 + 回答 | 6 步方法论 + 26 张表 + 阶段总结  |
| 输出  | 一段文本        | 一段回答/引用 | 结构化信息 + 解决方案 + PPT 大纲  |
| 来源  | 不稳定、常编      | 有引用但不分级 | 来源 + 权威性 + 证据等级，缺来源标未知 |
| 复用  | 无           | 文档级     | 产品资料库跨场景复用             |
| 数据  | 云端          | 云端/私有化  | 本机存储；不建云端知识库           |

### 1.7 产品边界

- **不替用户做最终决策**：产品给信息、给建议、给方案，进不进、投不投由用户拍板。
- **不保证“什么场景都能做”**：能力缺口、资质门槛、价格劣势会如实进表，不靠话术掩盖。
- **不把模型知识当来源**：没有可核验来源的内容标“未知”，不用行业通例冒充客户事实。

## 二、需求背景与痛点

### 2.1 背景：售前调研是方案团队的固定瓶颈

系统集成商、设备厂商和行业方案公司的售前架构师，接到的不是“写一份文档”，而是一个需要判断的客户场景：

- 这个场景客户到底怎么买、预算在谁手里？
- 有哪些硬门槛（资质、合规、接口、交付）？
- 现在谁在供、价格什么水平、我们有没有赢面？
- 如果要做，方案怎么落、交付运维怎么兜？
- 最后怎么快速变成一份能对客户讲的方案？

这套判断依赖大量信息，但信息天然分散、来源复杂、更新快。多数团队靠“老架构师的经验 + 临时搜索 + 拼文档”，结果高度依赖个人，难以复用，也难以保证质量。

### 2.2 痛点清单

#### 痛点 1：材料散落在邮件、网盘、聊天记录里

- **怎么发生**：客户招标文件在邮箱，产品白皮书在共享盘，历史案例在个人电脑，竞品价格在聊天记录；没有一个按“场景/产品线”组织的入口。
- **影响谁**：架构师（找材料）、售前负责人（无法确认团队用的是什么版本）、新同事（上手慢）。
- **现在怎么应对**：每次重新收集；找到什么用什么；版本不一致时靠人记。
- **代价**：重复收集、漏材料、用错版本；一个场景启动的前 1–2 天常常花在找材料上。

#### 痛点 2：不知道该看什么，调研维度容易漏

- **怎么发生**：行业调研没有固定骨架，合规、竞争、上游供给、交付运维、价值指标这些维度，靠个人经验决定查不查。
- **影响谁**：架构师（漏项导致方案被客户问倒）、售前负责人（方案质量参差）。
- **现在怎么应对**：老同事带新人；临时列提纲；参考上一份方案改。
- **代价**：同一个场景不同人做出来差异很大；合规/交付类硬约束常在方案后期才暴露，返工成本高。

#### 痛点 3：来源不可追溯，结论被追问时站不住

- **怎么发生**：调研结论来自网页、报告、聊天或“行业常识”，没有记录出处；客户追问“这个数字哪来的”时答不上。
- **影响谁**：架构师（可信度受损）、公司（方案风险）。
- **现在怎么应对**：凭记忆解释；临时再搜；把“行业通例”当客户事实。
- **代价**：方案可信度低；错误数字进入报价/承诺；严重时影响投标。

#### 痛点 4：每接一个场景就重做一遍

- **怎么发生**：产品能力、案例、认证、报价是全局资产，但每次做新场景都重新收集、重新整理；同一产品线的材料在不同项目里重复上传。
- **影响谁**：架构师、产品经理、售前团队。
- **现在怎么应对**：个人维护自己的资料夹；团队共享盘靠人工同步。
- **代价**：重复劳动；资料越用越散；新人无法复用老人的积累。

#### 痛点 5：方案写作耗时，且质量不稳定

- **怎么发生**：调研做完后，要把信息组织成“现状—问题—方案—价值—实施”的文档；不同人写出来结构、详略、口径都不同。
- **影响谁**：架构师（加班写方案）、负责人（审稿成本）。
- **现在怎么应对**：套模板、复制旧方案、让同事帮忙改。
- **代价**：单份方案写作 1–3 天；模板痕迹重；客户视角弱。

#### 痛点 6：调研过程沉淀不下来

- **怎么发生**：调研结论留在个人文档或脑子里；下一个场景无法复用；竞品、未满足需求没有进入团队资产。
- **影响谁**：团队、管理者。
- **现在怎么应对**：靠人传、靠复盘会、靠共享盘。
- **代价**：人员流动即资产流失；团队整体能力提升慢。

### 2.3 现有替代方案为什么不够

| 替代方案                | 能做什么      | 不够在哪                          |
| ------------------- | --------- | ----------------------------- |
| 人工调研 + Word/PPT     | 灵活、可定制    | 慢、依赖个人、来源不可追溯、难复用             |
| 通用大模型/Deep Research | 快速给一段分析   | 不懂我方产品、不产结构化表、来源不稳定、无法直接形成交付物 |
| 通用知识库/办公 AI         | 检索文档、回答问题 | 只解决“找得到”，不解决“该看什么、看全没有、怎么成方案” |
| 咨询/行业研究报告           | 有行业深度     | 贵、周期长、不针对具体客户场景、不落到我方能力       |
| CRM/售前管理工具          | 管商机/流程    | 不管调研内容，不生成方案                  |

### 2.4 场景通的对应解法

| 痛点     | 场景通的解法                        | 落地位置         |
| ------ | ----------------------------- | ------------ |
| 材料散    | 产品资料库按产品线组织，场景引用；材料一次入库、跨场景复用 | 产品资料库 + 场景项目 |
| 维度漏    | 6 步流程 + 26 张信息表，把“该看什么”固化成骨架  | 流程与表定义       |
| 来源不可追溯 | 每条信息可标来源/权威性/证据等级；没有来源标“未知”   | 来源与证据模型      |
| 重复做    | 产品资料库复用；场景级覆盖不污染主库            | 资料库与场景引用     |
| 方案写作慢  | 阶段总结 + 解决方案 + PPT 大纲自动生成      | 交付物          |
| 沉淀不下来  | 调研结果落库；产品资料与场景资产持续累积          | SQLite 本地库   |

### 2.5 真实场景

以上痛点不是推演出来的，是在真实售前场景里反复出现的：

- 已用场景通跑过智慧会议室、智慧教室、地铁能源管控、管网阀室、智慧厨房等真实场景，走完从材料入库、场景定义到 6 步分析、解决方案与 PPT 大纲的完整链路；
- 这些场景里有客户招标文件、产品白皮书、历史案例、竞品信息等真实材料，材料散、来源杂、需要反复核对的问题都出现过；
- 本文不写客户名称、金额和项目细节；提交版用匿名场景 + 可核对的内部记录说明“真实发生过”。

## 三、价值量化

### 3.1 一句话价值

**场景通把售前调研从“靠人、靠记忆、靠加班”变成“AI 先跑一遍、人只做判断”，价值直接落在周期、质量、复用三本账上。**

### 3.2 周期账：从“周”到“天”

| 环节            | 没有场景通    | 用场景通       | 变化                   |
| ------------- | -------- | ---------- | -------------------- |
| 接到场景到方案可讲     | 1–2周     | 1–2天       | 缩短约 70%–90%          |
| 收集/整理材料       | 1–3 天    | 1–2 小时     | 产品资料库直接复用，不再每次翻邮件/网盘 |
| 调研与分析         | 3–5 个工作日 | 1–2 天      | AI 先完成检索、抽取、填表，人只校对  |
| 写 Word/PPT 初稿 | 1–3 天    | 30 分钟–2 小时 | 解决方案与 PPT 大纲同一次生成    |

一个客户场景，原来要排“下周再给”，现在当天/次日就能拿出可讲版本。售前响应速度从“按周”变成“按天”，这是最直接的价值。

### 3.3 质量账：方案更全、更可信、更一致

- **不漏维度**：6 步流程 + 26 张信息表，把合规、竞争、上游供给、能力边界、交付运维、价值指标固定下来，不再靠个人经验决定查不查。
- **来源站得住**：每条结论可标来源（文件/页码/URL）、权威性 T1–T4、证据等级 A–D；查不到就写“未知”，不拿模型知识冒充客户事实。客户追问“这个数字哪来的”，能当场翻到出处。
- **口径一致**：解决方案与 PPT 大纲由同一套信息生成，不会出现 Word 和 PPT 两套说法。
- **返工更少**：方案初稿就有结构、有来源、有边界，评审/客户退回修改的轮次从 2–3 轮降到 1 轮左右。

### 3.4 复用账：一次入库，长期复用

- 产品资料库按产品线组织，产品清单、规格书、能力、边界、报价、认证/案例一次入库，所有场景引用，不再重复上传。
- 场景级补充与主库隔离，既复用了公司资产，又不会把某个客户的特殊情况写进主库。
- 调研结果落到本地库，竞品、未满足需求、行业趋势持续沉淀；人员流动不等于资产流失。
- 新人上手从“跟着老人跑 4–6 周”缩短到“1–2 周就能独立跑一个场景”，因为方法论和资料库都在产品里。

### 3.5 业务价值：不只是省时间

1. **多接场景**：同样人手每月多承接 10–20 个场景，前端响应速度变成竞争力。
2. **提高方案说服力**：方案有来源、有边界、有差异化，不靠话术；该说“不能做”的地方早说，少投入无效标。
3. **沉淀团队资产**：产品库、场景库、竞品与需求持续积累，团队能力不依赖某个老架构师。
4. **降低新人成本**：新人按 6 步流程就能跑，培养周期从月级降到周级。
5. **数据安全**：业务数据存本机、不建云端知识库；模型调用只发送必要材料片段，可配置本地/私有端点。

### 3.6 价值从哪里来

- **AI 承担重活**：场景理解、联网调研、26 张表初稿、解决方案、PPT 大纲都由 AI 生成，人只做校对和判断；
- **方法论固化**：6 步流程把“该看什么”变成产品能力，不依赖个人经验；
- **来源与证据**：来源、权威性、证据等级随行记录，查不到就标未知；
- **交付物闭环**：不是停在表格，最后直接产出可讲的 Word/PPT；
- **本地与复用**：产品资料库跨场景复用，数据留在本机。

**一句话：场景通卖的不是“一个 AI 功能”，是“一个售前团队更快、更全、更可信地交付方案的能力”。**

## 四、竞品分析与商业模式

### 4.1 市场与客户

#### 谁买、谁用

| 角色  | 是谁                     | 关心什么               |
| --- | ---------------------- | ------------------ |
| 使用者 | 解决方案架构师 / 售前方案工程师      | 少加班、少返工、方案能讲、来源站得住 |
| 购买者 | 售前总监 / 解决方案负责人 / 数字化部门 | 团队人效、方案质量一致性、可复用资产 |
| 决策者 | 事业部/公司管理层              | 投入产出、客户响应速度、赢单率    |

#### 目标客户类型

1. **系统集成商**：多行业、多产品线，售前团队规模 10–100 人，方案重复度高；
2. **设备/产品厂商的售前部门**：产品资料多，场景跨行业，最需要“产品能力 × 场景”的匹配；
3. **行业解决方案公司/咨询公司**：需要快速判断新场景、输出可讲方案；
4. **大中型企业数字化部门**：内部场景多，需本地化、数据不出内网。

#### 购买触发点

- 新行业/新场景拓展，售前人手不够；
- 投标/大客户方案周期紧，返工多；
- 产品资料散、新人上手慢；
- 客户要求“说清依据”，现有方案来源站不住；
- 团队想沉淀可复用的行业/产品资产。

### 4.2 竞品格局（按替代关系分四类）

#### 4.2.1 通用大模型 / Deep Research

代表：ChatGPT（含 Deep Research）、Claude、Microsoft Copilot、豆包/通义/文心等。

| 能力      | 表现             | 对场景通的影响              |
| ------- | -------------- | -------------------- |
| 通用调研/写作 | 强，能快速生成分析      | 用户可能觉得“用 ChatGPT 就行” |
| 我方产品知识  | 不懂，需要用户每次贴资料   | 场景通的产品资料库是差异         |
| 结构化流程   | 无，靠用户自己 prompt | 6 步/26 表是差异          |
| 来源可信    | 不稳定，常无出处       | 来源/证据分级是差异           |
| 交付物     | 一段文本，需人工再整理    | 解决方案 + PPT 大纲闭环是差异   |
| 数据      | 云端             | 本地桌面是差异（客户材料敏感时）     |

#### 4.2.2 办公/知识库 AI

代表：飞书智能伙伴、Notion AI、钉钉 AI 助理、企业知识库产品。

| 能力      | 表现              | 对场景通的影响           |
| ------- | --------------- | ----------------- |
| 文档检索/问答 | 强               | 解决“找得到”，不解决“该看什么” |
| 流程/表格   | 弱，偏通用           | 场景通的 26 张表是垂直资产   |
| 来源追溯    | 有引用，但不做权威性/证据分级 | 场景通更严格            |
| 交付物     | 不生成售前解决方案       | 场景通闭环更强           |
| 数据      | SaaS 为主         | 本地/私有化是差异         |

#### 4.2.3 咨询/行业研究

代表：赛迪顾问、艾瑞咨询、头豹研究院、行业咨询公司。

| 能力     | 表现       | 对场景通的影响           |
| ------ | -------- | ----------------- |
| 行业深度   | 强，有专家与报告 | 场景通不替代深度咨询        |
| 客户场景定制 | 弱，报告通用   | 场景通按客户场景生成        |
| 周期/价格  | 周/月级，费用高 | 场景通是“日常工具”，不是咨询替代 |
| 我方能力匹配 | 通常不含     | 场景通结合产品资料库        |

**定位**：咨询是“深度外包”，场景通是“团队日常提效 + 方案初稿”；可互补，不正面竞争。

#### 4.2.4 售前/标书/CRM 工具

代表：销售易、纷享销客、标书制作/查重工具、方案模板库。

| 能力      | 表现  | 对场景通的影响      |
| ------- | --- | ------------ |
| 商机/流程管理 | 强   | 场景通不做 CRM    |
| 标书排版/查重 | 强   | 场景通不做标书排版    |
| 调研与方案内容 | 弱   | 场景通补内容生产     |
| 产品资料库   | 弱/无 | 场景通的产品资料库是差异 |

**定位**：可与 CRM/标书工具集成，不替代。

#### 4.2.5 竞品对比总表

| 类别 | 代表产品 | 强项 | 收费模式 | 短板 / 场景通差异 |
|---|---|---|---|---|
| 通用大模型 / Deep Research | ChatGPT、Claude、Microsoft Copilot、豆包/通义/文心 | 通用推理、写作、联网调研 | 个人订阅 / 团队按席位 / 企业版询价 | 不懂我方产品、不产 26 张表、来源不稳定、交付物不闭环 |
| 办公 / 知识库 AI | 飞书智能伙伴、Notion AI、钉钉 AI 助理 | 文档检索、企业协作、知识库 | 按席位订阅 / 企业版 | 解决“找得到”，不解决“该看什么、看全没有、怎么成方案” |
| 咨询 / 行业研究 | 赛迪顾问、艾瑞咨询、头豹研究院 | 行业深度、专家资源 | 项目制 / 报告购买 | 贵、周期长、不针对具体客户场景、不含我方能力匹配 |
| 售前 / 标书 / CRM | 销售易、纷享销客、标书工具、方案模板库 | 商机流程、标书排版、模板 | 按席位 / 项目 / 企业定制 | 不生产调研内容与方案正文；可与场景通互补 |

> 本内部测试不展开具体竞品价格与市场规模测算；正式商业评估另做。场景通不靠“比通用模型便宜”竞争，而靠垂直流程、产品资料库和交付物闭环。

### 4.3 竞争结论

场景通的差异化不在“模型更强”，而在**垂直流程 + 产品资料库 + 来源可信 + 交付物闭环 + 本地数据**：

1. 通用模型有智力，但没有“售前调研的骨架”和“我方产品底账”；
2. 知识库有资料，但不告诉你“该看什么、看全没有”；
3. 咨询有深度，但贵、慢、不针对具体客户场景；
4. CRM/标书工具有流程，但不生产方案内容。

**风险**：通用模型能力持续增强，会压缩“通用调研/写作”的价值；场景通必须把壁垒放在**垂直数据（产品库/场景资产）、流程标准、证据与交付物**上。

### 4.4 商业模式

#### 4.4.1 收费对象

- 首要：售前/解决方案团队（按席位）；
- 其次：企业级私有化部署（按年授权 + 实施/维护）；
- 补充：按项目/按场景的报告包（低频客户）。

#### 4.4.2 三种模式对比

| 模式         | 怎么收          | 适合谁         | 优点             | 风险               |
| ---------- | ------------ | ----------- | -------------- | ---------------- |
| A. 团队席位订阅  | 每架构师每月/每年    | 中小售前团队      | 简单、可扩张、与使用频率挂钩 | 客户可能觉得“又一个 SaaS” |
| B. 私有化授权   | 年授权费 + 实施/维护 | 大型企业、客户数据敏感 | 客单价高、粘性强       | 交付重、销售周期长        |
| C. 按项目/场景包 | 每场景/每份报告     | 低频、试用型客户    | 门槛低、易试用        | 收入不稳定、难预测        |

**建议**：先 A 验证付费意愿，B 做高价值客户；C 只作为试用/补充，不做主力。

#### 4.4.3 定价原则

- **价值定价**：定价应让客户能用节省的人天算得过账；具体价格在商务阶段按客户规模确定；
- **按席位**：与使用者数量挂钩，简单透明；
- **私有化服务**：数据存本机、可接内部模型/知识库，按部署与维护工作量收费；
- **不按 token 收费**：售前用户不关心模型成本，按结果/席位更容易理解。

### 4.5 获客与落地路径

1. **内部试点**：先在 1–2 个售前团队用 4 周，记录周期/人天/返工；
2. **案例包**：匿名化 3 个场景的前后对比，形成可转发的案例；
3. **渠道**：厂商售前体系、集成商合作伙伴、行业社群；
4. **产品化**：从“单机工具”到“团队版”（共享产品库/模板/权限）再到“私有化”；
5. **服务**：轻咨询（场景梳理/模板定制）带动订阅。

### 4.6 壁垒与风险

**壁垒**：

- 垂直流程与 26 张表的领域资产（不是通用 prompt）；
- 产品资料库与历史场景资产（越用越厚）；
- 来源/证据/质量门禁形成的可信度；
- 本地化部署能力（业务数据存本机，可接内部模型，材料不整包上传）。

**风险**：

- 通用模型能力提升，压缩“通用调研”价值；
- 客户不愿为“工具”付费，除非能证明人效/赢单；
- 模型/检索成本与稳定性；
- 售前流程非标，产品需要行业模板；
- 数据安全与合规（客户材料、模型调用）。

## 五、AI 原生设计说明

### 5.1 什么叫 AI 原生

AI 原生不是“在原有表单上加一个聊天框”，而是：

1. **产品的核心产出由 AI 生成**：场景理解、调研分析、表格初稿、解决方案、PPT 大纲；
2. **交互以自然语言/智能体为主**：用户说清场景，AI 决定查什么、填哪张表、怎么收口；
3. **去掉 AI，产品不成立**：剩下的是一堆空表和空文档，用户无法在合理时间内完成调研；
4. **确定性层只做质量门禁**：来源校验、数字可溯源、结构校验、导出格式，不替代 AI 的内容生成。

场景通按这四条设计。

### 5.2 为什么核心功能必须由 AI 承担

售前调研的难点不是“把用户已知的信息填进表”，而是：

- 用户只知道一个模糊场景名，AI 要先把行业/场景讲清楚，再问关键问题；
- 需要联网找公开资料，判断哪些能用、哪些是广告、哪些没有来源；
- 需要把非结构化材料（招标文件、白皮书、案例）变成 26 张表的结构化行；
- 需要把表格结论组织成客户能听的解决方案与 PPT 大纲。

这些工作依赖**语义理解、信息抽取、跨来源归纳、自然语言生成**，规则引擎做不了；通用表单也做不了。去掉 AI，用户仍然要自己搜、自己读、自己填、自己写——产品就退化成“表格模板”。

### 5.3 AI 在 6 步流程中的落点

| 步骤         | AI 做什么                               | 用户做什么    |
| ---------- | ------------------------------------ | -------- |
| 1. 场景定义与边界 | 先讲清行业/场景，再提 ≤3 个关键问题；整理成场景锚          | 回答、补充、确认 |
| 2. 认识场景    | 联网调研 + 生成门槛/要素/架构/约束等表               | 校对、补来源   |
| 3. 理解商业    | 调研利润池、方案形态、采购、竞品、替代、坑、需求、趋势          | 校对、判断    |
| 4. 能力匹配    | 结合我方产品资料，生成能力底账、参与地图、需求-能力对照、优先级、竞争力 | 校对、补证据   |
| 5. 方案与实现   | 生成架构/接口、实施计划、交付运维                    | 校对、补边界   |
| 6. 交付物     | 汇总全链，写《解决方案》＋同步生成 PPT 大纲             | 审阅、编辑、导出 |

每一步都不是“用户填完表让 AI 润色”，而是 **AI 先产出初稿，用户做审核与补充**；核心内容由 AI 驱动。

### 5.4 AI 原生交互

#### 5.4.1 对话式定义，不是先填表

新建场景只输名称，AI 先讲清“这类场景大概是什么样”，再问客户/行业、覆盖范围等关键问题；用户说“大概”，AI 整理成表。避免一上来给用户 26 张空表。

#### 5.4.2 右栏对话改表

用户可以在右栏直接说“把第 3 行改成……”“补一条来源”，AI 调工具改表；中栏实时刷新。用户不需要找单元格、不需要记字段名。

#### 5.4.3 智能体自主决策

AI 根据当前步骤决定：

- 先联网检索还是先读材料；
- 查哪些 query、抓哪些页面；
- 填哪张表、哪些字段留“未知”；
- 是否重试、是否收口到交付物。

用户看到的是进度与结果，不是“选菜单”。

#### 5.4.4 人机分工

| 环节   | AI       | 人           |
| ---- | -------- | ----------- |
| 场景理解 | 先讲、提问、整理 | 确认/纠正       |
| 调研   | 检索、抽取、归纳 | 判断可信度、补一手信息 |
| 填表   | 生成初稿     | 逐格校对、补来源    |
| 交付物  | 写解决方案、大纲 | 审阅、改口径、导出   |
| 决策   | 给信息与建议   | **最终拍板**    |

> 这不是“AI 只做辅助”，而是“AI 做重活，人做判断”。评审如果看到“人还要大量填表”，说明演示没把 AI 初稿展示出来。

### 5.5 确定性层与 AI 的边界（防止“AI 胡说”）

| 事项        | 归属         | 做法                        |
| --------- | ---------- | ------------------------- |
| 来源是否存在    | 确定性层       | 来源必须能定位到文件页码/URL；查不到标“未知” |
| 数字是否来自正文  | 确定性层       | 数字/比例与材料比对，禁止编造           |
| 表结构/字段/长度 | 确定性层       | 契约校验，不合法就修正/提示            |
| 质量门禁      | 确定性层       | 导出前逐条检查，问题点名，不静默放行        |
| 内容归纳/表达   | AI         | 模型生成，允许用户修改               |
| 场景判断/建议   | AI 给建议，人决定 | 产品不替用户拍板                  |

这套分工既保证 AI 原生，又避免“模型说啥就是啥”。

### 5.6 失败与兜底

| 失败               | 产品行为                         |
| ---------------- | ---------------------------- |
| 联网检索不到来源         | 该步写“未知（未检索到公开来源）”，不编；提示用户补材料 |
| 模型返回空/截断/不合 JSON | 重试一次；仍失败保留已有内容并提示，不静默丢数据     |
| 模型调用失败           | 显示原因，可重试；不阻断已完成的步骤           |
| 表格字段不合法          | 确定性校验修正/丢弃非法行，提示原因           |
| 用户改过内容           | 先读后写，保留用户版本，另存新版本，不覆盖        |
| PPT 组件缺失         | 提示安装/先导出 Word，不阻断主流程         |

### 5.7 为什么不是“AI 辅助工具”

对照评审的扣分红线：

| 红线             | 场景通的回答                         |
| -------------- | ------------------------------ |
| AI 只做辅助，去掉也能用  | 去掉 AI，26 张表和解决方案都要人从零写；产品只剩空模板 |
| 传统菜单/表单交互      | 核心入口是对话：场景定义、右栏改表、交付物生成        |
| Demo 有断点、需人工补充 | 材料→分析→交付物→导出闭环；人只做校对           |
| 只交文档不交 Demo    | 有桌面安装包 + 可录制的完整流程              |
| 交互是填表          | 表格是“AI 初稿的审核界面”，不是用户从零录入的入口    |

### 5.8 一句话总结

场景通的 AI 不是“附加的写作功能”，而是产品的主生产流程：场景是 AI 理解的、表是 AI 先填的、方案和大纲是 AI 写的，人只做判断和校对。去掉 AI，产品只剩 26 张空表和空文档——这就是“AI 原生”与“AI 辅助”的区别。

## 六、AI 能力落点与工程实现

### 6.1 工程总览

场景通是“桌面壳 + 本机服务 + 本地库 + AI 引擎”的单机应用：

```
Electron 桌面壳（macOS / Windows）
  ├── React + Vite 前端（三栏工作台）
  ├── Fastify 本机服务（127.0.0.1，随机端口）
  │     ├── 应用层：场景/流程/表格/对话/交付物/导出
  │     ├── 领域层：判定、校验、质量门禁（纯 TS，可单测）
  │     └── 基础设施：SQLite、文档解析、DSH 客户端
  └── 本地数据目录（场景、资料、交付物、日志）

AI 引擎：DeepSeek Harness（DSH）Agent 会话 / OpenAI 兼容模型
```

关键工程选择：

| 选择                     | 原因                              |
| ---------------------- | ------------------------------- |
| 桌面应用，不是网页 SaaS         | 客户材料敏感；业务数据存本机、本地服务，模型调用只发必要片段 |
| 本机 Fastify + 随机端口      | 不暴露公网；只绑 127.0.0.1；桌面壳负责启动/健康检查 |
| SQLite（better-sqlite3） | 单机单人，无需数据库服务；事务与迁移简单            |
| DSH Agent 会话           | 支持工具调用、流式输出、断点续做；模型可切换          |
| 确定性领域层                 | 来源/数字/结构/质量门禁可单测，不把判定交给模型       |
| 契约共享（TypeScript）       | 前后端同一套类型，26 张表结构单一事实源           |

### 6.2 端到端流程

```mermaid
flowchart LR
  A[上传客户材料/产品资料] --> B[解析入库]
  B --> C[新建场景]
  C --> D[AI 场景定义对话]
  D --> E[表1-1 场景锚]
  E --> F[6 步分析: 检索→生成→校验]
  F --> G[26 张信息表]
  G --> H[阶段总结]
  H --> I[解决方案 + PPT 大纲]
  I --> J[导出 Word/PPT/Markdown]
```

每一步的 AI 调用都带：

- 系统提示：角色、当前步骤、目标表结构、质量要求、禁止事项；
- 用户输入：场景锚、上游表、材料摘要、检索结果；
- 输出契约：JSON/表格结构，服务端校验后落库；
- 失败策略：重试、降级、保留旧内容、提示用户。

### 6.3 AI 能力落点（逐项）

| #   | 能力     | 模型/能力          | 输入            | 输出             | 失败兜底                |
| --- | ------ | -------------- | ------------- | -------------- | ------------------- |
| 1   | 场景定义   | 对话 + 行业知识      | 场景名、用户回答、材料   | 行业说明、关键问题、表1-1 | 问不出就按用户输入整理，标“系统推断” |
| 2   | 联网调研   | Agent + web 工具 | 场景/步骤/实体      | 来源列表 + 正文摘要    | 无来源写“未知”，不编         |
| 3   | 表格生成   | 结构化输出          | 场景锚、上游表、材料、来源 | 26 张表的行/列      | 字段不合法修正/丢弃，提示原因     |
| 4   | 阶段总结   | 归纳生成           | 本步表格          | 右栏总结文档         | 生成失败保留表格，可重试        |
| 5   | 解决方案   | 长文生成           | 全链表格/总结       | 七章 Markdown    | 分章重试/兜底，不产空文件       |
| 6   | PPT 大纲 | 结构化生成          | 解决方案正文        | 6–15 页大纲       | 失败不推翻解决方案，可重生成      |
| 7   | 对话改表   | 工具调用           | 用户自然语言 + 当前表  | 单元格更新          | 找不到目标就反问，不猜         |
| 8   | 导出     | 确定性渲染          | 正文/大纲         | docx/pptx/md   | 失败给原因，不产生半文件        |

### 6.4 关键工程实现

#### 6.4.1 Agent 运行时

- 消息日志：system + user + assistant tool_calls + tool results；
- 多步循环：模型可连续调工具（读表、写表、检索、保存），最多 N 步，重复调用去重；
- 工具结果回喂：模型根据结果决定继续/修正/收口；
- 流式输出：SSE 推进度，前端可续连；
- 失败反馈：工具错误作为 tool 消息回给模型，不直接中断。

#### 6.4.2 结构化输出与校验

- 契约定义 26 张表的列、必填、长度、枚举；
- 模型输出 JSON → 服务端解析 → 领域层校验 → 非法行修正/丢弃并提示；
- 关键数字与来源做确定性比对；
- 质量门禁在导出前逐条跑，问题点名到页/行。

#### 6.4.3 来源与证据

- 来源类型：材料文件（文件名 + 页码）、URL（标题 + 日期）、用户输入；
- 权威性 T1–T4、证据等级 A–D；
- 没有来源 → 写“未知”，不拿模型知识冒充；
- 来源索引与全文检索（SQLite FTS）。

#### 6.4.4 本地数据与安全

- 数据目录：macOS `~/Library/Application Support/@scene/desktop/data/`；Windows `%APPDATA%\@scene\desktop\data\`；
- 服务只绑 `127.0.0.1`，随机端口；
- 模型 Key 应用内配置，本地保存；
- 客户材料与业务数据存本机，不建云端知识库；只有模型调用所需的摘要/片段发给配置的模型端点；
- 日志脱敏，不记录 Key。

#### 6.4.5 交付与打包

- Electron 36 + electron-builder；
- macOS Apple 芯片 dmg；Windows x64 setup；
- Windows 安装包内置 PPT 组件（Python + ppt-master 脚本），装完可导出 PPT；
- GitHub Actions 双平台构建 + 真启动冒烟 + 打包冒烟；
- 版本 0.9.4。

#### 6.4.6 质量验证

- 单元测试：108 文件 / 1,998 例；
- E2E：51 例（真实服务 + 浏览器）；
- 类型检查 0 错误；
- CI：macOS / Windows 各自构建、启动、检查数据库与页面。

### 6.5 PRD 摘要

#### 产品目标

让解决方案架构师在一个桌面应用内完成“客户场景调研 → 结构化信息 → 可讲方案”的闭环。

#### 核心用户故事

1. 作为架构师，我上传客户材料后，AI 能先理解场景并问我关键问题，而不是让我填 26 张表；
2. 作为架构师，我按 6 步推进，每一步 AI 先给初稿，我能逐格校对并看到来源；
3. 作为架构师，我能在右栏用自然语言改表，中栏立即更新；
4. 作为架构师，我最后能一键生成解决方案和 PPT 大纲，并导出 Word/PPT；
5. 作为售前负责人，我能看到方案里的每条结论有来源，没有来源的标“未知”。

#### 功能范围

- 产品资料库：上传/解析/去重/跨场景引用；
- 场景项目：新建/重命名/归档/删除；
- 场景定义对话；
- 6 步流程与 26 张表；
- 右栏对话改表、阶段总结；
- 解决方案 + PPT 大纲 + 导出；
- 模型配置、安装/升级、本地数据。

#### 验收口径

- 安装可启动、数据不丢；
- 6 步能走完，表可编辑，来源可追溯；
- 解决方案/PPT 大纲能生成并导出；
- 关键错误有提示，不白屏/不静默丢数据。

### 6.6 已知限制与交付边界

- 安装包未签名：macOS 首次需右键打开，Windows SmartScreen 需“仍要运行”；
- 本版无内置备份/恢复：升级前需手动复制应用数据目录；
- 重复入库按行去重：模型重抽的值变体保留原值并提示冲突；
- PPT 导出依赖本机/内置组件：Windows 0.9.2 起已内置，macOS 需本机 Python；
- 联网调研受目标站点反爬/网络影响：失败时如实标“未知”，不伪造来源；
- 当前版本是单机版，不含团队共享库、权限与多租户。

这些限制不影响核心闭环，但演示和交付时要提前说明，避免评委按“成熟 SaaS”预期检查。
