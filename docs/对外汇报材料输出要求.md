## 二、总体口径

1. **读者**：客户的业务与 IT 负责人。他们没看过调研表，读到的必须是一份能独立成立的方案。
2. **口吻**：给客户做汇报的方案撰写人。章章落到客户身上——现状说这空间今天怎么运转、卡在哪；场景与问题说客户自己的痛；方案说我方做什么、做到哪一步、接口在哪、不做什么；价值说采用之后变成什么样、怎么核；下一步说谁在什么时候交付什么。
3. **不给决策建议**：不写"建议先做试点""推荐采用""值得投入""应当优先""不建议上"。
4. **不含内部信息**：不出现内部表号（表X-X）；不出现来源标注（文件名、页码、URL、"来源：/出处："）；不出现证据等级、权威性、核实结论、信息完整度、待补齐/信息缺口；不出现 `ingest-*`；不出现竞品身份与竞争位势判断；不出现我方财务测算与利润池（成本、报价、毛利推演）。
5. **篇幅**：正文（表格不计）**约 2,600–3,200 字**，全文约 6,900 字。定稿实测正文 **2,644 字**、全文 6,860 字；逐章正文基准：现状 888 / 场景与问题 169 / 方案 1,203 / 价值 9 / 下一步 251。**表格是结构**（定稿 6 张表：既有体系 8 行、总体架构 6 行、主辅职责 7 行、选型与配置 12 行、价值 6 行、步骤与交付物 11 行），表格不计入正文；流水账是正文又把表里的行讲了一遍。
6. **表格与正文分工**：表格承载结构，正文给判断与代价。定稿：现状章 5 段 + 1 表、场景与问题 2 段无表、方案章 3 段 + 3 表 + ①–⑤ 编号连接、价值章**只有 1 张表**、下一步 1 段 + 1 表。
7. **规则铁律**：
   - 只用调研得到的信息，不改数字、不引入材料外信息；
   - 不给决策建议、不含内部信息（见 3、4）；
   - **不写整段的自我说明与免责**；分条不用「一、二、」式编号（章标题除外），用「第一 / 其一 / 价值一 / ①」。
8. **口径与量的处理**：
   - 具体数字优先（CT15、AI Box 6TOPS NPU、200+ 工业协议、4096 字节、第 1–23 天、4K30）；
   - **行业量级一律括注「（行业通例量级）」**（价值表里逐条出现）；
   - **服务水平直接陈述，不加免责括注**——定稿删掉了「（以上为行业常见服务水平，非本客户承诺）」，写「到货约 30 天、远程响应 ≤2 工作小时…」即可；
   - 客户还没给的写「待客户提供 / 待客户确认」（如"接口与数据同步待确认""客户提供接口与鉴权"），一句话带过，不写成整段免责，也不逐条挂"待补"。

## 四、行文规范

1. **说人话**：不用"赋能 / 抓手 / 闭环"这类空话；型号与术语首次出现给一句限定（如"AI Box 边缘算力，6TOPS NPU，已交付"）。
2. **不写说明书腔与自证句**：不写「口径是…」「度量口径是…」「本节出现的数字…」「数据来源：…」；要交代的口径直接写在数字旁边（如「（行业通例量级）」）。
3. **一个事实只说一次**：能在表里说的，正文不再讲一遍。
4. **先结论后依据**：小节与段落开头一句就是判断，后面才是支撑；单段 2–5 句。
5. **加粗只用于条目首句**（原则、价值条、特征），不强调句中词。
6. **表格**：表头用中文短名（层次/现有构成/现状主要接口、需求/选型/边界与前置条件、价值/现在/采用后/怎么核）；单元格写结论与关键参数，不写整句话；缺数据写 `—`。
7. **标点**：中文全角；区间用 `~` 或 `–`（2 万~8 万、第 1–23 天、4K30）；编号用「第一/其一/价值一」与 ①②③；引号用「」或 `""`。
8. **术语与型号与定稿完全一致**：在鸿、在鸿·近场通、在鸿物联平台、元服务、碰一碰、物模型、分布式软总线、CT15/CT16/CT21B/CT31/CT32/CT33/CT34、PD34、7885 平板、AI Box、claw 智能体。
9. **行业口径与客户事实分开**：行业量级加括注；本客户未提供的不编具体数字，写「待客户提供 / 待客户确认」并点到缺什么（接口与鉴权、信创目录、预约数据）。

## 五、校验与生成流程

**硬伤（重写一次；仍不过则保留正文并提示）**

- **缺章**：五章必须齐——现状 / 场景与问题 / 方案 / 价值 / 下一步；
- **缺少方案构件**：自建表格（≥3 张）、设计原则、①②③ 编号连接关系、**对外价值表**（表头含 价值/现在/采用后/怎么核，数据行 ≥3）；
- **对外泄漏内部信息**：内部表号 `表X-X`；`来源：/出处：/摘自：/参见：/依据材料：`；`证据级/权威性/核实结论/信息完整度/待补齐/信息缺口`；`ingest-*`；
- **出现决策建议**：`建议先 / 优先 / 应当 / 应该 / 推荐采用 / 值得投入 / 不建议` 这类措辞；
- **价值写成缺口清单**：价值章出现 ≥3 处 `待补 / 未提供 / 待补充 / 无法核实 / 需客户提供 / 尚需`。

**软提示（不阻断）**

- 缺小节（对照 `### 场景在业务中的位置 / 既有体系构成 / 现状特征与提升空间 / 设计原则 / 总体架构 / 主辅职责对照 / 连接关系与接口 / 选型与配置 / 实施要点 / 步骤与交付物`。**「场景边界」「七类问题」「价值表」在定稿里不单独成节**——契约已按 `noHeading` 跳过，不会再报）；
- 正文用了章号式编号（`**一、`）；说明书腔（价值章 ≥2 处「度量口径是/口径是/本条信息/数据来源：」）；说明性套话（"不含决策建议""以试点实测为准""本节出现的数字""本材料只陈述"）；篇幅超标或不足。

**篇幅口径（按定稿校准）**

| 口径 | 值 | 说明 |
|---|---|---|
| 校验上下限（`report-gate.ts`） | 正文 **1,200–4,500 字** | 定稿 2,644 字，通过 |
| 提示词建议（`report-prompts.ts`） | 正文 **2,500–3,200 字** | 对齐定稿 2,644 字 |
| 逐章回炉触发线（`PROSE_BUDGET.external`） | 现状 **1,000** / 场景与问题 **300** / 方案 **1,350** / 价值 **200** / 下一步 **400** | 定稿实测 888 / 169 / 1,203 / 9 / 251；回炉线必须高于定稿，否则一生成就被压改 |
| 篇幅基准（定稿） | 见 §二.5 | 逐章预算是**回炉线**，不是篇幅目标 |

**压缩守恒（只删不加）**：某章正文超预算时让模型压一次——不许引入素材外信息、不许改数字与判定；删的是同一事实的重复、铺垫与过渡句、对表格的复述、形容词与套话、自我说明与免责；留的是结论、判断、代价、边界与表格本身；**表格原样保留**，`##` 章名与 `###` 小节标题一个都不能少、不许改名或合并；方案构件（设计原则 / 编号连接 / 价值表）必须留；分条不许改成「一、二、」；不许留半句话。三种情形**作废这次压缩、保留原正文**（宁可偏长，不能缺构件）：构件变少；原本有 `###` 小节、压完一个小节都不剩；出现残句（短段落不以句末标点收尾）。

**生成流程**（`apps/server/src/deliverable-report.ts`）

1. 按章取素材 → 按章撰写（每块素材最多 12 行，归纳责任在模型）；
2. 确定性校验 → 有硬伤带违规清单**重写一次**；
3. 缺章**单独补写一次**；
4. 逐章篇幅回炉（超预算压一次，带上面的守恒守卫）；
5. 装配：封面（`# <场景名称> 对外汇报材料 <日期>` + 场景行 + 日期行）→ 五章（`---` 分隔）；某章完全没写出来时用要点版兜底。**不追加附录或术语表。**

## 六、可直接复用的提示词骨架

```text
你是给客户做汇报的方案撰写人，不是材料的整理者。读者是客户的业务与 IT 负责人，他们没看过我们的调研表。
全篇只有一个主角——我们的方案：现状说这个空间今天怎么运转、卡在哪；场景与问题说客户自己的痛；
方案说我们做什么、做到哪一步、接口在哪、不做什么；价值说采用之后变成什么样、怎么核；下一步说谁在什么时候交付什么。
只说客户能验证的事实与行业通例：行业量级一律括注「行业通例量级」；服务水平直接写数字，不加免责括注；
客户还没给的写「待客户提供 / 待客户确认」，一句话带过，不写成整段说明。
不许出现：内部表号（表X-X）、来源与页码、证据等级与核实口径、竞品身份、我方财务测算与利润池、
决策建议（建议 / 推荐 / 值得投入 / 应当优先 / 不建议）。
输出 Markdown：`# <场景名称> 对外汇报材料 <日期>` 起；封面两行引用块（场景 + 日期）；五章用 `## 一、…`（现状 / 场景与问题 /
方案 / 价值 / 下一步），章间 `---`，小节用 `### …`；写到「五、下一步」为止，不要附录、不要术语表。
逐章骨架：
- 一、现状：`### 场景在业务中的位置`（2 段：承载什么、谁负责哪一段；采购与预算怎么走、三方口径为什么对不上）
  → `### 既有体系构成`（一句过渡 + 一张 `层次 | 现有构成 | 现状主要接口` 表，8 层）
  → `### 现状特征与提升空间`（2 段：三个特征决定天花板 + 提升空间三处与行业趋势同向）。
- 二、场景与问题：先一句场景边界、再一段七类问题归纳（**都不设小节标题、也不写门槛与合规**）。
- 三、方案：`### 设计原则`（原则一/二/三）→ `### 总体架构`（层次 | 我方组件 | 承担什么）
  → `### 主辅职责对照`（环节 | 我方角色 | 我方做什么 | 谁来做其余部分）→ `### 连接关系与接口`（①–⑤）
  → `### 选型与配置`（需求 | 选型 | 边界与前置条件）→ `### 实施要点`（23 个工作日主线一段 + 回退路径一段）。
- 四、价值：**只有一张四列表** `| 价值 | 现在 | 采用后 | 怎么核 |`（6 行），**不套小节标题、不写边界段落**。
- 五、下一步：`### 步骤与交付物`（步骤 | 时间窗口 | 交付物 | 前置条件）→ 表后一段交付与运维口径
  （直接写数字，不加免责括注）+ 试点建议 + 成功判据示例区间。
写法：先结论后依据；一个事实只说一次；表格承载结构、正文给判断；分条用「第一 / 其一 / 价值一」，
不许用「一、二、」；不写「口径是…」这类自证句，也不写整段免责。
```

## 七、与内部调研报告输出要求的差异

| 项 | 对外汇报材料 | 内部调研报告 |
|---|---|---|
| 类型名与标题 | 标题 `# <场景> 对外汇报材料 <日期>`（与文件名一致） | 标题 `# <场景> 内部调研报告 <日期>` |
| 封面 | 场景行 + **日期**行 | 场景行 + **生成日期**行 |
| 章节 | 五章（现状 / 场景与问题 / 方案 / 价值 / 下一步），**无附录、无术语表** | 五章（现状 / 场景与问题 / 方案 / 价值 / **主要风险点**），无下一步、无附录 |
| 一、现状 | 三节**都有**小节标题 | 前两段并进章首导语，只 `### 现状特征与提升空间` |
| 二、场景与问题 | 章下两段，**没有任何小节**（无门槛与合规） | `### 场景边界` + `### 典型问题` |
| 三、方案 | 六节，**有** `### 实施要点` | 五节，**无**实施要点 |
| 四、价值 | **只有四列表格**（价值/现在/采用后/**怎么核**），无边界段落 | 段落式 `**价值N：…** 现在：… 采用后：…` + `### 能力边界`，**不写怎么核** |
| 五、主要风险点 | 无（风险信息不单独成章） | **有**，章下直接 3–8 条、不套小节 |
| 结尾 | 到「五、下一步」；给交付口径、试点建议与成功判据 | 到「五、主要风险点」；不写缺口与出处 |
| 校验差异 | 多「对外泄漏内部信息」；篇幅 1,200–4,500 | 多「缺风险或边界」；篇幅 1,800–6,000 |
