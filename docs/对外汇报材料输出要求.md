## 二、总体口径

1. **读者**：客户的业务与 IT 负责人（他们没看过 33 张信息表，也可能没读过我们的内部调研报告）。
2. **口吻**：**给客户做汇报的方案撰写人**，不是材料整理员。章章落到客户身上——现状说这个空间今天怎么运转、谁负责哪一段，场景与问题说客户自己的痛与门槛，方案说我们做什么、做到哪一步、接口在哪、不做什么，价值说采用之后变成什么样、好多少，下一步说谁在什么时候交付什么。
3. **不给决策建议**：不写"建议先做试点""推荐采用""值得投入""应当优先""不建议上"——产品只给事实、方案与边界，进不进由客户决定。
4. **不含内部信息**：不出现内部表号（表1-1…）；不出现来源标注（文件名、页码、URL、"来源：/出处："）；不出现证据等级、权威性、核实结论、信息完整度、待补齐、信息缺口；不出现 `ingest-*` 这类材料 id；不出现**竞品身份与竞争位势判断**；不出现内部论据与结论牢度自评；不出现**我方的财务测算与利润池**（成本、报价、利润推演、毛利目标）。
   - **定稿如此**：「门槛与合规」的经济行是**行业通例量级**的商务门槛，不是我方财务口径——写单间造价量级、集采门槛（注册资本/业绩/垫资）、保证金与质保比例、回款周期、分销与集成毛利区间（定稿第 49 行）。
5. **篇幅**：正文（表格不计）**约 3,000–3,500 字**，全文约 9,000 字；定稿实测正文 3,442 字 / 全文 9,179 字。逐章正文基准（定稿实测，表格不计）：现状 933 / 场景与问题 429 / 方案 1,203 / 价值 422 / 下一步 323 / 术语表 8。**篇幅按正文算**：表格是结构（分层、架构、职责、选型、价值、步骤、术语），本该有；流水账是正文把表格里的行又讲一遍。
6. **表格与正文分工**：表格承载结构，正文给判断与叙述。定稿 7 张表（体系 8 行 / 总体架构 6 行 / 主辅职责 7 行 / 选型 12 行 / 价值 6 行 / 步骤 11 行 / 术语 48 行）+ ①–⑤ 编号连接 + 判断性正文（现状章 4 段、问题章 2 段、方案章 5 段、价值边界 4 段、下一步 1 段）。
7. **规则铁律**：
   - 只用调研得到的信息，不改数字、不引入材料外信息；
   - 不给决策建议（见第 3 条）、不含内部信息（见第 4 条）；
   - 不写整段的自我说明与免责（"本材料只陈述…""以试点实测为准""除特别说明外"）；
   - **不出现「一、二、」式正文编号**（章标题除外）；分条用「第一/其一/价值一/①」。
8. **口径与量的处理**：具体数字优先（CT15、AI Box 6TOPS、200+ 工业协议、4096 字节、第 1–23 天）；**行业通例量级一律括注**——正文里写「（行业通例量级）」，服务水平写「（以上为行业常见服务水平，非本客户承诺）」；客户还没给的写「待客户提供」「待客户确认」，**一句话带过，不写成整段免责说明**，也不逐条挂"待补"。

## 三、章节骨架（五章 + 附录）

### 一、现状

| 小节 | 写什么 | 形式 |
|---|---|---|
| `### 场景在业务中的位置` | 2 段：①这空间承载什么（预约排会、签到、音视频呈现、远程会议、内容共享与批注、录播纪要、灯光空调环境控制、设备运维）、谁负责哪一段（预约归行政与 OA、音视频归 IT、灯光空调归物业、纪要归召集人，没人负全责）；②采购与预算怎么走（新建改造随工程配套招标、集成商实施、总部定标准分支复制、交付后转年度维保），三方口径（工程款出钱 / IT 与行政扛事 / 使用者评价）为什么对不上 | 正文 2 段 |
| `### 既有体系构成` | 一句过渡（各层各买各的、各管各的）+ **一张分层表**：`层次 \| 现有构成 \| 现状主要接口`，8 行——交互与显示 / 采集与感知 / 音视频处理与控制 / 环境与通行 / 网络与供电 / 平台与应用 / 物理空间与家具 / 交付与运维服务；接口写具体协议（HDMI/DP/USB-C、Miracast/AirPlay/Cast、USB UVC、RTSP/ONVIF、NDI、Dante/AES67、Zigbee/KNX/Modbus/MQTT、SIP/H.323、WebRTC、RS-232/485、Relay/GPIO、POE、CalDAV/iCal、SSO、SNMP/SDK） | 一句正文 + **一张表**（8 行） |
| `### 现状特征与提升空间` | 一段：先给结论（**三个特征决定天花板**），再逐条加粗说——交付是一次性、运行是长期的（验收后无人日常看管、外包报障、年度维保数小时至 24 小时响应、季度或半年巡检、跨品牌互相推诿）；设备在线状态基本不可见（多无统一网管、运维事后响应）；数据沉淀不下来（使用率/能耗/故障靠人工按季或按年汇总）。落到提升空间三处（统一协议接入、人进房—设备就绪—人离场—设备释放整链自动化、运行数据自动落到客户自己的系统），再写行业趋势同向（远程协同节点、设备管理云化、AI 纪要由选配转基础期望、信创适配下沉音视频、录音与转写数据留存合规趋严、无线投屏与自带设备普及、能耗与使用数据成为空间管理依据、方案按高中低端分层并行），末尾如实说明本客户哪些输入待补 | 正文 1 段 |

### 二、场景与问题

| 内容 | 写什么 | 形式 |
|---|---|---|
| 场景边界（**不设小节标题**） | 一句话：管会议空间本体及设备联动（预约、音视频、远程、录播、环境、运维），不介入 OA、门禁、会议云平台、集团空间规划，**只对接不替换** | 正文 1 句 |
| 七类问题（**不设小节标题**） | 一段：`七类：协议不通、状态不可见、合规存疑、结论不沉淀、存量标准不一、用不起来、空置与抢不到并存。`再分组（前三条归接入与可见性、中间两条归数据与内容、后两条归效率与投资保护），末句点根因（设备是信息孤岛，缺统一连接与动作层）；**一段写完，不再另起分层小标题** | 正文 1 段 |
| `### 门槛与合规` | 三行，每行一句话，行内换行、**不设分条编号**：**技术**——终端过平台认证；4K60 HDMI 约 12Gbps、铜缆 ≤15m；投屏需 Miracast/AirPlay/Google Cast 认证、4K30 ≥20Mbps；跨品牌靠中控或第三方纳管。**行业准入**——政采与央国企集采、涉密资质、等保、CCC、信创目录。**经济**——单间小型 2 万~8 万、中型 5 万~15 万、大型与董事 30 万~100 万以上；集成招标常见注册资本 ≥500 万、业绩 2~3 个、垫资 3~6 个月；毛利分销 10%~20%、集成 20%~35%；投标保证金 ≤估算价 2%、履约 ≤合同 10%、质保 ≤结算 3%；回款 6~12 个月（行业通例量级） | 正文 3 行 |

### 三、方案

| 小节 | 写什么 | 形式 |
|---|---|---|
| `### 设计原则` | 3 条，每条 `**原则N：<一句主张>。** <一句落地含义>`：①不改客户的软件，只做设备与控制层的统一（预约、OA、门禁人事、会议云平台是客户既有投资，不替换）；②控制逻辑放在边缘，网络断了会议照开（本地控制器执行并保存状态，断网掉电恢复后不失控）；③数据只透传、不留存，记录写回客户自己的系统（不汇聚业务数据，控制记录写入客户业务系统登记） | 正文 3 段 |
| `### 总体架构` | **一张表**：`层次 \| 我方组件 \| 承担什么`，6 行——端侧交互（在鸿平板 PD34、7885 平板、三防平板、CT34 工业触控屏）/ 网络接入（CT31 网关、CT32/CT33 在鸿物联网关）/ 边缘控制与算力（CT15、CT16 模块化 IO、AI Box 边缘算力、CT21B 工控机）/ 平台与服务（在鸿·近场通、原子化服务平台）/ 运维管理（边缘本地 web 运维平台、在鸿物联平台）/ 既有系统对接（网关协议转换 + API/事件流）；"承担什么"写这一层干什么，给具体型号 | **一张表**（6 行） |
| `### 主辅职责对照` | **一张表**：`环节 \| 我方角色 \| 我方做什么 \| 谁来做其余部分`，7 行——会议预约与空间资源管理 / 参会人识别与无感签到 / 会场环境设备控制 / 音视频会议 / 会议内容记录与智能纪要 / 近场交互与终端协同 / 设备运维与空间能效管理；角色用「**替代 / 辅助 / 外围配合**」，"我方做什么"必须落到具体产品与能力（CT15/CT16 的 DI/DO/AI/AO 与 200+ 协议、AI Box 6TOPS NPU、碰一碰拉起与软总线直连），"谁来做其余部分"写清合作方与需补齐项 | **一张表**（7 行） |
| `### 连接关系与接口` | ①–⑤ 编号段，每段：`① A → B：做什么，走什么协议，边界/前提是什么`——①端侧交互层→平台与服务层（碰一碰/近场触发拉起元服务卡片，走 NFC、BLE 与分布式软总线；触发源限 NFC/信标/位置，不含第三方认证载体）；②网络接入层→边缘控制与算力层（第三方设备经 CT31/CT32/CT33 接入，协议解析转统一物模型，覆盖 Modbus RTU/TCP、CAN、RS-485 等 200+ 工业协议，未收录私有协议需另行适配；接网口设备须与网关同网段）；③边缘层/平台层→云平台（网关经 MQTT 与在鸿物联平台通讯，需有效 MQTT 地址与端口）；④平台与服务层→客户业务系统（控制事件记录由外部系统登记写入，平台侧不留存业务数据，不改客户系统代码）；⑤运维管理层→边缘设备（局域网直连设备 IP，历史数据与日志查询导出、版本升级、VNC 远程桌面，云端经在鸿物联平台 OTA；单条日志上限 4096 字节、缓冲 50K/秒/进程、超限丢弃） | 正文，圆号编号（**5 条**） |
| `### 选型与配置` | **一张表**：`需求 \| 选型 \| 边界与前置条件`，12 行左右（多品牌设备接入与协议打通 / 环境设备联动 / 占用感知与自动释放 / 人脸扫码签到 / 语音转写与纪要 / 无纸化终端与电子桌牌 / 无线投屏与多屏互动 / 视频会议终端与编解码 / 会议大屏显示 / 预约排期与统一管理软件 / 与客户 OA·HR·IT 对接 / 数据本地化与安全）；"选型"给型号与厂商归属（**外采 / 第三方专业 AV 厂商 / 客户或第三方应用软件 / 需外部模块**必须写明），"边界与前置条件"写不支持什么、缺什么、什么时候必须改选（CT15 无 NPU、CT32 无硬件 NPU、CT34 为 7 英寸工业 HMI 非会议级大屏、PD34 计划 2026 年 6 月推出、端层认证限自研官方载体） | **一张表**（12 行） |
| `### 实施要点` | 2 段：①推进窗口——按 23 个工作日的窗口推进，逐条给天窗（现场勘测与方案设计第 1–3 天、端侧近场交互部署第 4–5 天、南向设备接入与协议适配第 6–9 天、边缘控制层安装与本地逻辑配置第 10–12 天、平台层元服务编排与托管下发第 10–14 天与边缘环节并行、客户业务系统事件记录对接第 15–18 天、云平台接入配置第 15–16 天、端到端联调与验收测试第 19–21 天、运维交付与人员培训第 22–23 天），并点出**订货前必须完成的两条前置确认**（AI 能力路径、CT16 无线选配）；②回退路径——协议不匹配则网关退为旁路状态监测、本地逻辑异常则切回原面板开关、托管下发失败改端侧本地部署、接口联调不通则事件记录暂存边缘日志人工导出、云不可达退回局域网本地运维、验收未过回滚上一可用版本重测，原则是**不让现场停摆** | 正文 2 段 |

| 四条边界（**不设小节标题，表后直接四段**） | **不替代**：客户的 OA、协同办公、会议室预约系统、门禁人事系统；视频会议云平台；专业 AV 厂商的视频会议终端、MCU 与音频处理产品；楼宇自控系统。**不参与**：客户既有业务系统内部的数据治理；客户的空间资产规划与预算决策。**不承担**：客户系统内部的接口鉴权与安全策略；强电回路的电气施工资质责任；非标私有协议的适配义务（未收录协议需另行定制）；第三方算法（人脸识别、ASR 转写、无线投屏协议模块）的授权与适配责任。**受限条件**：端层认证仅限自研官方载体、不开放第三方，会议室若已有他厂终端或中控需另行处理；CT15 无 NPU、不支持 AI 推理与 LLM，无智能体需人工编程；CT32 无硬件 NPU、仅 CPU 软推理；CT15 金属片与总线端子不支持热插拔、扩展模块拆装须断电、安装方向错误无法运行 | 正文 4 段，**加粗句首** |

**价值章禁忌**：不写「度量口径是…」「口径是…」这类说明书句；不逐条挂"待客户提供/未提供/无法核实"（价值章出现 ≥3 处即判**硬伤**）；不写章末基线免责句；不写"六条价值对应六个指标"这类自证开场。

### 五、下一步

## 四、行文规范

1. **说人话**：一句话说清一件事，不堆形容词，不用"赋能/抓手/闭环"这类空话；术语首次出现给一句限定（如"AI Box 边缘算力，6TOPS NPU，已交付"）。
2. **不写说明书腔与自证句**：不写「口径是…」「度量口径是…」「本节出现的数字…」「数据来源：…」；要交代的口径直接写在数字旁边（如「（行业通例量级）」）。
3. **一个事实只说一次**：同一件事不在各章反复铺垫；能在表里说的不写第二遍正文。
4. **先结论后依据**：小节与条目开头一句就是判断，后面才是支撑；单段 2–5 句。
5. **加粗只用于条目首句**（原则、价值、边界、特征），不用来强调句中词。
6. **表格**：表头用中文短名（层次/现有构成/现状主要接口、需求/选型/边界与前置条件这类）；单元格写结论与关键参数，不写整句话；缺数据写 `—`。
7. **标点**：中文全角；区间用 `~` 或 `–`（如 2 万~8 万、第 1–23 天、4K30）；编号在正文用「第一/其一」，分条价值用「价值一」，连接关系用 ①②③；引号用「」或 `""`。
8. **术语与型号与定稿完全一致**：在鸿、在鸿·近场通、元服务、碰一碰、物模型、分布式软总线、CT15/CT16/CT21B/CT31/CT32/CT33/CT34/PD34/AI Box。定稿里的写法照抄（如"AI Box 边缘算力，6TOPS NPU，已交付""在鸿 claw 智能体"）。
9. **行业口径与客户事实必须分开**：行业通例加括注；本客户未提供的一律不编具体数字，写「待客户提供 / 待客户确认」并说明缺什么。

## 五、校验与生成流程

**基准**：定稿本身过对外口径的确定性校验——`ok=true`、**零硬伤零提示**（正文 3,442 字）。模型产出的稿子达不到这条就不算合格。

**硬伤（必须重写一次，仍不过则保留正文并提示）**

- **缺章**：五章必须齐——现状 / 场景与问题 / 方案 / 价值 / 下一步（`## 附录、术语表` 单独判「缺术语表」）；
- **缺少方案构件**：自建表格（≥3 张）、设计原则、①②③ 编号连接关系、**对外价值表**（表头含 价值/现在/采用后/怎么核、数据行 ≥3）、边界声明（不替代/不参与/不承担/受限条件）；
- **对外泄漏内部信息**：内部表号 `表X-X`；`来源：/出处：/摘自：/参见：/依据材料：`；`证据级/权威性/核实结论/信息完整度/待补齐/信息缺口/证据缺口`；`ingest-*`；
- **出现决策建议**：`建议先/优先/应当/应该/采用/选择/通过/投入/采购/放弃/推进`、`推荐采用`、`值得投入`、`不建议`、`我方（我们/本报告）认为应该…`；
- **价值写成缺口清单**：价值章出现 ≥3 处 `待补/未提供/待补充/无法核实/需客户提供/尚需`。

**软提示（不阻断，但影响打分）**

- 缺小节（按本文件第三节的小节名核对，认小节名也认同义关键词：场景在业务中的位置 / 既有体系构成 / 门槛与合规 / 设计原则 / 总体架构 / 主辅职责对照 / 连接关系与接口 / 选型与配置 / 实施要点 / 步骤与交付物。「场景边界」「典型问题」「核心价值」在定稿里是**章下直接写、不套小节标题**，校验不要求它们单独成节）；
- 缺术语表；正文用了章号式编号（`**一、`…）；说明书腔（价值章 ≥2 处「度量口径是/口径是/本条信息/数据来源：」）；说明性套话（"不含决策建议""以试点实测为准""按材料口径的测算""除特别说明外""本节出现的数字""本材料只陈述"）；篇幅超标或不足。

**篇幅口径（变更表 #129 已按定稿校准）**

| 口径 | 值 | 说明 |
|---|---|---|
| 校验上下限（`report-gate.ts`） | 正文 1,200–4,500 字 | 定稿 3,442 字，通过 |
| 提示词建议（`report-prompts.ts`） | 正文 **3,000–3,600 字** | 对齐定稿实测 3,442 字（原来写 1,800–3,000，会把定稿压掉） |
| 逐章回炉触发线（`PROSE_BUDGET.external`） | 现状 **1,050** / 场景与问题 **500** / 方案 **1,350** / 价值 **500** / 下一步 **400** / 术语表 200 | 定稿实测 933 / 429 / 1,203 / 422 / 323，回炉线必须高于定稿，否则一生成就被压改 |
| 篇幅基准（定稿） | 见 §二.5 | 逐章预算是**回炉线**，不是篇幅目标 |

**压缩守恒（只删不加）**：某章正文超预算时，让模型**压一次**，规则是——不许引入素材外信息、不许改数字与判定；删的是同一事实的重复、铺垫与过渡句、对表格的复述、形容词与套话、自我说明与免责声明；留的是结论、判断、代价、边界、度量口径与表格本身；表格原样保留，`##` 章名与 `###` 小节标题一个都不能少、不许改名或合并；方案构件（设计原则/能力边界/度量口径/价值）必须留；分条不许改成「一、二、」；不许留半句话。三种情形**作废这次压缩、保留原正文**（宁可偏长，不能缺构件）：压缩后缺的构件比压缩前多（构件变少）；原本有 `###` 小节、压完一个小节都不剩（结构塌陷）；出现残句（短段落不以句末标点收尾）。

**生成流程**（`apps/server/src/deliverable-report.ts`）

1. 按章取素材（事实层）→ 按章撰写（判断层），每块素材最多 12 行，归纳责任在模型；
2. 确定性校验 → 有硬伤带违规清单**重写一次**（重写只带硬伤，提示性项不塞回去）；
3. 缺章**单独补写一次**（只写缺的那几章）；
4. 逐章篇幅回炉（超预算压一次，含上面的守恒守卫）；
5. 装配：封面（`# <场景名称> 解决方案` + 场景行 + 日期行）→ 五章（`---` 分隔）→ `## 附录、术语表`（模型没写就不出现这一节，不造假）；某章完全没写出来时用要点版兜底。

## 六、可直接复用的提示词骨架

```text
你是给客户做汇报的方案撰写人，不是材料的整理者。读者是客户的业务与 IT 负责人，他们没看过我们的调研表。
全篇只有一个主角——我们的方案：现状说这个空间今天怎么运转、卡在哪；场景与问题说客户的痛与门槛；
方案说我们做什么、做到哪一步、接口在哪、不做什么；价值说采用之后变成什么样、怎么核；
下一步说谁在什么时候交付什么。章章都要落到客户身上，不许罗列素材、不许摘要腔。
只说行业通例与客户能验证的事实：行业量级一律括注「行业通例量级」，服务水平括注「以上为行业常见服务水平，非本客户承诺」；
客户还没给的写「待客户提供 / 待客户确认」，一句话带过，不写成整段免责说明，也不逐条挂"待补"。

决策建议（建议/推荐/值得投入/应当优先/不建议）。

方案 / 价值 / 下一步），章间 `---`，小节用 `### …`；最后 `## 附录、术语表`（术语 | 说明两列）。
```

## 七、与内部调研报告输出要求的差异

| 项 | 对外汇报材料 | 内部调研报告 |
