# 场景会话体系技术方案

> 状态：方案梳理，待评审后进入技术验证  
> 日期：2026-10-23  
> 范围：当前本地单用户桌面产品；数据模型预留团队/权限扩展，但不在本期实现  
> 结论：**不把“聊天”做成第四个孤立页面，而是把会话做成围绕业务对象的可追溯工作线程；会话内核复用 DeepSeek Harness，产品侧只做领域上下文、提案与工作台。**

---

## 1. 现状与问题

当前产品的会话只服务于「场景定义」：

- `conversation` / `message` 两张表存会话与消息；
- 每次发消息新建一个 DSH session，把最近 12 条 / 6000 字符历史手工拼进 prompt；
- 左侧栏只显示「场景定义」会话，阶段分析会话不再登记；
- 通用会话 CRUD 接口仍在，但前端没有新建普通会话的入口；
- 会话内容与业务产出（表 1-1、阶段表、交付物章节、来源）没有稳定关联。

代码依据：

- [会话数据表](packages/infra/src/sql/001_init.sql:256)
- [会话编排](apps/server/src/converse.ts:154)
- [会话路由](apps/server/src/routes-ui.ts:1270)
- [场景定义会话](apps/server/src/scenario-definition.ts:621)
- [左栏会话列表](apps/web/src/components/ProjectList.tsx:160)

这能支撑“把场景聊清楚”，但支撑不了用户接下来会提出的三类需求：

1. **追问依据**：这条结论为什么成立？来源在哪？能不能打开原文？
2. **继续检索**：这个判断还缺证据，再查一轮；查不到要如实说明。
3. **优化产出**：这段方案怎么改？改完和原表/原图/原来源是否一致？

因此需要把会话从“场景定义的一个弹窗”升级为**围绕产品功能的会话体系**，但不能再造一套通用 ChatGPT 页面。

## 2. 目标与非目标

### 2.1 目标

- 用户可以在任意业务对象上发起追问，不丢失上下文；
- 每个回答都能追溯到项目、步骤、表/行/章节、产出物版本和来源；
- 长任务（检索、审阅、优化）在切页、刷新、回项目后仍能接回；
- 模型只给建议和提案，写操作由产品确定性地执行并留痕；
- 会话可管理：自动标题、搜索、置顶、归档、分支、删除、收件箱；
- 复用成熟开源代码，不自行实现会话日志、压缩、检索、重试、工具循环。

### 2.2 非目标

- 本期不做多租户、组织权限、云端同步；
- 不把产品做成通用聊天客户端；
- 不允许模型直接改数据库或直接执行导出；
- 不追求“无限上下文”，而是用压缩 + 按需检索 + 明确省略。

## 3. 产品形态：围绕对象的会话

### 3.1 会话不是按“阶段”堆，而是按“对象 + 目的”挂

建议统一叫“线程（Thread）”，底层仍可复用 `conversation` 表。线程有两个维度：

- **作用域（scope）**：这个线程围绕什么对象；
- **目的（purpose）**：用户想干什么。

| 作用域 | 典型入口 | 线程目的 | 说明 |
|---|---|---|---|
| 项目 | 项目助手、全局提问 | assistant / review | 每个项目一个常驻项目助手，跨步骤 |
| 场景定义 | 新建项目、第 1 步 | definition | 现有「场景定义」迁移为普通线程的一种 |
| 流程步骤 | 步骤页头「问这一步」 | assistant / verify | 只带当前步骤的表、总结、来源 |
| 表格 | 表头「问这张表」 | verify / optimize | 适合整表一致性检查 |
| 表格行/单元格 | 行尾「问这一行」 | verify | 高频入口：为什么这么判、依据在哪 |
| 交付物 | 交付物页「审阅全文」 | review | 检查结构、事实、来源、前后矛盾 |
| 交付物章节 | 章节「优化这一段」 | optimize | 返回 diff 提案，不直接覆盖 |
| 来源/结论 | 右栏来源「继续检索」 | research | 生成后台检索任务，补齐证据 |
| 待验证结论 | 自检项「查一下」 | verify | 与 G-R0/G-R8 打通 |

**产品原则：一个对象默认只有一条活跃线程。** 用户要另起话题时显式「新建线程」或「从这里分支」；避免每点一次就多一个会话。

### 3.2 双尺度交互

- **快速追问**：右侧面板/抽屉，当前对象上下文自动带入；适合“为什么”“依据呢”“这句话什么意思”。
- **深度工作**：打开独立的会话工作台（类似当前「场景定义」独立弹窗），左侧对话、右侧产出物/来源/差异；适合审阅、优化、长检索。
- **不要**再增加一个永久第四栏；沿用现有三栏，把会话放到右侧“阶段总结 / 会话”Tab，深度工作再进独立页面。

### 3.3 会话类型不要过多

不建议做“问答会话、研究会话、优化会话、审阅会话、定义会话”五套 UI。只保留三种呈现：

1. **对话线程**：普通问答、追问、解释；
2. **任务线程**：检索、审阅、批量优化，有进度、可后台、有结果；
3. **分支线程**：从某条回答 fork 出来做 what-if，默认不写回产出物。

三者共用同一套消息流、引用、上下文和权限，只是任务线程多一个运行状态与结果卡。

### 3.4 典型用户路径

```text
用户在看「表3-2 客户角色」
  → 点行尾「问这一行」
  → 右侧打开线程，顶部上下文条：项目 / 第3步 / 表3-2 / 行「付费者」/ 产出物版本 v7
  → 问「为什么付费者不是设备部？」
  → 回答给出：表3-2 该行 + 表3-3 角色判定 + 来源链接
  → 用户点「继续检索」
  → 线程转为后台任务，左栏收件箱显示「运行中」
  → 用户切到别的步骤，任务继续
  → 完成后收件箱提示，打开看新增来源；用户选择「写入依据」或「忽略」
```

## 4. 会话管理功能

### 4.1 列表与组织

- 左栏项目下只展示：**项目助手（置顶）** + **最近 3 条线程** + 「查看全部」；
- 全部线程进入项目级列表，支持按作用域、状态、目的过滤；
- 全局「收件箱」：等待用户确认的提案、等待回答的问题、运行中的任务、失败任务；
- 全局搜索：标题 + 消息正文 + 来源/产出物引用，使用 FTS，不要求用户记得在哪个项目问过。

### 4.2 生命周期

```text
首次发消息 ──> 活跃
                 ├─ 运行中 ──> waiting_user（需要确认/补充）
                 │             ├─ completed
                 │             └─ failed（可重试）
                 ├─ 用户归档 ──> 已归档
                 └─ 删除（二次确认，软删除后清理）
```

- 线程在**第一次发送时**创建，不在打开面板时创建，避免空会话；
- 自动标题：首条用户消息生成（DSH 确定性回退；需要模型摘要标题时在专用 profile 打开），用户可重命名；
- 置顶：项目助手默认置顶；用户可置顶任意线程；
- 归档：建议默认 30 天无活动自动归档，置顶除外；归档不是删除；
- 删除：软删除 + 保留期，项目删除时级联；
- 分支：从任意助手消息 fork，继承当时的上下文快照与产出物版本；
- 导出：Markdown/JSON，含上下文、引用、提案与决策记录。

### 4.3 上下文可见、可核对

每个线程顶部固定显示“上下文条”：

```text
项目：管网阀室   |   第 3 步：理解商业   |   表3-2 客户角色 · 行「付费者」
产出物版本：v7（2026-10-23 06:40）   |   来源：3 条   |   模型：...
```

- 用户可以增删上下文对象，但增删会记录到线程；
- 回答里每个关键结论带引用角标，点击定位到右栏来源/表格行；
- 上下文版本变化时，线程显示「基于旧版本」提示；旧版本提案禁止直接应用，需刷新或重新生成；
- 不允许“模型说看过全文”但实际没带上下文：UI 显示实际使用的上下文清单。

### 4.4 待处理与通知

- 任务完成、提案待确认、模型追问时进入收件箱；
- 桌面通知只在长任务完成/失败时触发，不打扰普通回答；
- 切页/刷新后通过线程 id + 事件序号接回，不依赖组件是否还挂载；
- 这与刚修复的交付物生成问题同一条原则：**长任务归服务端，UI 只是观察者**。

### 4.5 迁移现有「场景定义」

- 保留现有会话与消息，新增一条 `scope_type=definition` 的索引；
- 新线程体系上线后，定义对话作为项目助手的一个特殊线程继续可用；
- 不强制一次性迁移全部历史；旧消息只读展示，新消息走新内核；
- 用户可见的名称不变，避免“功能消失”的感知。

## 5. 数据模型

### 5.1 原则

- **DSH 会话日志是对话内容的唯一真相**；
- 业务 SQLite 只存线程索引、业务产出、提案、审计；
- 不在两处各存一份可编辑的消息正文；
- 所有上下文与提案带版本，支持追溯和并发冲突检测。

### 5.2 表设计建议

```sql
-- 在现有 conversation 上扩展，不新建第二套会话表
conversation (
  id                 TEXT PRIMARY KEY,
  scenario_id        TEXT NOT NULL,
  title              TEXT NOT NULL,
  status             TEXT NOT NULL,          -- 活跃 / 已归档（沿用现有值）
  kind               TEXT NOT NULL,          -- 兼容旧数据：用户 / 阶段分析 / 定义
  scope_type         TEXT NOT NULL,          -- legacy/project/definition/step/table/row/deliverable/section/claim
  scope_id           TEXT NOT NULL,
  purpose            TEXT NOT NULL,          -- legacy/assistant/verify/research/optimize/review/regenerate
  parent_id          TEXT,                   -- fork 来源
  pinned             INTEGER NOT NULL DEFAULT 0,
  dsh_session_id     TEXT NOT NULL,
  context_json       TEXT NOT NULL,          -- 引用清单，不存正文
  context_hash       TEXT NOT NULL,          -- 产出物版本/上下文指纹
  summary            TEXT,                   -- 压缩摘要
  last_activity_at   TEXT NOT NULL,
  owner              TEXT,                   -- 本期固定 local，预留团队
  created_at         TEXT NOT NULL,
  updated_at         TEXT NOT NULL
);

CREATE UNIQUE INDEX ux_conv_active_scope
  ON conversation(scenario_id, scope_type, scope_id, purpose)
  WHERE status = 'active' AND parent_id IS NULL;

conversation_artifact (
  conversation_id    TEXT NOT NULL,
  artifact_type      TEXT NOT NULL,          -- table/row/deliverable_section/source/claim
  artifact_id        TEXT NOT NULL,
  artifact_version   TEXT NOT NULL,
  relation           TEXT NOT NULL,          -- context/target/evidence
  PRIMARY KEY (conversation_id, artifact_type, artifact_id, artifact_version, relation)
);

proposal (
  id                 TEXT PRIMARY KEY,
  conversation_id    TEXT NOT NULL,
  message_seq        INTEGER NOT NULL,       -- DSH 会话事件序号
  target_type        TEXT NOT NULL,
  target_id          TEXT NOT NULL,
  base_version       TEXT NOT NULL,
  patch_json         TEXT NOT NULL,
  evidence_json      TEXT NOT NULL,
  status             TEXT NOT NULL,          -- proposed/accepted/rejected/superseded
  applied_at         TEXT,
  created_at         TEXT NOT NULL
);

thread_run (
  id                 TEXT PRIMARY KEY,
  conversation_id    TEXT NOT NULL,
  kind               TEXT NOT NULL,          -- research/review/optimize/rerun
  status             TEXT NOT NULL,          -- queued/running/waiting/completed/failed/cancelled
  progress_json      TEXT,
  error              TEXT,
  started_at         TEXT,
  ended_at           TEXT
);
```

说明：

- `message` 表逐步退化为兼容投影，不再作为新会话的写入真相；
- DSH 的事件序号用于把提案/引用锚定到具体回答；
- `context_hash` 不等于内容哈希；它标识“当时使用的产出物版本集合”；
- 提案的 `base_version` 与当前版本不一致时禁止应用，避免覆盖用户刚改的内容。

### 5.3 状态与并发

- 同一对象同一目的默认一条活跃线程；需要多版本讨论时 fork，不复制线程；
- 线程运行状态与 `status` 分离：归档的线程也可以有历史任务，但不再接受新消息；
- 产出物更新后，引用它的线程标记 `context_stale`；
- 应用提案使用事务 + 版本检查 + 下游失效标记，失败则不改任何东西。

### 5.4 迁移策略

不做“一次性把所有旧消息导入 DSH”的大迁移。旧数据是资产，不是新内核的启动负担：

1. 给 `conversation` 补 `scope_type/scope_id/purpose/context_json/context_hash` 等列，旧行回填为 `legacy`；
2. 旧「场景定义」会话继续走现有读取路径，冻结为只读历史；新入口创建 DSH 线程；
3. 新旧会话通过同一个 `SessionPort` 暴露给 UI，前端不区分底层；
4. 新会话只写 DSH 日志，不再写 `message`；旧 `message` 表仅服务旧会话读取与导出；
5. 经过至少一个版本验证后，再决定是否把旧会话做“摘要 + 关键消息”迁移；不追求逐条重放。

这样风险最小：旧功能不消失，新能力不被历史数据阻塞。

## 6. 运行时架构

### 6.1 推荐形态

```text
React UI
  ├─ 产出物视图（表格/交付物/来源）
  ├─ 右侧会话面板（快速追问）
  └─ 会话工作台（深度审阅/优化/任务）
          │ HTTP + SSE/WebSocket
Fastify 应用服务
  ├─ 线程索引 / 上下文构建 / 提案与版本 / 审计
  ├─ 领域工具网关（只读查询、检索、写提案）
  └─ SessionPort 适配器
          │ stdio JSON-RPC（首选）
DeepSeek Harness 运行时（独立 sidecar，固定版本）
  ├─ 会话事件日志 + JSONL 持久化 + 压缩
  ├─ Agent loop + 工具注册 + 模型适配
  └─ 会话搜索 / 标题 / 恢复 / 分支
```

### 6.2 为什么用 DSH，而不是继续自己拼历史

当前实现的问题不是“模型不够聪明”，而是会话基础设施太薄：

- 手写 12 条 / 6000 字符截断，没有压缩；
- 每条消息新建 DSH session，`dsh_session_id` 只保留最后一次；
- SSE 事件缓冲在进程内，重启后无法续传；
- 没有分支、搜索、标题、token 计量、工具循环。

DeepSeek Harness 已经提供了这些能力：

- 追加式、事件溯源的 Session 日志，消息历史由日志派生；
- JSONL 持久化、恢复、fork、压缩（compaction）；
- Session Query SQLite FTS5 全文检索；
- 标题（确定性回退 + 可选模型标题）、token 计量、子 agent；
- Agent loop、工具调用、取消、重试与超时。

因此建议**不要继续扩展当前 `converse.ts` 的历史拼接逻辑**，而是把会话内核切到 DSH；产品侧保留业务编排。

### 6.3 集成方式

首选 **DSH SDK sidecar**：

- 通过 `@deepseek-ai/dsh-sdk-client` 启动受控的 DSH runtime；
- 使用专用 profile，不加载 shell、任意文件写入等无关工具；
- 每个产品线程映射一个 DSH session；
- 应用服务消费 `session.event` / `session.status`，投影成 UI 消息、工具卡、提案；
- 模型配置复用产品现有供应商登记，通过 DSH 的 `pi-ai` OpenAI-compatible 路由接入，避免两套设置；
- 领域工具不直接读业务库，统一调用应用服务的本地鉴权工具网关，保证数据属主与可审计。

备选 **DSH 内嵌**：如果 sidecar 的打包体积/IPC 不可接受，再把同一套 `SessionPort` 适配器换成进程内 DSH；领域层和 UI 不改。

**SDK 暴露面与内核能力的差距**：

| 能力 | DSH 内核 | SDK 协议 | 本方案处理 |
|---|---|---|---|
| 创建会话 / 发消息 / 事件流 | 有 | 有 | 直接用 SDK |
| 取消生成 | `Agent.cancel` | 无 | 薄扩展 `session/cancel`；或切 Web Remote |
| 列出/搜索会话 | Session Query | 无 | 产品索引 + FTS；或薄扩展 |
| 重命名/归档/置顶 | 内核/产品概念 | 无 | 产品索引实现 |
| 真正 fork | Session fork | 无 | 先做产品级“分支”（新会话 + 上下文摘要）；后续薄扩展 |
| 审批请求 | 有（Web/Remote） | 无 | 写操作由产品提案层处理，不依赖 SDK 审批 |

因此建议定义一个 `SessionPort` 适配接口：

```ts
interface SessionPort {
  create(scope, context): Promise<SessionRef>
  prompt(sessionId, parts): AsyncIterable<ThreadEvent>
  follow(sessionId, afterSeq): AsyncIterable<ThreadEvent>
  cancel(sessionId): Promise<void>
  close(sessionId): Promise<void>
  fork(sessionId, seq): Promise<SessionRef>
  history(sessionId, cursor): Promise<MessagePage>
}
```

一期先实现 SDK 适配器；cancel/fork 缺失时，要么在 DSH SDK server 上补很薄的方法（底层能力已存在），要么切换到 DSH Web Remote（自带 cancel/fork/search），**不自己重写 agent loop**。接口不变，产品层无需重写。

### 6.4 专用 DSH profile

只挂载产品需要的部分：

- 模型适配（OpenAI-compatible / DeepSeek）；
- 会话、持久化、压缩、标题、FTS；
- 产品领域工具插件；
- 不挂 shell、任意文件写入、桌面控制、无关 MCP 服务；
- 工具白名单 + 本地鉴权 + 超时/并发上限；
- 按 `purpose` 选择模型档位：解释/追问用低成本模型，审阅/研究/优化用高能力模型，避免所有线程都烧高配。

### 6.5 领域插件

建议做一个 `scene-product` DSH 插件，负责：

- 每轮注入产品上下文清单（项目/步骤/对象/版本/权限）；
- 注册只读工具：项目上下文、表/行读取、来源追溯、材料检索、联网检索；
- 注册提案工具：`propose_patch`（只产生提案，不直接写库）；
- 统一输出引用、证据等级、无法核实的显式标记；
- 把产品的 G-R0/G-R8 规则以工具/校验器方式接入，而不是只写在提示词里。

## 7. 上下文与工具设计

### 7.1 分层上下文

不要每轮把整个项目塞进 prompt。按层组装：

| 层 | 内容 | 进入方式 |
|---|---|---|
| L0 | 产品角色、规则、输出格式 | system，稳定 |
| L1 | 线程作用域、产出物版本、用户意图 | developer/user，短 |
| L2 | 目标表/行/章节 + 直接依赖 | 结构化上下文 |
| L3 | 相关来源、证据摘要 | 按需工具检索 |
| L4 | 对话摘要 + 最近若干轮 | DSH compaction |
| L5 | 全库/联网检索结果 | 工具按需返回，不预灌 |

原则：**能通过工具拿到的，不提前塞进 prompt；能引用 ID 的，不复制全文。**

### 7.2 工具清单

| 工具 | 类型 | 用途 |
|---|---|---|
| `get_project_context` | 只读 | 项目定义、当前步骤、流程状态 |
| `get_table_rows` | 只读 | 指定表/行，带版本 |
| `get_deliverable_section` | 只读 | 交付物章节与相邻章节 |
| `trace_sources` | 只读 | 从结论/行反查来源与证据等级 |
| `search_materials` | 只读 | 本地材料全文检索 |
| `web_search` / `fetch_url` | 只读 | 外部检索，沿用多引擎兜底 |
| `propose_patch` | 写提案 | 生成 diff，不直接应用 |
| `request_rerun` | 写提案 | 请求重跑阶段/章节，需确认 |
| `export_artifact` | 写提案 | 导出，需确认 |

禁止：任意 SQL、shell、文件系统写、直接修改业务表、绕过来源门禁。

### 7.3 写操作：提案而不是命令

```text
用户：把这段结论改得更保守，并补上来源
  → 模型读取目标章节 + 约束 + 来源
  → 返回 proposal：target、base_version、diff、理由、引用
  → 应用服务校验：目标存在、版本一致、来源可定位、格式合法
  → UI 展示 diff（接受 / 拒绝 / 让我改）
  → 接受：事务应用 → 标记下游待重算 → 记录审计
```

模型永远不能直接把“建议”变成“已写入”。这既符合当前“模型建议、用户决定”的产品原则，也避免长对话中的误改。

### 8.1 复用边界

**直接复用，不重写：**

- 会话事件日志、持久化、恢复（内核能力）；
- 上下文压缩、token 计量；
- agent loop、工具调用、模型适配、重试/超时；
- 会话全文检索、自动标题（内核能力；SDK 未暴露的部分用薄扩展或产品投影）；
- SSE/事件流与断线恢复（按 DSH 的 Session 事件模型接）。

原则：**消息历史、压缩、工具循环、模型重试绝不由产品重写**；只补 DSH 暴露面上的薄适配。

**必须产品侧实现：**

- 线程作用域与对象绑定；
- 上下文清单、版本与 stale 检测；
- 领域工具与来源追溯；
- 提案/diff/应用/回滚/审计；
- 会话工作台、收件箱、内联入口；
- 产品规则与权限。

### 8.2 创新点

复用成熟内核不等于产品没有创新。本方案的创新在**领域集成层**，不在会话存储本身：

1. **对象级线程**：会话不是按阶段堆，而是绑定表/行/章节/来源，带作用域与目的；
2. **版本化上下文**：每条线程记录产出物版本与上下文指纹，产出物变了会提示“基于旧版本”并阻止旧提案；
3. **提案式写回**：模型只能产出 diff 提案，应用层做版本检查、来源校验、下游失效和审计；
4. **证据闭环**：回答中的引用必须能定位到来源/表格行，查不到就明确“不确定”，不允许伪引用；
5. **后台任务线程**：检索/审阅/优化是服务端任务，切页/刷新/重启后可接回，而不是绑在组件生命周期上；
6. **收件箱而非会话列表**：管理的是待确认提案、待回答问题、运行中任务，减少会话爆炸。

这与通用聊天产品的差异是：通用产品管理“对话”，本产品管理“围绕产出物的决策过程”。

### 8.3 不选通用聊天底座的原因

通用聊天产品解决的是“人和模型对话”，本产品解决的是“人围绕一份会变化的分析产出做决策”。差异在：

- 上下文不是聊天记录，而是表/行/章节/来源的版本化引用；
- 输出不是一段回答，而是可核对的结论、证据和可应用的 diff；
- 管理对象不是“会话列表”，而是“项目下的待处理事项”；
- 失败模式不是“答得不好”，而是“改错产出物/伪造来源”。

因此复用**内核**，不复用**产品壳**。

## 9. 分阶段落地

### P0：技术验证（先做 spike，不接业务写操作）

- 启动 DSH SDK sidecar，验证 create / prompt / resume / event / compaction / session search；
- 验证 macOS + Windows 打包、进程生命周期、崩溃恢复；
- 验证自定义 profile 与领域工具插件；
- 验证 cancel 缺口：补 `session/cancel` 或评估 Web Remote；
- 产出 go/no-go 与包体积/启动耗时数据。

**通过标准**：同一线程重启应用后可恢复；切页/刷新可接回事件；工具调用有引用；不加载 shell/任意文件工具。

### P1：只读会话骨架

- 项目助手 + 步骤/行/章节「问一问」；
- 上下文条、引用跳转、来源追溯；
- 线程列表、搜索、自动标题、重命名、置顶、归档；
- 后台任务状态、收件箱、切页恢复；
- 迁移「场景定义」到同一索引。

**通过标准**：用户能从任意行发起追问，回答带可定位引用；刷新后线程不丢；找不到来源时明确说“不确定”，不编造。

### P2：产出优化与审阅

- 章节/表格 diff 提案；
- 交付物审阅线程（结构、事实、来源、前后矛盾）；
- 接受/拒绝/回滚、版本检查、下游失效；
- 审计记录与导出。

**通过标准**：提案不能越过版本检查；接受后产出物可追溯；拒绝不产生副作用。

### P3：检索任务与后台工作

- 「继续检索」任务线程；
- 多引擎检索、材料检索、来源分级；
- 任务进度、取消、失败重试、收件箱；
- 长对话压缩与成本/耗时展示。

**通过标准**：切页/刷新/回项目后任务继续；检索失败有明确记录；新增来源可被审阅后写入。

### P4：规模化

- 跨项目搜索、团队只读/评论/编辑；
- 线程模板（审阅清单、优化指令）；
- 成本与质量看板；
- 可选云端同步。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| DSH developer preview 破坏性变更 | 升级即坏 | 固定 commit/版本；`SessionPort` 适配层；契约测试；升级走独立分支 |
| sidecar 包体积/启动耗时 | 桌面体验变差 | P0 量测；必要时内嵌 DSH 或只复用 session 包 |
| SDK 无 cancel/审批 | 长任务不可停 | 薄扩展 cancel；或切 Web Remote；产品侧超时兜底 |
| 会话爆炸 | 左栏不可用 | 对象默认单活跃线程；收件箱；自动归档；搜索优先 |
| 上下文漂移 | 回答基于旧版本 | context_hash + 版本检查 + stale 横幅 + 提案阻止 |
| 模型伪造来源 | 产品信任受损 | 工具返回结构化来源；确定性校验；无来源显式失败 |
| 模型直接改产出 | 数据损坏 | 只允许 proposal；应用层事务、版本、权限、审计 |
| 本地数据丢失 | 用户资产损失 | SQLite + DSH home 一起备份；启动自检；导出/恢复 |
