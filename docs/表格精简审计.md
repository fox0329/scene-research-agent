## 三、第一层：表级审计

### 3.1 最要紧的发现——21 张表是「只写不读」

`collectUpstreamData()` 只往后续阶段塞两类东西：

```ts
if (stage >= 3) { M1_产品型号, M2_规格参数, M3_能力清单, M4_边界声明, M5_已知限制, O_可选材料 }
if (stage >= 2) { 阶段1_门槛筛查  ← 阶段1 的全部行 }
```

阶段小结（`stage_summary`）也不进提示词（只在 `routes-ui.ts` 给界面读）。

| 阶段 | 表 | 后续阶段能否读到 |
|---|---|---|
| 0 | M1–M5、可选材料 | ✅ 阶段≥3 作为库上下文读入 |
| 1 | 表1-1、1-3、2-2、2-3、2-4、2-5 | ✅ 阶段≥2 整包读入 |
| **2** | **表3-1…表3-9（9 张）** | ❌ **从不读入** |
| **3** | **表1-2、表2-7、表4-1…表4-5（7 张）** | ❌ **从不读入** |
| **4** | **表5-1、表5-3、表5-4（3 张）** | ❌ **从不读入** |
| **5** | **表6-1、表6-4（2 张）** | ❌ **从不读入** |

**这直接推翻了几处设计承诺**：

- 表4-3 写「缺口（来自表3-8）」「覆盖表3-8 每条」——但生成表4-3 时**读不到表3-8**，只能靠模型重新猜一遍；
- 表4-5 写「我方与对手的对照在阶段3 表4-5」、表3-4 写「不写我方」——两边互指，但阶段3 读不到表3-4；
- 表3-7 写「我们方案里怎么避」，可它自己在下游看不见，「怎么避」不会影响任何后续产出。

**所以 21 张表的现状价值只剩两处**：给人看（界面）、进交付物（而交付物只显式用表1-1/表6-1）。

> 判断：**这不是「删表」能解决的，也不是「加表」能解决的。修的是接线。**

### 3.2 逐表判定

判定口径：
- **保留**：产出影响后续决策或交付物，且不可被其它表替代
- **接线**：内容有价值，但目前下游读不到（修 §3.1）
- **合并**：与另一张表说同一件事
- **降级**：不必是独立表，收成某表的列/行级元数据
- **删除**：既不进下游、也不进交付物、且人工也不看

| M1 产品清单 | 13 | 保留 | 库上下文，下游读；`资料同步` 列 0% 填充且代码零引用 → 删该列 |

## 四、第二层：列级审计

### 4.1 溯源元数据占了 40%，而且存了两处

| 列 | 出现表数 |
|---|---|
| `核实结论` | 32 |
| `核实说明（准确·客观·为什么）` | 32 |
| `来源` / `出处` | 31 |
| `证据等级` / `来源权威性` | 14 |
| 合计 | **122 / 303 列（40%）** |

同时 `stage_data` 表**已经有** `source` / `source_authority` / `evidence_level` / `source_type` 四个顶层列。同一事实存两处，结果两处都不全：例如 `证据等级` 在 表1-3/2-5/3-1/3-4/3-8/1-2/4-2/6-1 里 **0% 填充**，因为写到了顶层列或根本没写。

**建议**：这 122 列收成「行级元数据一处存」，表定义里只保留 `source`（人看得懂的唯一必需项），其余由质检流程统一写顶层列。**预计列数 303 → 约 190**。

**顺带一个真实成本**：`核实说明` 真实数据共 **523 行、71,156 字**，均长 136 字/行，最长 237 字（表6-1）。它是生成与复核的中间产物，不该作为每张表的一列反复生成。

### 4.2 14 列「必填却从没填过」

真实数据里实质填充 = 0（有行、有数据，但这一列一次都没真填）：

| 表 | 列 | 必填 | 判断 |
|---|---|---|---|
| 表4-4 | 综合排序 | 是 | **结论列没填 → 这张表的产出实际不存在**，必须修或删表 |
| 表3-8 | 排序 / 痛到什么程度 | 是 | 同上：痛点排序是这个表的全部意义 |
| 表4-5 | 评分(1-5) | 是（17% 填充） | 评分体系没落地，赢面结论无支撑 |
| M5 | 影响程度 | 是 | 已知限制不说影响程度，等于只说「有坑」 |
| M5 | 日期 | 否 | 删（限制的发生/发现时间无决策用途） |
| M1 | 资料同步 / 曾用名 | 否 | 删（0% 且代码零引用） |
| 表1-3 | 认证差距 | 否（26%） | 与 表4-2/4-3 的差距判断重复，删或并入 |
| 表3-6 | 编号 | 否 | 删（与表3-4 合并后不需要） |
| 表2-2 | 竞争激烈度 | 否 | 删（与 表3-4 重复衡量） |
| M4 | 计划时间 | 否 | 与 M5 的计划字段重复，删 |

**注意**：这些都是「修」还是「删」，取决于该表是否该产出这个结论。`综合排序`/`排序`/`评分` 属于**表的核心产出**，不是多余列——**这 3 处是 bug，不是冗余**。

### 4.3 泛化列名（低信息量）

`项`/`内容`/`说明` 这类列出现在 表1-1、表2-7、表5-3、表5-4、表6-4，共 4 组。它们本身不是问题（键值型表需要），但 `项` 的取值靠模型自由发挥，导致同一件事在不同表里叫不同名字（这正是 §3.1 链路断开时最糟的情况）。
