# 端到端拆解：材料解析入库 → 7 步分析 → 装配式交付物的完整链路

> 读完这篇文章你能：把"一堆散资料变成两份能汇报的交付物"这条链路拆成 7 个可独立验证的环节，知道每一环为什么这么设计、代价落在哪里，并能把其中三四个机制直接搬到自己正在做的 Agent 项目里。

## 一、先把整条链路摊开看

先澄清标题里的一个歧义：**"7 步"指阶段 0 到阶段 6 这七个步骤，但真正发起模型分析的只有其中 5 步**。阶段 0（材料解析入库）和阶段 6（交付物组装）是确定性代码路径——前者是解析与建索引，后者是按章节取料装配。这两步不调模型不是疏忽，是刻意设计，第二节和第五节会专门讲为什么。

整条链路按 **7 阶段（0-6）/ 33 张信息表** 组织，产出是一份"33 张信息表 + 若干份阶段总结 + 两份交付物"。33 这个数字按阶段分布得很具体：

| 阶段 | 名称 | 产出方式 | 表数 | 表号 |
|---|---|---|---|---|
| 0 | 材料解析与入库 | 解析入库（不调模型） | 6 | M1、M2、M3、M4、M5、可选材料 |
| 1 | 认识场景（含门槛与合规） | 模型分析 | 6 | 表1-1、表1-3、表2-2、表2-3、表2-4、表2-5 |
| 2 | 理解商业 | 模型分析 | 9 | 表3-1 至 表3-9 |
| 3 | 能力匹配 | 模型分析 | 7 | 表1-2、表2-7、表4-1、表4-2、表4-3、表4-4、表4-5 |
| 4 | 方案与实现 | 模型分析 | 3 | 表5-1、表5-3、表5-4 |
| 5 | 价值与验证 | 模型分析 | 2 | 表6-1、表6-4 |
| 6 | 最终交付物 | 系统组装（不调模型） | 0 | 文档产出，不是表 |

6 + 6 + 9 + 7 + 3 + 2 + 0 = 33。注意阶段 6 的表数是 0——交付物不是"又一张表"，它是从表里长出来的文档。

### 1.1 一张流水线图

整条链路只有六个动作，可以先用这张图在脑内建模型：

```text
投喂材料            阶段 0                阶段 1-5               阶段 6
.pdf / .docx   →   解析（按页切分）   →   逐阶段分析        →   按章节 ← 表
.xlsx / .pptx      归类 + 建全文索引      若干张表 + 阶段总结     装配（不调模型）
(四种格式)         (不调模型)             (每步 2-5 分钟)              │
                        │                      │                      │
                        └── 来源校验 ──────────┘                      │
                            「文件名:页码」                             │
                           不存在则条目作废                             ↓
                                              导出 ←── Markdown / Word / PPT
```

图里有两处值得停一下：**阶段 0 和阶段 6 是"哑"的**——输入确定则输出确定，中间夹着的阶段 1-5 才是需要理解与表达的部分；**来源校验是一条贯穿线**，阶段 0 写入的页码级索引就是后面每次反查的底座。

### 1.2 一次完整跑批的时序说明

- **第 1 步｜选材料。** 一次投喂可以混格式，`.pdf`、`.docx`、`.xlsx`、`.pptx` 混着丢进去都行。
- **第 2 步｜阶段 0 解析。** 逐个文件走对应解析器，抽出正文、表格结构与页数；PDF 若被判为扫描件，转走本机识别引擎。结束时库里多出两类东西：条目化的材料内容（按 M1-M5 / O1-O6 归类），以及按页建立的全文索引。
- **第 3 步｜阶段 0 校验。** 表号白名单、来源格式、来源存在性各过一遍。不过的条目直接作废，不留"待补充"的中间态。
- **第 4 步｜阶段 1（认识场景）。** 开头先走对话确认"场景定义"（这一步不跑模型分析），把口径"整理成定义"写进表1-1；阶段 1 的其余几张表才由模型分析产出。
- **第 5 步｜阶段 2 到阶段 5。** 每步输入是"上游已就绪的表 + 已入库材料"，输出是几张表加一份阶段总结。生成过程通过 SSE 流式推送，断线不用把这一步整个重跑。
- **第 6 步｜阶段 6 装配。** 按"章节 ← 表"的映射把正文和附表取出来，装配成两份交付物。
- **第 7 步｜导出。** Markdown、Word 随时可导；PPT 需要本机有 Python 3.10+，没装也不影响分析与前两种导出。

整条链路的"慢"集中在第 5 步：解析是自动完成的，而每个分析阶段的生成实测 2-5 分钟（行数越多越久）。这不是卡住了，是模型在按表逐行产出——下一节讲界面怎么让人"看见"这段时间花在哪。

## 二、第一段：材料解析入库（阶段 0，不调模型）

阶段 0 是整条链路里最像传统工程、最不性感、但最容易出事的一段。它的产出方式在流程定义里就是"解析入库"，全程不发起模型调用。

### 2.1 为什么只支持这四种格式

支持的扩展名固定为四个：`.pdf`、`.docx`、`.xlsx`、`.pptx`。少一个会让后续链路漏气，多一个会让契约变模糊。

| 格式 | 这个场景里的典型资料 | 定位单位 |
|---|---|---|
| `.pdf` | 对外白皮书、盖章文件、扫描版老资料、客户给的规格说明 | 页码 |
| `.docx` | 内部调研纪要、需求文件、方案草稿、产品说明 | 页码（按解析后分页） |
| `.xlsx` | 参数表、点表、BOM、报价明细表 | 工作表 + 行 |
| `.pptx` | 产品介绍、汇报材料、客户交流用的图册 | 幻灯片页 |

为什么收窄到这四个，而不是"什么都能传"？按重要性排三条理由：

- **定位单位必须先确定。** 整条链路的溯源契约是"来源必须能定位到 `文件名:页码`"。要满足它，解析器必须给出一个稳定、可复算的定位单位：PDF 和 Word 有页，Excel 有工作表和行，PPT 有幻灯片页。反过来，独立的图片、压缩包、纯文本都没有"页"这个概念——硬收进来，只会让溯源契约在源头就漏气。
- **解析路径确定，结果才可复算。** 每种格式对应一条固定解析路径。格式集固定，测试面就固定；同一份文件解析两次结果一致。这是后面所有"可回查"能成立的地基——如果解析本身带随机性，页码级索引就没有意义。
- **工业与售前场景的资料形态本来就集中。** 白皮书、规格书、参数表、汇报材料，实际投喂进来的东西绝大多数落在这四类里。为长尾引入更多解析分支，收益远小于维护成本。

一个边界要说清楚：独立的图片文件不在支持范围内，但**图片型 PDF 是支持的**——它虽然是图，却仍然有页的概念，定位单位还在，所以可以走识别路径把它救回来。这是"收窄格式"和"保留能力"之间一个刻意的折中。

### 2.2 PDF 扫描件判定：为什么阈值是"去空白后不足 10 字符"

PDF 分两类：有文本层的（能直接抽字）和图片型的（扫描件，抽出来是空的或只有零星水印）。两类解析路径完全不同，所以入口必须先判一次。

判定规则很短：去掉全部空白字符后剩下的文本**小于 10 个字符**，且页数**大于 0**，两条同时成立就判为扫描件，转走本机文字识别路径，单文件识别超时 **180 秒**。

10 是"极低残留"和"真有内容"之间的分界线：

- **真扫描件的残留通常极短。** 图片型 PDF 并非绝对抽不出字符——页眉页脚、水印、元数据串偶尔会被抽出一两个。所以判定不能写成"等于 0"。写"等于 0"，大量扫描件会被漏判，然后以"空内容"的状态入库：条目在、来源在，正文却是空的，后面每一步都拿不到依据。这是最难查的一类问题，因为它不报错。
- **有内容的 PDF 一页至少几十字符。** 10 远低于任何有信息量的页面，所以不会把正常文件误判成扫描件；而误判的代价不小——一次误判就要走 180 秒识别流程，白白拖慢入库。
- **下界取 10 而不是 3 或 5。** 残留字符长度没有稳定规律，取太小容易把"有少量文字的正常文件"卷进识别流程。10 是在"不误吞正常文件"和"不漏掉扫描件"之间选的保守点。

识别超时定成 180 秒也是同一个思路——卡死比失败更难处理：失败可以报错让人重试，卡死会让整个入库流程一直停在"进行中"。

### 2.3 分类到 M1-M5 / O1-O6，以及两道校验

解析抽出来的内容不直接落库，要先条目化：把正文段落和表格行整理成候选条目，再归到阶段 0 的六张表里——M1 到 M5 是我方产品资料的五张主表，O1 到 O6 是可选材料分类。两类都会进入后面的失效传播计算——已交付案例、价格与授权这类可选材料，同样是某些阶段的上游（见 4.1）。

归类之后有**两道校验，任何一道不过，条目直接作废**，不留"待人工"的中间态。

**第一道：表号白名单。** 表号必须落在允许的集合内。这条看着简单，实际拦的是一类很典型的错误——编号漂移。一个已经废弃的表号如果没清干净，条目就会落到一张不存在的表里；这类错误在界面上表现为"数据莫名消失"，排查成本极高。白名单是最便宜的一刀：不在名单里的表号，直接拒收。

**第二道：来源格式 + 来源存在性。** 来源必须同时满足两条：

- 格式必须是 `文件名:页码`。缺页码不行，只写文件名不行，写"见附件"更不行——格式不对等于没有来源。
- 这个出处必须真的存在于全文索引里。这不是格式检查，而是**存在性检查**：拿着 `文件名:页码` 去索引里查那一页，查得到才算数。

两道放一起，效果是"来源不存在则条目作废"。注意这里的设计取向：**作废，而不是降级为"存疑"**。如果允许"存疑条目"入库，后续每一张消费这些条目的表都要重新处理一次"这条到底靠不靠得住"，成本会顺着链路一路放大。在入口处一次性拒收，是成本最低的位置。

📎 **源码速览**：下面是入库条目的准入判定示意（伪代码，不是代码里的真实实现），它把上面两道校验压成了三行。

```ts
// 入库条目准入判定（示意）
function acceptEntry(entry: Entry, idx: SourceIndex): boolean {
  if (!TABLE_WHITELIST.has(entry.table)) return false;   // 表号不在白名单 → 拒
  if (!/^.+:\d+$/.test(entry.source)) return false;      // 来源必须是「文件名:页码」
  return idx.hasPage(entry.source);                      // 这一页真的在索引里 → 通过
}
```

### 2.4 全文索引：FTS5 + trigram，为什么不用默认分词

索引的结构是：一张 FTS5 虚拟表，分词器用 **trigram**，靠 INSERT / UPDATE 触发器与业务行同步。

先说 FTS5。它是 SQLite 的全文检索扩展，虚拟表形式，不需要额外进程或服务——对"数据全在本机"这个前提来说这是最合理的选择：不引入第二个存储，不引入网络依赖，索引跟着数据文件一起走。

再说**为什么是 trigram 而不是默认分词器**，这是本节最值得讲的技术判断：

- FTS5 的默认分词器按空格和标点切词，这套逻辑是为英文这类有词边界的语言设计的。
- 中文没有空格。默认分词器面对中文，要么把整段当成长 token，要么切出一堆没意义的碎片，结果是**短串检索大面积失配**：你明明知道那句话里有"过载保护"四个字，但索引里根本没有这个 token，MATCH 查不到。
- trigram 换了思路：不切词，改为把文本切成**三字符的滑动窗口**。任意长度不小于 3 的连续文本都会在索引里留下痕迹。对中文这种无空格语言，这是天然友好的做法——它不关心词边界，只关心字符序列。
- 另一个好处是**页码级定位天然成立**。索引按页建：一条记录对应"某个出处的某一页"，`source` 是 `文件名:页码`，`content` 是这一页的原文片段。一次命中天然带着页粒度，不需要再回头算"这句话在第几页"。

代价也说清楚，不然就成了单向宣传：**索引体积变大**（trigram 的记录数大致与文本长度同阶）；**检索是子串匹配而非词匹配**（召回强，精度靠调用方自己约束）；**最短 3 字符的硬下界**（两个字的片段检索不出来，这正好引出下一小节）。

### 2.5 反查只查那一页：成本与精度是同一件事

反查的调用方式很窄：**只用 MATCH 查短语，并且只查该出处那一页**，短语最短 3 个字符，不做全库模糊匹配。两个独立的理由指向同一个结论。

**理由一：成本。** 这条反查会被高频调用——每一批生成结果都要逐条核对"这句话到底在不在源件里"。全库模糊匹配的代价随材料总量线性增长：材料库从几份涨到几百份，每次核对的成本跟着涨。而"这条结论出自哪一页"这个问题**本身就自带出处**——调用方手里已经有 `文件名:页码` 了，没有任何必要去扫全库，多扫的那些页扫完也不会改变结论。

**理由二：精度，而且更重要。** 全库匹配会把"别的页写过"当成"这页写过"。举例：白皮书第 12 页和第 47 页都有"过载保护"，某条结论标注来源是第 12 页，实际那句话出在第 47 页——全库模糊匹配照样命中，于是这条**页码标错的**结论被放行。而这恰恰是溯源最该拦住的一类错误：内容对、页码错，人照着页码翻不到，从此不再信任这个功能。

限定"只查该出处那一页"，是把"库里有这句话"这个弱命题换成"这一页确实有这句话"这个强命题。溯源的价值全在这个差别上。

配套的两条防御也要说：片段要先用双引号包成 FTS 短语、内部引号翻倍转义，因为片段可能带引号或星号这类 FTS 语法字符，直接拼进 MATCH 轻则语法错误、重则被解释成通配符；短语太短（去掉字母数字后不足 3 字符）时 trigram 判不了，此时返回"通过"——**判不了就不指控**。一个核验机制最怕的不是漏报而是误伤，误伤会让人去修一个根本不存在的问题，消耗的是对整套机制的信任。

## 三、第二段：逐阶段分析（阶段 1-5）

阶段 1 到 5 是链路上唯一"需要理解"的部分，也是模型真正干活的地方。五步的形状高度一致，一致到可以用一句话概括：**输入是上游已就绪的表加已入库材料，输出是若干张表加一份阶段总结。**

一致性本身就是设计。五步形状相同，意味着界面、状态机、失效传播、阶段总结的消费方式都只需实现一次；差异只在表数和表号上：

- 阶段 1（认识场景）：6 张表——表1-1、表1-3、表2-2、表2-3、表2-4、表2-5。
- 阶段 2（理解商业）：9 张表——表3-1 到 表3-9。
- 阶段 3（能力匹配）：7 张表——表1-2、表2-7、表4-1、表4-2、表4-3、表4-4、表4-5。
- 阶段 4（方案与实现）：3 张表——表5-1、表5-3、表5-4。
- 阶段 5（价值与验证）：2 张表——表6-1、表6-4。

表数分布不均匀也有信息量：阶段 2 的 9 张表集中在"这门生意怎么运转"上（利润池、方案形态、采购机制、竞争对照、上游格局、替代方案等），阶段 5 只有 2 张表。越往链路下游，表越少、每张表的结论性越强——前面是把事实铺开，后面是把判断收窄。

### 3.1 输入是"上游已就绪的表"，不是"上下文里有什么就吃什么"

每一步的输入被显式声明为两部分：**上游已就绪的表**提供"已确认的口径"（比如 M3 能力清单一变，阶段 1 的环节角色和阶段 3 的能力底账都要重新看）；**已入库材料**提供"事实依据"（阶段 0 建好的页码级索引，让每一步生成的每条结论都能落回某个出处）。

这和"把整份材料塞进上下文让模型自由发挥"是两条路。区别在于：后者的产出无法被校验（你不知道模型看了哪一段才这么写），前者的产出可以逐条反查。前者的代价是更长的流程和更多的表，后者省事但把风险推给了读文档的人。

### 3.2 锁步机制：`ready` 和 `readyHint` 的语义

界面上的流程进度轴是**锁步**的：第 n 步完成之前，第 n+1 步处于"未解锁"状态，点不动。支撑这个行为的是两个字段，分工很清楚：

- **`ready`（布尔）**：本步"数据上是否够格被标记完成"。它是一个**数据判定**，由服务端根据"本步该产出的表有没有数据"算出来，前端只负责显示。边界在于：判定的是**流程能不能往下走**，不是**信息是否完备**——缺可选列不算不齐备、不阻断，缺本步该产出的表才阻断。
- **`readyHint`（字符串）**：未就绪时"缺什么"，用一句人话直接给出来。它不是错误码，是要显示在按钮旁边、让人一眼知道下一步该干什么的提示——先告诉你已经有多少了，再告诉你能不能往下走。

几个具体行为值得记住：未就绪时"完成本步"按钮**不可点**（disabled），不是点了再报错；前一步没完成时，后续步骤"未解锁"，同样不可点；已完成的步骤**可以回看、可以重跑**，回退不删数据，由失效与重算语义处理（见第四节）；`ready` 只回答"能不能点"，**不替人点**——没有"自动完成"，没有"自动推进"。

📎 **源码速览**：就绪判定的形状（伪代码，示意用途）。注意返回值里同时带了布尔和一句人话提示，这两个字段是一起被消费的。

```ts
// 阶段就绪判定（示意）
function readiness(step: Step, data: Tables): FlowReadiness {
  const missing = step.expects.filter((t) => data.rowsOf(t).length === 0);
  if (missing.length > 0) {
    return { ready: false, readyHint: `还缺 ${missing.length} 张表：${names(missing)}` };
  }
  return { ready: true, readyHint: "数据齐了，点『完成本步』继续" };
}
```

### 3.3 为什么不做"自动往下跑"

这是整条链路里最反直觉的决定：既然每一步的触发条件都能算出来，为什么不干脆一连到底？答案是**错误前置比返工便宜**。算一笔账：

- 阶段 2 的 9 张表全部建立在阶段 1 的场景要素（表2-2）与分层架构（表2-3）之上。如果阶段 1 的要素清单有口径偏差，而这个偏差在自动推进下没被任何人看见，阶段 2 到阶段 5 一共 21 张表就都建在错的地基上。
- 这 21 张表每张都要花生成成本，返工还不是重跑一遍那么简单——前面所有"人已看过并认可"的内容都要重新看一遍。

一笔是"几分钟 × 5 次"，另一笔是"整条链路重来"。锁步机制的本质是把检查点强制固定在阶段边界上——不是因为它更智能，而是因为它更便宜。副作用也是好事："这一步是谁在什么时候认可的"天然有记录。

### 3.4 阶段总结：给人看的摘要，同时是交付物的正文来源

每一步的产出是"若干张表 + 一份阶段总结"。很多人第一次看到会以为它是顺手生成的"读后感"。它有两个身份，第二个更重要：

- **身份一：给人看的摘要。** 阶段边界上那几分钟的检查靠的就是它。表是给机器校验的，总结是给人读的——人不可能靠读三十多列的表判断"这一步的方向对不对"。
- **身份二：交付物的正文来源。** 阶段 6 装配交付物时，正文取的就是各步的阶段总结。所以总结不是可选的装饰，它是最终文档的原料。

这个双重身份带来一个很实际的后果：**阶段总结的质量直接决定交付物的质量。** 如果某一步的总结写得敷衍，交付物对应章节就会空洞——而且这个空洞在阶段 6 补不上，因为阶段 6 不调模型，只做取料和装配，不会替你重写正文。换句话说：**想清楚交付物长什么样，倒推回每一步的总结该写什么。**

### 3.5 实测节奏，以及第 1 步为什么不跑模型

先说清楚：下面是一次演示跑批的实测值，换模型、换网络、换材料规模都会变，不是性能承诺。真正影响时长的是**这一阶段的表有多少行**，不是阶段序号：

| 阶段 | 表行数 | 实测时长 |
|---|---|---|
| 阶段 1 | 49 行 | 约 8 分钟（含三轮生成后自检） |
| 阶段 2 | 53 行 | 约 2 分钟 |
| 阶段 3 | 116 行 | 约 4.6 分钟 |
| 阶段 4 | 32 行 | 约 4.8 分钟 |

单个分析阶段的实测区间是 **2-5 分钟**；阶段 1 之所以到 8 分钟，是因为它多背了三轮生成后自检的成本。材料入库则是一次投喂、自动完成，几分钟量级。已测的四个阶段加起来约 19 分钟，**五个分析阶段合起来是二十多分钟的量级**，这还不含人在每个阶段边界上的确认时间。

然后是阶段 1 里的一个例外：**第 1 步"场景定义"不跑模型分析，走对话确认**，一两轮对话就能定下来。表1-1（场景概述）的行粒度是"本场景单行"，两列是"项 / 内容"，内容由对话里"整理成定义"这一步写入。为什么特殊处理？两条理由：

- **这一步定的是全局口径。** 场景边界、业务画像、采购特征，这些不是"分析出来的结论"，是"事先约定的前提"。前提错则后面全错，而前提本身没法从材料里分析出来，只能由人给。
- **口径只能由人拍，而且这样更省。** 同一堆材料可以支撑两种不同的场景切法，两种都能自圆其说，选哪一种是业务判断。与其花几分钟让模型写一版很可能被推翻的定义，不如直接在对话里问清楚。

### 3.6 SSE 流式推送与断线续传

生成过程通过 SSE（Server-Sent Events）流式推送到界面。为什么必须流式，而不是"等结果、转圈、一次性返回"？因为两到五分钟是个尴尬的长度：短到不值得泡杯咖啡，长到足够让人反复怀疑程序卡死——而且时间越长，流式的必要性越高。流式推送把这段时间变成可见的过程：表一张一张出来，人能看到进度在动、已经出来的是什么。这不只是体验问题：如果界面只有一个转圈，人在第 60 秒做出的决定通常是"是不是坏了，重开试试"，而重开意味着把已生成的部分浪费掉。

**断线可续**是配套的：连接断了不用把这一步整个重跑。这在桌面应用里尤其重要——合上盖子、切个网络、系统休眠都会断连接，而生成本身不该因此作废。再说句诚实的：流式解决的是"可观测"，不解决"快"。

## 四、第三段：失效传播与重算

前两节讲链路怎么往前走，这一节讲**往前走之后被人改了怎么办**——这是所有"链式生成"结构绕不开的问题。

### 4.1 表间依赖共 15 条，粒度是"上游表 → 受影响阶段"

先纠一个数字：整条链路里的有效表间依赖是 **15 条**。注意它的粒度——依赖指向的是**受影响阶段**，不是"某一张指定的下游表"：上游一变，被标记的是整整一个阶段，界面再把该阶段里受影响的表逐张列出来。

| 上游表 | 受影响阶段 | 业务含义 |
|---|---|---|
| M1 产品清单 | 阶段3、阶段4 | 匹配候选池（表4-3）、架构选型（表5-1） |
| M2 规格书 | 阶段3、阶段4 | 选型对照、选型 |
| M3 能力清单 | 阶段1、阶段3 | 环节角色、表4-1 能力底账 |
| M4 边界声明 | 阶段1、阶段3 | 环节能否参与、我方参与地图 |
| M5 已知限制 | 阶段4、阶段5 | 实施风险、验收约束 |
| O2 已交付案例 | 阶段3、阶段6 | 能力证明、对外材料 |
| O3 价格与授权 | 阶段4 | 定价 |
| 表1-2 场景环节地图 | 阶段1 | 要素清单范围 |
| 表1-3 门槛与合规 | 阶段4 | 约束与合规 |
| 表2-2 场景要素清单 | 阶段2、阶段4 | 竞品对照维度、方案架构选型 |
| 表2-5 物理与合规约束 | 阶段4 | 合规路径（跨阶段表：阶段1 填要求值、阶段4 填我方路径） |
| 表3-6 替代方案 | 阶段4 | 竞品价格对照、我方价格位置 |
| 表3-8 未被满足的需求 | 阶段3 | 痛点排序、匹配矩阵缺口 |
| 表4-3 需求-能力对照 | 阶段4 | 方案范围 |
| 表4-4 细分优先级 | 阶段4 | 先做哪个细分 |

另有 3 条指向已删除表的死条目，实际永不触发，不影响上面的结论。

15 条，相对 33 张表可能的两两引用是一个很小的数——这件事本身就是设计成果，不是巧合。如果 33 张表互相之间随意引用，"上游改动影响哪些下游"就会变成一个需要图遍历、结果大得没法展示的问题，最终只能退化成"全都重算"。依赖摆在明面上、条数可控，影响面才能精确算出来、完整列给人看。**能算清影响面，才谈得上让人做决定。**

这张表里有三条值得单独读的信息：

- **上游分两类：材料表 7 条，分析表 8 条。** M1-M5、O2、O3 这 7 条是阶段 0 的产物——这正是"材料重入库"也会触发失效传播的原因：材料库不是一次性输入，它自己也在这张依赖图里。
- **受冲击最重的是阶段 4（方案与实现），被 10 条依赖打到**；其次是阶段 3 的 6 条、阶段 1 的 3 条，阶段 2、5、6 各一条。越靠下游的阶段汇集的上游入口越多，这个分布符合直觉。
- **阶段 6 也会被牵动，入口是 O2 已交付案例。** 装配式交付物不只是表格数据的函数：它引用的对外材料变了，交付物同样要重新装配。

### 4.2 从一次改动到 `is_stale`

失效传播的因果链是固定的五步：

- **触发。** 两种来源：单元格编辑，或材料重入库。
- **反查。** 按 4.1 的依赖表反查受影响的阶段。
- **标记。** 给受影响阶段的表写上 `is_stale`（"待重算"）。
- **提示。** 界面顶部出现横幅："资料已更新，建议重算受影响阶段"，同时把受影响的表逐张标出来。提示语用的是"建议"，不是"即将"。
- **决定。** **由用户决定是否重算**——不是自动全量重算。

`is_stale` 是**标记，不是删除**。下游表的数据还在，只是被标为"可能已经过期"。这个区别很重要：如果直接清数据，人在决定"要不要重算"之前就已经失去了对比的基准；标记则保留了完整信息——旧结论还在，人能看着旧结论判断"这个改动到底影响不影响它"。

重算本身还带三条约束：**只删本次确实产出的表；零产出不清库；半张表不覆盖。** 拆开看——"只删本次确实产出的表"是防止重算失败时把上一轮的成果一起清掉；"零产出不清库"是说这一步如果什么都没生成出来，也不该把已有数据清空；"半张表不覆盖"是说被部分填充的表不能整体盖掉。三条合起来是一句话：**重算的失败模式必须是"没更新"，不能是"数据没了"。**

### 4.3 提示，而不是自动全部重算

这是本节最重要的一条：**实际行为是"提示 + 人工决策"，不是"自动全部重算"。** 自动重算看起来更省事，但有两个问题，第二个是硬伤：

- **白烧调用。** 重算的代价是实打实的，每个受影响的阶段都是 2-5 分钟的生成。而"上游改了"和"下游结论失效"并不是等价关系：如果改的只是措辞、补了个备注、把一个描述写得更清楚，下游结论可能一个字都不用动。全部自动重算，等于每次都按最坏情况付费。
- **静默重写，人不知道自己看过的结论已经变了。** 前面每一步都是人确认过才推进的，人对那些结论的信任建立在"我看过它、我认可它"之上。如果下游被自动重写，人下次打开看到的是一份自己没读过的新内容，而界面上没有任何"这里是新的"的痕迹。链路上所有检查点建立的信任，会在这一刻被一次性作废。**审计性比省事重要。**

所以设计是：**系统负责算清影响面，人负责决定要不要动。** 这和整条链路的一贯分工一致：大模型负责"写"，确定性层负责"判"，而"要不要动"这类取舍，归人。

## 五、第四段：阶段 6 装配式交付物（不调模型）

阶段 6 是链路的终点，也是全篇里最容易被想错的一步。

### 5.1 两份交付物

产出是两份文档：《〈场景〉解决方案》和《〈场景〉建设工作方案》。`〈场景〉` 是占位符，实际名字由场景本身决定。这个占位符结构本身就是设计的一部分——交付物按"模板 + 场景数据"生成，不是每次从零写一份。

### 5.2 按章节 ← 表映射装配，不是"每阶段拼一个文件"

这是阶段 6 最核心的概念，也是它不调模型的原因。

先看**错误做法**长什么样：如果按"每阶段拼一个文件"的方式做交付物，你会得到一份"阶段1 + 阶段2 + 阶段3 + …"的堆叠，它的章节顺序等于**生成顺序**而不是**阅读顺序**。后果很具体：

- 读者想看"这门生意怎么运转"，内容可能散在几个不相邻的段落块里——因为它按生成阶段切，不按阅读顺序切。
- 同一件事会被多个阶段各说一遍（阶段 1 的要素、阶段 3 的能力、阶段 4 的架构都可能提到同一个业务环节），拼起来就是重复，措辞还不一致；两处口径冲突时也没有裁决机制。

**装配式反过来：先定章节，再定每个章节取什么料。** 章节结构是固定模板，决定骨架和阅读顺序；每个章节声明两件事——正文取哪一步的阶段总结，附表取哪几张表；装配器按声明逐章节取料填充。这里的关键是"正文取各步阶段总结"，它把 3.4 讲的阶段总结的第二身份接上了。必须再强调一次：**阶段总结写得好不好，在阶段 6 是救不回来的。**

### 5.3 为什么阶段 6 不调模型

理由一句话：**装配不需要生成。** 把已经写好、已经过校验、已经被人确认过的文字按位置放进模板，这是一个纯粹的搬运问题。搬运换来三个好处：

- **确定性。** 同一份表数据，装配两次得到两份完全相同的文档。这让"交付物 diff"成为可能——上一版与这一版的差异，恰好等于表格数据的差异，中间没有模型重写带来的噪声。
- **可审计。** 文档里每一段正文都能指回"哪一步的阶段总结"。因为搬运过程不改变文字，这个指向是精确的。
- **风险为零。** 用模型把正文重写一遍，内容可能更好一点，也可能悄悄改了某个数字、软化一个原本明确的判断——收益是小概率的改进，风险是"已校验过的内容被重新随机化"。

回到那句话：大模型负责"写"，确定性层负责"判"。装配既不是写也不是判——它是搬运，搬运不需要模型。

### 5.4 篇幅门禁：为什么下限和上限都要有

两份交付物都有字数区间门禁：

| 交付物 | 下限 | 上限 | 门禁在管什么 |
|---|---|---|---|
| 《〈场景〉解决方案》 | 1200 字 | 4500 字 | 下限管完整性，上限管可读性 |
| 《〈场景〉建设工作方案》 | 2000 字 | 5000 字 | 同上，区间按文档定位放大 |

门禁落在领域层的一个模块里（`report-gate`），是可单测的判定——和门槛、证据分级、能力匹配这些判定一样，属于"必须落在确定性层"的那一类。

**下限在管什么？** 下限是"完整性"的代理指标。这两份文档是拿去汇报的，一份 800 字的"解决方案"通常不是写得精炼，而是**有章节空着**——某一阶段没跑完、某一步的总结没长出来、或者某张关键表是空的。下限就是拦住"表格都跑完了但内容没长出来"这种情况，让它在导出前被发现。

**上限在管什么？** 上限管的是结构，不是内容量。超长的常见原因不是"内容真的多"，而是**同一件事被写了三遍**：阶段总结写一遍、附表附一遍、说明再补一遍；另一种是把过程性内容塞进了正文——引用痕迹、生成过程、核对说明该在右栏（来源与证据那一栏），进了正文篇幅立刻虚高。所以上限的作用是强制压缩，让文档保持"能一口气读完"的长度。

**下限和上限一起才是门禁。** 只有下限，文档会无限膨胀；只有上限，残缺的文档也能导出去。

### 5.5 三种导出格式，以及 PPT 的环境依赖

导出支持 Markdown、Word、PPT 三种格式，有一个明确的环境差异要提前知道：

| 导出格式 | 环境依赖 | 没有依赖时 |
|---|---|---|
| Markdown | 无 | 正常导出 |
| Word | 无 | 正常导出 |
| PPT | 本机需要 Python 3.10+ | 不影响分析与前两种导出 |

为什么 PPT 是特例？因为 PPT 的导出路径和另外两种不一样——它需要在本机做图形与版式合成，这一步依赖 Python 环境；而 Word 和 Markdown 是纯文本结构化输出，不需要额外环境。这里的设计取舍是：**没有把 PPT 的能力做成硬依赖。** 缺 Python 环境时，产品行为是"PPT 这一条路暂时不可用"，而不是"整个导出页不可用"，更不是"分析流程不可用"。理由很直接：分析能力是核心价值，导出格式是外设——让"少装一个 Python 环境"阻断核心流程，是把依赖放错了位置。

## 六、一次跑批的实测数据（虚构演示素材）

下面这组数据来自一次完整跑通的演示流程。**必须先说清楚：公司名、产品线、型号、客户场景、参数全部是虚构的**——演示主体是"云枢智控（YunShu Controls）"，一家虚构的工业边缘智能设备与平台供应商，三条产品线、8 个型号，客户场景是虚构的汽车零部件压铸车间设备联网与 OEE 提升。列出来只为说明链路的规模与形状，不代表任何真实产品或客户。

### 6.1 入库结果

投喂的素材是四份虚构材料：一份 1.1 万字的产品白皮书（docx）、一张 89 行的规格参数表（xlsx）、一份 9 页的产品介绍（pptx），以及两份客户调研纪要（docx）。

| 项 | 数字 |
|---|---|
| 一次投喂的文件数 | 3 个（docx / xlsx / pptx 三种格式一次投喂） |
| M1 产品清单 | 8 个型号 |
| M2 规格书 | 111 条参数 |
| M3 能力清单 | 39 项能力 |
| M4 边界声明 | 9 条"不做的事" |
| M5 已知限制 | 29 条限制 |
| 已标注来源的记录 | 119 条 |
| 材料质量六维 | 5/6 达标 |

两点值得单独说。**材料质量六维里唯一没达标的一项是：111 条参数里有 10 条没提及测试数据。** 这不是"入库失败"，而是"材料本身缺了一块"——入库过程把它识别出来了，而不是等分析走到一半才发现某个数字没依据。另外，**"已标注来源的记录 119 条"和 M1-M5 的行数是两套口径**，不要相加减。

### 6.2 场景私有库：客户资料单独入库

除了全局的产品资料库，客户资料会单独入库成"场景私有库"。同一次演示里，场景 A 的私有库一共 **36 行**：

| 分类 | 行数 |
|---|---|
| M1 | 5 |
| M2 | 7 |
| M3 | 7 |
| M4 | 3 |
| M5 | 9 |
| O1 | 1 |
| O5 | 4 |

5 + 7 + 7 + 3 + 9 + 1 + 4 = 36。这个分布也有信息量：**私有库的限制（M5）比全局库多、能力（M3）比全局库少**——客户资料里更多是"这个现场有什么约束"，而不是"我们有什么能力"。这也正是两套库要分开的原因：全局库回答"我方能给什么"，私有库回答"这个现场是什么样"，混在一张表里既没法复用，也没法隔离。注意 O1、O5 这类可选材料的行数都是个位数——它们也不在 4.1 的依赖表里，角色是补充依据，不会有下游表"因为 O1 没数据而无法推进"。

### 6.3 阶段 1 跑出来的五张表

| 表号 | 表名 | 行数 |
|---|---|---|
| 表1-3 | 门槛与合规 | 11 行 |
| 表2-2 | 场景要素清单 | 10 行 |
| 表2-3 | 分层架构 | 6 行 |
| 表2-4 | 要素间关系 | 12 行 |
| 表2-5 | 物理与合规约束 | 10 行 |

行数和表名之间有一层对应关系：**表1-3 的 11 行就是 11 道门槛**，一行一道各自独立判定；**表2-2 的 10 个要素是这一阶段的枢纽**，表2-3 和表2-4 都从它长出来；**表2-3 只有 6 行（6 个层级），表2-4 有 12 行**——6 层架构要承载 10 个要素，交互关系自然会超过要素数量本身。

## 七、这条链路的三个设计取舍

前面讲了链路怎么走，这一节讲三个"为什么不那样做"的决定。三个都不是技术能力不够，而是刻意选的。

### 7.1 为什么阶段 0 不用模型

**取舍：解析走确定性代码，不走模型。**

阶段 0 做的是"把文件里的文字和表格变成带页码定位的结构化条目"。这是一个**有唯一正确答案**的问题：这份 PDF 第 12 页写了什么，答案只有一个。对有唯一答案的问题套上模型，收益是零，引入的是不确定性。而不确定性在这个位置的代价特别大，因为它是整条链路的地基：

- 页码级索引依赖"解析结果可复算"。同一份文件解析两次得到不同的文本切分，索引就没法稳定指向某一页——反查会时灵时不灵，而"时灵时不灵"的核验机制比没有核验更糟，因为它会让人错误地信任它。
- 后续每一步都消费阶段 0 的产物。地基上带一点随机性，会在 33 张表上被放大 33 次。

唯一的例外是识别路径（扫描件 OCR）。这里确实有一个非确定环节——图像转文字是识别，不可能保证两次结果逐字相同。但它是**必要的**：没有文本层时不识别就只能得到空内容。所以这里的处理不是"用模型猜"，而是"用本机识别引擎读"，并且把它限定在"确实没有文本层"这一个分支上。**例外必须被限定在一个明确的分支里，否则它会慢慢扩散成常态。**

### 7.2 为什么阶段 6 不用模型

**取舍：交付物走映射装配，不走"再生成一遍"。**

阶段 6 做的是"把已确认过的文字放到模板对应的位置"，不需要生成能力——它是一个搬运问题（5.3 已算过这笔账：确定性、可审计、零风险）。把它和另外两步放在一起看，整条链路的模型使用边界就清楚了：**阶段 0 不调模型**（确定性解析）、**阶段 1-5 调模型**（内容生成与表达组织）、**阶段 6 不调模型**（按映射装配）。

节点在两端"哑"、中间"聪明"，是为了让全链路两头都可复算：入口的解析可复算，出口的装配可复算，中间那一段需要理解与表达才交给模型。直接结果是：**同一次跑批出来的交付物，去掉模型随机性之后的部分（结构、取料、篇幅门禁）是稳定的，只有正文措辞带模型特征。**

### 7.3 为什么不做"一键全自动"

**取舍：判定权在人，不做无人推进。** 三层理由，一层比一层实际：

- **锁步的价值来自"人在边界上看一眼"。** 3.3 算过账——检查点成本是几分钟，省下的是整条链路返工。如果把检查点去掉，锁步就白做了：流程还是一步步走，但没人看。
- **有些决定只能由人做。** 最典型的是 4.3 讲的失效重算——"上游这个改动到底有没有影响下游结论"，取决于改的是措辞还是口径。这是业务判断，不是数据判定。系统能算清影响面，但不能替人下"这次要不要重算"的结论。
- **产品只做单行逐格的判定与核对，不产出"进不进"的结论。** 这个工具的判定是**对每一格内容的**——这一格的来源能不能落到某一页、这个词是不是绝对化措辞、这个数字有没有依据；它**不产出**"这个场景该不该进"这种整体结论。既然整体结论本来就不该由工具给，那么"一键跑完并给出结论"从定位上就不成立。

所以"没有一键全自动"不是功能缺失，是**定位决定的**。工具负责把信息和依据摆到桌面上，决定权在用它的人手里。

## 八、行动清单

如果你正在做类似的"资料进、文档出"的链路，下面五条是能从这套设计里直接搬走的：

- **先把定位单位定下来。** 你的溯源契约是 `文件名:页码`、`表名:行号`，还是别的？定位单位定不下来，后面的索引和反查都是白做。定下来之后，只支持能给出这个单位的格式，其余一律不收。
- **给阶段边界加一个硬门禁，先跑两周。** 不用一开始就做全链路，挑一个现有流程里的阶段边界，加上"数据没齐按钮就不可点"，记录它拦下了几次本该发生的返工。这个数据会告诉你门禁值不值得推广。
- **把"全量重算"换成"提示 + 人工决策"。** 先把你链路里的依赖关系列成一张显式清单（条数可控、粒度到阶段，这是个设计指标），然后只做"标出受影响项 + 横幅提示"，不要自动重跑，不要让下游被静默重写。
- **交付物改成"章节 ← 表"的映射清单。** 写清每个章节的正文取自哪一步的总结、附表取哪几张。这份清单会立刻暴露一个问题：某些章节的正文来源是空的——那就说明那一步的总结需要加内容。
- **给交付物加一个区间门禁，落在能单测的地方。** 下限管完整性、上限管可读性，两个都要。

回到开头那张流水线图。整条链路里最贵的部分不是模型调用，是**每一步都要人确认**这件事——它把 33 张表切成 7 个可检查的边界，让错误在最便宜的位置被拦住。阶段 0 和阶段 6 之所以不调模型，也是同一个取向的延伸：**在能确定的地方确定，只在必须理解的地方使用模型。**
