# 引用投影与生成后自检：FTS5 全文索引、T1–T4 证据分级与三轮「这真实吗」

> 读完这篇文章你能：把"让模型别胡说"拆成三个可落地的工程动作——出处可定位、结论可复算、措辞不越界；并照着文中的 FTS5 建表、按页反查语句与三轮自检骨架，在自己项目里落一遍。

这是系列第 4 篇。前三篇讲了信息模型（7 阶段 / 33 张表）、端到端链路、以及四层架构为什么把判定从大模型手里拿走。这一篇往下走一步：判定不交给模型之后，**怎么保证模型写出来的每一行都能翻回原件那一页**。

## 一、引言：把"可信"拆成三件可工程化的事

### 1.1 一段看起来很专业、其实全是雷的输出

```text
本客户已完成设备联网改造，产线 OEE 提升 20%（来源：产品白皮书 第 12 页）。
```

这句话读起来很顺，但埋了三颗性质完全不同的雷：

- 「本客户已完成」是**客户事实**，而它引用的依据是一份通用产品文档——产品文档不会记录某一家客户的改造进度。
- 「OEE 提升 20%」是**价值主张**，但没有本客户基线。没有基线，这个数字既不能被验证，也不能被反驳。
- 「（来源：产品白皮书 第 12 页）」是**引用**，格式标准得挑不出毛病，可那一页根本没有这句话。

三颗雷的修复手段完全不同：第一颗要把口径退回行业层，第二颗要补基线（补不到就得承认"这条收益不可验证"），第三颗则是**来源不成立**，整条结论作废。它们的共同点是：**都不是"换个更强的模型"能解决的**，而是三件需要工程约束的事。

### 1.2 为什么"让模型更诚实"不是工程方案

在提示词里写上"不要编造、务必标注真实来源"，根本问题是：**它把验收标准交给被考核的人自己保管**。

- **不可测试**。"模型是否诚实"没有可断言的输出，你没法为它写单测；而"这一页是否真的出现了这个数字"可以写成断言：查到就是查到。
- **不可复算**。模型输出是采样结果，同一输入跑两次措辞可能不同；而"格式是否合法""依据是否复述了结论"这类判定，跑一万次结果必须一致。
- **不可审计**。线上出现一条编造的来源，你要能回答"哪个环节漏了、按什么规则漏的"，祈使句给不出这个答案，可单测的判定函数可以。

所以我们的做法是：**不去要求模型变诚实，而是把"诚实"翻译成一组能判、能查、能留痕的检查项**，再把判定权收走。大模型负责"写"，确定性层负责"判"。

### 1.3 三件事：出处可定位、结论可复算、措辞不越界

| 要保证的事 | 具体含义 | 工程落点 | 失败时的表现 |
|---|---|---|---|
| 出处可定位 | 每条主张能指到「文件名 + 页码」，且该页确有这句话 | 全文索引（FTS5 + trigram）+ 按页反查 | 页码是编的；或这句话是从别的页挪来的 |
| 结论可复算 | 判定与分级由代码算出，不由模型自述 | 领域层确定性判定模块，算完再入库 | 模型自己盖了"已核实"的章，出处却查不到 |
| 措辞不越界 | 行业通例不写成客户事实，推断不当结论，引用不进中栏 | 生成后三问自检 + 确定性收口 | 一格塞三件事加一句出处；硬话没有依据 |

### 1.4 本文的边界

只谈可信度工程本身；文中材料、型号、数字全部来自一套虚构演示素材（一家工业边缘智能设备供应商的产品资料与两份客户调研纪要）。

## 二、来源溯源铁律（G-R0）：先定义什么叫"来源"

### 2.1 铁律只有一句话

**每条证据标注来源，来源不存在则条目作废。**

最需要工程化的是最后四个字："作废"。但讲作废之前，得先定义"来源"长什么样——否则"来源不存在"无从判定。

### 2.2 合法来源只有两种形态

- **URL**：`http(s)://` 开头、主机部分非空，用于公开资料。
- **文件引用**：文件名 + 定位符，「定位符」是 `:页码` 或 `#章节`，例如 `规格书.pdf:12`、`白皮书#3`。定位符里不许再出现路径分隔符或冒号。

第二条约束看着琐碎，其实是关键：**它强制了"定位符只有一个，而且必须是位置"**。如果允许 `某目录/某文件.pdf:12:3` 这种写法，"这一条到底指哪里"就没法机械判定，反查也无从下手。

📎 **源码速览**：来源格式校验的形状。非法格式直接返回 false，调用方据此作废条目。

```ts
// 简化伪代码：来源格式校验（两种形态二选一）
function verifyCitation(source: string): boolean {
  const s = source.trim();
  if (s.length === 0) return false;
  const isUrl = /^https?:\/\/\S+$/.test(s);           // URL：协议 + 非空主机
  const isFileRef = /^[^\s/:#]+[:#][^/\s]+$/.test(s); // 文件名 + :页码 / #章节
  return isUrl || isFileRef;
}
```

### 2.3 为什么定位粒度是"页"，不是"文件"

一份 1.1 万字的产品白皮书，你说"依据是白皮书"，信息量约等于零——查的人还是得从头翻一遍。页码是**人能在一分钟内打开确认**的最小单位。

整个可信机制最终要能被人抽查，"每个质量关至少抽查 3 条来源、打开确认内容一致"这条要求，只有在定位粒度足够细时才成立：如果一条来源指向 60 页的文档，抽查一次的成本足以让人放弃抽查，规则就废了。

顺带说一句解析的边界：支持 `.pdf`、`.docx`、`.xlsx`、`.pptx` 四种格式；扫描件（去空白后不足 10 字符且页数大于 0）走本机 OCR，超时 180 秒。**OCR 是这套机制里最脆弱的一环**——识别错一个字，按页反查就可能查不到。

### 2.4 "作废"比"降级保留"严格在哪

这是铁律的设计核心。假设有一条参数标着来源 `规格书.xlsx:8`，但材料库里没有这一页，有两种处理：

- **降级保留**：留着，把证据级从 B 降到 C、权威性从 T3 降到 T4，肉眼看还在表里。
- **作废**：这条不许进表。

我们选后者，理由三条：

- **降级保留留了一条逃生通道**。只要模型学会"标低一档就能过"，它就有动机把没依据的一律标低——表面诚实，没依据的内容照样交付。降级是给"有依据但依据较弱"准备的。
- **一条查不到出处的结论，比没有结论更危险**。没有结论，读的人知道自己缺信息；挂着格式正确引用的结论，读的人会当成已核实的事实。前者的风险是"不知道"，后者是"错误地确信"。
- **"来源不存在"往往指向编造，而不是笔误**。文件名加页码是模型最容易顺手生成的句式，对这种形态必须零容忍。

### 2.5 作废的两处落地：为什么不能只有一把尺子

- **材料入库阶段（阶段 0）**：M1–M5 是从资料里**提取**出来的东西，无来源佐证的宣称必须删——硬作废，记录根本不进表。
- **分析阶段（阶段 3 之后）**：这些行是**我们自己的推理产出**，工作流标准明确允许写推理和判断。

拿同一把尺子量就会得出荒谬结论："AI 推断 + 未核实 = D 级 = 不许入库"——而分析行的本质就是推断。所以两处用两把尺子：

| 行类型 | 分级取值 | 无出处时的处理 |
|---|---|---|
| 材料入库行（M1–M5） | A / B / C / D | D 级不得入库（作废） |
| 分析行 | 只有 A / B / C，结构上产不出 D | 有可定位出处判 B，给不出出处判 C |

## 三、引用反查的技术实现：FTS5 + trigram

出处可定位是规则，反查是它的执行机构。这一节讲怎么用 SQLite 的 FTS5 把"这一页到底有没有这句话"变成一次真查。

### 3.1 虚拟表长什么样

| 列名 | 存什么 | 说明 |
|---|---|---|
| `ref_id` | 业务行 id | 触发器写入，用于删除/更新时定位索引行 |
| `source` | 出处串，形如 `ingest-xxxx.pdf:10` | **按页存**：一页一条或多条，不是一份文件一条 |
| `content` | 该页的原文片段 | 反查时匹配的对象 |
| `table_code` | 业务表号（M1–M5 / O1–O6） | 便于按材料类别收窄 |

关键在 `source` 按页存：所以"这份材料的第 10 页"在索引里是一个可以等值命中的值，而不是需要从头检索的范围。这是页码级定位能成立的前提。

### 3.2 为什么是 trigram

FTS5 内置分词器里最常用的是 `unicode61`，它对中文有两个致命问题：

- **中文没有空格**。`unicode61` 会把一段连续汉字当成一个 token，于是"设备联网改造"整句成了一个词，你查"设备联网"匹配不上——短语查退化成"必须逐字相同"。
- **我们要的是短串匹配，不是分词匹配**。"6 TOPS"、"OEE 提升"这类片段，需要的是"这段字符序列在不在这一页里"，而不是"分词后有没有共同的词"。

`trigram` 把文本切成 3 字符的滑窗，好处是任何长度不小于 3 的连续字符序列都能被定位（天然的子串匹配），而且不依赖语言。代价是**索引体积更大**，以及**查不了 3 字符以下的片段**——所以实现里设了最短长度门槛，低于门槛的片段不能用来判定"这一页没有这句话"：`6 TOPS` 去掉空格变成 `6TOPS` 就查不到了，这种查不到是索引的局限，不是材料的问题，不能据此扣"出处无此内容"。

### 3.3 反查策略：只在该出处那一页做短语查

这是整套机制里最该被抄走的一条。反查 SQL 只有一行，但两个条件缺一不可：

```sql
-- 在这个出处（也就是这一页）里，找这个短语
SELECT 1
FROM source_fts
WHERE source = ?                 -- 先把范围收敛到这一页
  AND source_fts MATCH ?          -- 再在这一页里做短语匹配
LIMIT 1;
```

而不是 `SELECT 1 FROM source_fts WHERE source_fts MATCH ?` 这种全库模糊匹配。

差别在哪？**"别的页写过"不等于"这页写过"**。只做全库匹配的话，模型把白皮书第 3 页的数字挂到第 12 页上，反查照样通过——引用位置错了，检查却抓不到。而引用位置的准确性，恰恰是"能翻回原件那一页"的全部意义。

这么做有两个明确好处：

- **精度**：出处与内容在同一页内校验，串页引用会被判出来。检查结果从"这句话在材料里存在"升级为"这句话在这一页存在"。
- **成本**：`source = ?` 先把候选集收敛到一页，`MATCH` 走倒排索引，不是对全库文本做扫描；加上 `LIMIT 1` 短路，命中即返回。一次反查的成本与材料库总规模基本无关。

落到接口上只有两个问题：这个出处存在吗（`hasSource`，等值查）、这一页真的出现了这句话吗（`hasContent`，短语查）。两者必须分开，因为严重程度不同——**出处不存在是硬伤，出处存在但内容对不上是存疑**（可能改写自材料，也可能引错了页，需要人看一眼）。

### 3.4 查什么片段：只挑"编不出来"的东西

反查的输入是片段，不是整行。这里有个容易忽略的取舍：**如果要求每一行都与材料逐字相同，那每一行都会被误判成"出处无此内容"**——分析行本来就是模型组织的语言。

所以抽片段只挑三类"如果材料里没有、基本就是编的或张冠李戴"的东西：

- **带量纲的数**：有单位的数字（算力、容量、频率、时延、金额、百分比、台数等），最容易被顺手编出来，反查收益也最高。
- **引号里的词**：模型加引号时通常是在引用原文。
- **长专名**：连续的中文长词或字母数字串（产品名、协议名、标准名、模块名）。

普通描述性文字不参与反查；核实说明与核实结论两列也不参与——它们说的是"我核过了"，不是"事实是什么"。两个防御细节：**片段要包成短语再进 MATCH**（片段可能带引号或星号，直接拼进去会变成语法错误或意外通配）；**FTS 语法异常不许让自检崩掉**——检查工具自己报错，不能成为给内容扣罪名的理由。

### 3.5 触发器同步索引：INSERT、UPDATE，以及那个漏掉的 DELETE

索引与业务表不同步是这类机制的经典故障：**库改了，索引没改**，反查于是给出假阳性——一份已经被删掉的材料，它的出处照样"存在"。

处理方式是触发器同步：每张资料库表各配两个触发器，`AFTER INSERT` 写入索引，`AFTER UPDATE` 先删旧行再写新行。业务表是唯一写入入口，索引只是它的投影——不允许业务代码自己维护，否则迟早有人漏掉一处。

📎 **源码速览**：索引同步触发器的形状。注意 UPDATE 是"先删后插"，不是原地更新。

```sql
-- 简化示意：一张资料库表的索引同步（真实实现按 M1–M5 各配一组）
CREATE TRIGGER trg_demo_update AFTER UPDATE ON demo_table
BEGIN
  DELETE FROM source_fts WHERE ref_id = OLD.id;  -- 旧索引行先删
  INSERT INTO source_fts (ref_id, source, content, table_code)
  VALUES (NEW.id, NEW.source, NEW.name, 'M1');   -- 再写入新行
END;
-- INSERT 触发器同形，只是不做 DELETE
```

真正值得记的是**触发器不是万能的**。上面这组只覆盖 INSERT 和 UPDATE，**没有 DELETE 触发器**：删掉一行业务数据，索引里那一行还在，出处存在性判断对一份已删除的材料照样返回"存在"——来源真实性自检给出**假阳性**。

启发是：**只要有一个写入路径没被覆盖，索引同步就是错的**，而且删得越干净、自检越不准。修法是给删除入口补一个显式的索引清理动作，按 `ref_id` 删——触发器负责常规路径，删除这种低频但破坏性强的路径单独兜底。

## 四、证据分级：为什么它也属于确定性层

### 4.1 来源权威性 T1–T4

| 档位 | 含义 | 典型来源 |
|---|---|---|
| T1 权威 | 一手信息 | 用户补充的资料；政府文件、标准、法规 |
| T2 较权威 | 用户确认过的事实 | 官方文档、年报 |
| T3 参考 | 从公开材料提取、未经确认 | 行业报告、媒体分析 |
| T4 待验证 | 无来源佐证 | 模型推断，没有可定位出处 |

映射是确定性的：来源标记为"用户补充"判 T1，"用户确认"判 T2，"AI 提取"判 T3，"AI 推断"判 T4；政府文件、标准、法规等类目级细化，在资料入库时按来源类目另行标注。

### 4.2 证据级 A–D

证据级回答"这条主张能不能当结论用"。其中两档有强制动作：

| 证据级 | 含义 | 强制动作 |
|---|---|---|
| A | 直接可验证 | 可作结论 |
| B | 间接有据 | 可作结论，需说明依据路径 |
| C | 架构推断 | **不写结论** |
| D | 过度宣称 | **必须删除** |

材料入库行的映射：

| 数据来源 | 是否已确认 | 证据级 |
|---|---|---|
| 用户补充 | 不区分 | A |
| 用户确认 | 不区分 | B |
| AI 提取 | 已确认 | B |
| AI 提取 | 未确认 | C |
| AI 推断 | 已确认 | C |
| AI 推断 | 未确认 | D |

注意最后两行：**AI 推断即使被确认过，仍然是 C**——"确认"改变的是可信度，不改变来源形态，推断就是推断。而"AI 推断 + 未确认"落到 D，直接删除。

分析行的映射只有 A/B/C，结构上产不出 D：用户补充判 A，用户确认判 B，"AI 提取 + 有可定位出处"判 B（与材料行同口径），"AI 提取 + 出处给不出来"判 C，"AI 推断"判 C。这就是 2.5 节那件事的代码化：**用同一把尺子量两种行，规则之间会打架**。

### 4.3 关键点：分级由服务端算完再入库

以上全部是纯函数映射——输入是"数据来源标记"和"是否已确认"两个字段，输出是档位，没有模型参与，不需要语义理解。这就是它属于确定性层的原因：**可单测、可审计、跑一万次结果一致**。

真正需要强调的是下一句：**模型自封的核实状态会被剥掉。**模型可以改内容列、可以改核实说明、可以把出处写进右栏，但**不许把核实结论升为"已核实"**——修正值的清洗逻辑里，任何试图把核实结论设成"已核实"的字段值一律丢弃。

### 4.4 为什么"谁盖章"必须由代码决定

这是权限问题，不是能力问题。"已核实"这个章意味着"这条主张有一个可定位的出处，而且那个出处确实支持它"。

- 如果模型能自己盖章，它同时是**运动员和裁判**。"我核实了"不携带任何可验证信息，只是又一句生成文本。
- 盖章的标准可以机械判定：出处能解析成「文件名:页码」列表、这些出处都能在材料库查到、抽出的关键片段至少有一个能在该页命中。全是查表和模式匹配。
- 反过来，**降级可以由模型提议**——它说"这条查不到出处，按实降为无法核实"，这是自我否定，不构成作弊动机；升级是自我肯定，必须由外部规则裁定。

所以权限线这么划：**升级只能由确定性层给，降级模型可以自己提。**

## 五、生成后三问自检（G-R8）：三轮，但成本只跟真问题成正比

### 5.1 三问问的是什么

每次生成之后，对每条信息连问三问：**这真实吗？客观吗？有价值吗？**三问不是修辞，每一问都有具体判据，而且大部分已经被写成确定性判定项：

| 这一问 | 具体查什么 | 确定性层对应的判定项 |
|---|---|---|
| 这真实吗 | 出处能不能对上材料；带量纲的数、引号里的词、长专名像不像编的；没有出处的推断有没有被写成事实 | 出处查不到 / 出处无此内容 / 声称有据但无出处 / 结论与证据矛盾 |
| 这客观吗 | 有没有绝对化、营销化措辞；有没有把行业通例写成本客户事实；口径是谁的 | 绝对化措辞 / 把推断写成客户事实 / 客户侧口径混入场景分析 |
| 这有价值吗 | 价值类主张有没有可测指标、有没有本客户基线 | 价值不可验证 |

"有价值吗"值得单独说一句：**没有本客户基线的收益等于无法验证**。而且基线的判据不能只看空值——如果模型写"行业通例：达成率提升 20%，本客户实测值未提供"，这句补白会让判据形同虚设。所以判据是：剥掉括注后，正文里只要出现"未提供 / 未给出 / 暂无 / 待补"这类词，同样算没有基线。

### 5.2 三轮分工：报告、修复、复查

| 轮次 | 处理范围 | 做什么 | 输出 |
|---|---|---|---|
| 第 1 轮 | 全量行 | 三问逐行过，**只报告不改** | 只有"哪几行有问题 + 哪一问 + 一句话说明" |
| 第 2 轮 | **只改被点名的行** | 给出可直接落库的字段值 | 改写后的内容列、核实说明、出处 |
| 第 3 轮 | 复查仍存疑的行 | 再问一遍 | 仍存疑的问题清单 |

"被点名的行"是确定性判定项判出的行，加上第 1 轮模型自己指出的行。第 2 轮改完**要重新跑一遍确定性判定**——改没改掉不是模型说了算，是规则说了算；第 3 轮的范围就是"改完仍被点名"的行。

### 5.3 为什么是三轮

- **第一轮全量，保覆盖度**。抽检会漏，所以逐行过、不抽检；这也是它唯一贵的地方。
- **第二轮修复，闭合环**。只报告不修，问题就只是清单。
- **第三轮复查，因为"改过"不等于"改对"**。第 2 轮的修改值是模型给的，它可能只改了措辞、没动口径，甚至引入新问题，必须重新判定加重新问一遍。
- **三轮封顶，成本有上界**。不设轮次上限的自检会变成"不知道还要多久"。

### 5.4 为什么第 1 轮不许改

第一版实现把"全量检查"和"顺手修复"合成了一次调用，结果是**检查成本变成与全量行数成正比**：模型读完所有行，然后为了改其中一小部分重写了一大段文本。真正需要改的只有少数行，输出量却按全量算，耗时直接压垮一次生成的节奏。

拆开之后两轮的成本结构完全不同：第 1 轮的输出只有"哪几行有问题"，它贵在**输入**（全量行）；第 2 轮只带被点名的行，它贵在**真问题数**。"成本必须与真问题数成正比，不许与全量行数成正比"的落地方式，就是**把报告和修复拆成两次调用**。

还有第二个理由，而且更重要：**报告-修复分离是一种防呆机制**。如果第 1 轮允许"边看边改"，模型会顺手改掉一些**没有被点名的地方**——这些改动没经过判定，也没留下问题记录，既不在自检报告里，也不在任何人的审查视野里。拆开之后权限被收窄成一句话：**第 1 轮只看不说，第 2 轮只说被点名的那几行。**

### 5.5 三条硬约束：批次、单轮超时、总时长

| 约束 | 值 | 作用 |
|---|---|---|
| 单批行数 | 不超过 60 行 | 不把一次提示撑爆；超出一批时按批连问 |
| 单轮超时 | 180 秒 | 超时就跳过本轮，用确定性结果收口 |
| 自检总时长 | 不超过 10 分钟 | 自检不许把一次生成拖到不可预期 |

配套还有两条工程决定：**某一批失败只丢那一批**，不牵连其他批次，自检整体不抛异常——宁可少跑一轮自检，也不能因为自检起不来就丢掉用户这次的产出；**拿不到索引时退化为"查不了就不指控"**，绝不能因为索引故障给一批本来正确的行扣上"出处查不到"的帽子。

### 5.6 三轮后仍改不掉的：按实降级

三轮跑完仍存在的硬伤，不会继续挂着"已核实"，而是**按实降级**。降级分两种，必须分清楚，否则会误伤：

- **结论降级**：核实结论降为「无法核实」，留痕写明原因，不得当结论用。适用于确实声称有来源、但出处定位不了的硬伤。
- **只改来源属性**：如果这行的结论本来就是"行业通例"（行情本来就能自证），那只把来源属性标为"AI 推断"，不定论降级。否则一句行业通例会被白白打成"无法核实"——实跑里真实发生过的误伤。

还有一条容易忽视的要求：**留痕文字必须与实际做法一致**。早期版本对"保留档位"的行，留痕里也写着"核实结论按实降为无法核实"，但库里实际改的是来源属性——用户看到的是"被降级了"，库里却是"行业通例 + AI 推断"。

### 5.7 这是生成过程的内部步骤，不交给用户判断

- 它自动查、自动改、改不掉的按实降级，**不把决定推给用户**。
- 它**不阻断推进**：三轮跑完就出结果，报告写清哪些已修、哪些已降级、哪些仍存疑，人想看时能看到，但不要求人先做判断才能继续。

理由也简单：如果自检每次都要人工确认，用户会习惯性点"继续"，这道关就退化成一次点击。**把判断留在系统里，把结果留在报告里**，才是可维护的形态。

📎 **源码速览**：三轮骨架的形状。第 2 轮只处理被点名的行，第 3 轮复查"改完仍被点名"的行。

```ts
// 简化伪代码：三轮增量自检
let findings = runDeterministicPostcheck(rows);          // 判定始终来自确定性层
const flagged = await triage(rows, findings);            // 第 1 轮：全量三问，只报告
const targets = rows.filter(r => flagged.has(r.rowId));  // 第 2 轮：只改被点名的行
for (const row of targets) applyFix(row, await repair(row));
findings = runDeterministicPostcheck(rows);              // 改完重判，不假设改对了
await triage(rows.filter(r => stillFlagged(r, findings))); // 第 3 轮：复查仍存疑的行
```

## 六、确定性收口：不靠模型自觉

三问自检是"模型参与"的那一半，天然有个弱点：模型可能连着改三轮也没改掉。所以每一类问题都必须配一个**确定性兜底**——不问模型愿不愿意，直接按规则处理。

### 6.1 中栏夹带出处：7 条模式，命中即判定

这条规则来自一个很直白的反馈：**中栏的表格要说价值、说结果，来源和引用放到右栏**。模型习惯把出处写在结论旁边，因为那在阅读上确实"完整"，代价却是读者抓不到结论。所以判定靠 7 条模式匹配：

| 序号 | 引用痕迹形态（描述性写法） | 说明 |
|---|---|---|
| 1 | 文件名加页码，扩展名是 pdf / pptx / docx / xlsx / txt / md / csv / png / jpg 之一，页码可带区间 | 最主流形态；匹配时必须整块吃掉，含材料 id 前缀 |
| 2 | 没带扩展名的材料 id，形如库内生成的材料编号前缀加随机串 | 说明内部标识漏出来了 |
| 3 | 「来源：」「出处：」「摘自：」「参见：」「见附件：」「依据材料：」这类引导词 | 引用引导语，无具体出处也判 |
| 4 | 括注形式的表号，如「（M5）」「（O2）」 | 材料类别标识，属内部编码 |
| 5 | 表号加下划线加字段名，如「M1_产品型号」 | 契约层字段名漏进正文 |
| 6 | 「第 N 页」 | 页码独立出现 |
| 7 | 「按白皮书」「按报告」「按标准」「按材料」这类"按某类材料"的说法 | 泛化引用，同样是引用痕迹 |

三个实跑踩出来的细节：

- **模式 1 必须排在第一位、整块匹配**。如果让模式 2 先把材料 id 前缀摘掉，剩下的就是一个光秃秃的 `.pdf:2`，比不处理还难看。
- **删除时不能"按词啃"**。早期实现对某些词做按词删除，把「未提供（本客户材料未含）」里的"材料未"当引用痕迹删掉了，正文变成病句「未提供（本客户 含）」。**「本客户材料未含」是缺材料的说明，是规则要求必须写的内容，不是引用痕迹。**修法是：括号里带"本客户 / 客户"的限定语整块保护，任何引用模式都不许碰。
- **例外只免长度，不免夹带**。表1-1 的正文列不受字数上限约束（见 6.2），但引用痕迹同样不许出现。

### 6.2 中栏太长：超过 60 字即超标

中栏内容格的约束是：一格一句话，**建议不超过 40 字，超过 60 字算超标**。一格里塞三件事再加一句出处，读的人根本抓不到结论在哪。

有且只有一个例外：**表1-1 的正文列**。这张表是场景画像概览，"项 / 内容"纵向呈现，"内容"就是整段表述，压到 60 字反而会把范围、口径、条件这些必要信息切碎。例外只给这一列——其余长文本的中栏列（怎么测、打分依据、要点等等）都是结论型格子，照旧受约束。曾经想过"凡是长文本列一律豁免"，查证后发现那等于把这条检查直接废掉，已经否掉。

### 6.3 三轮后仍夹带：确定性搬进右栏，正文一字不删

模型改了三轮中栏里还有引用痕迹，就不再等它，**确定性逻辑直接把引用搬进右栏**，做法分两种：

- **纯引用的句子整句搬走**：把引用痕迹和标点都摘掉后，剩下的字不超过 2 个——这句话除了说出处，什么都没说。
- **正文里夹带的引用片段摘掉，正文留下**：只摘引用痕迹，不删正文。

搬走的引用并进右栏的「来源」字段（已有内容就接在后面），**引用一条都不许丢**。搬空的格子**留空，交给完整度检查去报缺**，不许塞一句"待补"糊弄——如果一格只剩引用、搬空后内容是空的，说明它本来就没写出任何结果，这是一个真实的信息缺口，应该被报出来。

最后一条纪律：**正文一字不删**。正文是用户的资产，确定性收口只负责把引用挪到该在的位置。

### 6.4 硬结论无依据：写"不能碰"却没有依据，判硬伤

"不能碰 / 不参与"是最重的判定，等于告诉客户"这块别找我们"，所以必须过门槛：**如果这一行自己写的核实结论就是「无法核实」或「有反证」，那它就是"自认没依据还下了硬结论"**，直接判硬伤。依据是证据分级规则——C 级（架构推断）不写结论。既然这一行自己都承认核实不了，那它只能降级写"只能配合 / 辅助"，或者补足依据再说。

对应的实跑实例很典型：某一行判"不能碰"，而它的核实结论正是「无法核实」，依据只是一个单品的规格限制。**用一个型号的短板去否定一整块业务，是这类硬伤最常见的形态。**

### 6.5 判定与能力底账矛盾：跨表比对，只比能力名

这是六条收口里唯一一条**跨表**检查：拿能力底账表里的能力名清单，去比对那些下了硬否定结论的行。

触发条件是"这一行自己下了硬否定"——"能不能碰"列写着「不能碰」，或者"我方角色"列写着「不参与」。其他行里出现的"某型号无 NPU"是补充说明，不该被点名。然后从这一行的中栏文本里用模式抽出否定断言中的能力词（形如"无 / 没有 / 不支持 / 不具备 / 缺乏 + X能力 / X产品 / X功能 / X算法 / X硬件 / X模块 / X引擎 / X平台 / X方案"），拿去和底账比对，底账里有就是矛盾。

两个必须记住的判据约束：

- **只比能力名，不比限制条件**。限制条件记录的就是"我方缺什么"，拿它去证否"无 X"会得出"底账自己都说无 X"的鬼话——实测里这样做的结果是一批全是误报。分工很明确：**能力底账用来证明"我们有"，限制清单用来描述"这一块的条件"，两者不能互相引用。**
- **右栏枚举值不能拿来比对**。右栏有权威性和证据级的枚举值，纳入比对后，型号命名里恰好含某个档位子串的情况会全部误报，所以只认**中栏**的枚举列取值。

### 6.6 依据未落到事实：复述结论，或者写行业套话

"角色判定依据""打分依据""能力依据"这一类列，职责是写**我方凭什么**。两种典型废话都能确定性认出来：

| 废话形态 | 判定方式 | 例子（描述性） |
|---|---|---|
| 复述结论 | 依据文本里又出现了**同一行中栏枚举列的取值** | "程度 / 角色"两列已说"属外围配合"，依据列里又写一遍 |
| 行业套话 | 命中套话模式：通常 / 一般 / 大多 / 普遍 / 往往，后接"由某某承载 / 提供 / 负责 / 厂商 / 供应商" | "通常由第三方软件承载" |

两条判据都不需要语义模型：前者是字符串包含判断，后者是模式匹配——**一条看起来需要理解语义的规则，最终被化约成两条可比对的机械判据。**

## 七、引用投影：中栏说结果、来源归右栏（G-R9）

### 7.1 中栏的写法约束

中栏内容格只写**结论与结果**：谁、做什么、多少、能不能、意味着什么。一格一句话，建议不超过 40 字，超过 60 字算超标；数值列不许用文字代替数字。这条约束的动机不是审美，是**阅读路径**：看表的人第一眼要抓到结论，引用和证据是第二眼的动作。

### 7.2 什么不许进中栏

- 文件名、页码（含各种写法）
- 库内材料编号（材料 id 前缀那一类）
- 「来源：」「出处：」等引用引导词
- 括注形式的表号（材料类别标识）
- 「材料未提供」这类**说明性表述**——它属于缺材料的说明，走另一条规则，不是引用痕迹

### 7.3 右栏三个字段的分工

| 右栏字段 | 放什么 | 与中栏的关系 |
|---|---|---|
| 来源 | 出处：文件名 + 页码，多条用分隔符连接 | 中栏被搬走的引用最终落到这里 |
| 证明材料与判断依据 | 支撑这个结论的具体证据内容、判断依据 | 中栏说"是什么"，右栏说"凭什么" |
| 核实说明 | 核对过程、对不上的地方、降级原因、自检留痕 | 中栏不需要知道的过程信息 |

### 7.4 为什么是"搬走"，不是"删掉"

**删掉引用，等于把"可回查"这件能力本身删掉了。**如果中栏出现 `白皮书.pdf:12` 就直接删掉，这条结论的出处就永久丢失——右栏是空的，读者没法翻回原件，第二节讲的溯源铁律也就落空了。

所以处理方式必须是**投影**而不是删除：引用从"可见位置"（中栏）移到"归档位置"（右栏），信息一条不少，只是分层了：

> 结论放在读者第一眼看到的地方，证据放在读者需要验证时能找到的地方。

### 7.5 一个对照示例

| | 改前 | 改后 |
|---|---|---|
| 中栏 | 本场景已完成设备联网改造，覆盖产线 12 台设备，OEE 提升 20%（来源：产品白皮书 第 12 页） | 设备联网改造覆盖 12 台设备，OEE 提升 20% |
| 右栏来源 | 未写 | 产品白皮书.pdf:12 |

注意改后中栏依然有 12 和 20%——**数字和结论一个没丢**。变化只发生在两处：引用搬到了右栏，口径问题（"本场景已完成"这种客户事实口径）被记进了右栏核实说明。还有个细节：改后的中栏如果仍然超过 60 字，会继续被「中栏太长」判定项盯住——**搬引用不会顺带让格子变短**。

## 八、硬结论的双门槛（G-R10）

### 8.1 门槛一：逐条对照能力底账

写「无 X 能力」之前，必须先在能力底账里搜 X——**包括同义词和产品系列名**。底账里有，就改判。这条门槛用一句话说就是：**一个型号的限制，不能当公司级结论。**

### 8.2 门槛二：依据必须立得住

如果这一行的右栏核实结论是「无法核实」或「有反证」，**就不许下硬否定结论**，只能写"只能配合 / 辅助"，不确定的部分留在右栏。这与 6.4 是同一件事的两面：6.4 是确定性判定项（兜底判硬伤），这一条是正向的判定门槛。

### 8.3 为什么跨表只比能力名、不比限制条件

先区分两张表：**能力底账**回答"我方有没有这个能力"，每行是一个能力项；**限制清单**回答"这个能力有什么条件、哪个型号不支持"，每行是一条限制。

拿限制条件去证明"无 X"，逻辑上就错了：**限制清单的存在，恰恰说明这个能力是有的**（没有的能力不需要写限制）。用它证否会得出"底账自己都说无 X"这种自相矛盾的结论，实测里这样做的结果是整整一批误报。所以跨表比对只用能力名；限制条件该去的地方是右栏核实说明——它是**条件的描述**，不是**能力的否定**。

### 8.4 一个具体推演：某型号无 NPU，不等于我方无 AI 推理能力

假设某个边缘控制器型号（处于在研状态）的规格参数里写着「无 NPU」。如果据此写下"我方不具备 AI 推理能力，此环节不参与"，这条结论错在三层：

- **范围错**。一个型号的规格被扩张成了公司级能力判断，而底账里的能力项是按能力记的，不是按型号记的。
- **事实错**。能力底账里有「边缘 AI 推理算力（边缘算力盒子，6 TOPS NPU）」，状态是**已交付**——我方有这个能力，而且交付过。
- **归类错**。真实情况是"这个型号自身不带 NPU，需要外接算力盒子承载推理"，属于**硬件形态的限制**，不属于**算法能力的缺失**。

正确写法要把两件事分开：

```text
我方有边缘 AI 推理能力（6 TOPS NPU，已交付）；
该在研型号自身不带 NPU，边缘推理需外接算力盒子承载。
```

### 8.5 缺算法与缺硬件必须分开写

| 缺什么 | 表述方式 | 后续动作 |
|---|---|---|
| 缺算法 / 专业模型 | 写"该算法不在我方现有能力范围内" | 找合作伙伴补算法，或缩小场景范围 |
| 缺硬件 / 平台 | 写"该型号形态不支持，需外接某类硬件承载" | 换型号、加配件、改架构 |

混写成一句"我方做不了"，后果是**把一个可以解决的问题判成了不能碰**。表格里这两类问题必须写得能被分别复算——读的人要能看出"到底是什么缺了"。

## 九、诚实的边界：这套机制保证不了什么

### 9.1 规则能判格式和逻辑，判不了"这话虚不虚"

第六节的收口项都是可判的：引用痕迹是模式匹配，"不能碰"是枚举值比对，依据复述是字符串包含。但有一类问题判不了——**「我们的方案能显著提升管理效率」，这句话虚不虚？**

规则能抓"唯一""必然""彻底解决"这类绝对化词（它们在词表里），却抓不出"显著"这种**软化过的空话**：没有绝对化标记，也不是价值表的指标行，字数和引用都合规。补位方式只能是结构性的：要求价值主张必须有**可测指标 + 本客户基线**，没有基线的收益无论措辞多谨慎都判"价值不可验证"——**用"能不能验证"替代"听起来虚不虚"，一个更弱但可判的判据。**

### 9.2 正则一定会有漏网

7 条引用痕迹模式覆盖的是已经见过的形态，换一种写法就能绕过去：页码写成中文"第三页"；材料不写文件名，写成"那份产品说明"；引用不说"来源："，写"详见附件中的相关章节"。

所以规则的位置必须摆正：**它是"命中即判"的兜底，不是"没命中即合格"的证明。**人工抽查依然不可替代——这也是来源抽查这条要求一直保留着的原因：每个质量关至少抽查 3 条来源，打开确认内容一致。

### 9.3 分级依赖材料本身的质量

前面所有判定都建立在一个前提上：**材料库里的内容是可信的**。而这个前提本身有条件。

材料质量有六个评估维度。在一次演示素材的实测里，六维中有五维达标，唯一未达标的一项是：**111 条参数里有 10 条未提及测试数据**。这条未达标会向上传导：基于这些参数做的能力判断，可信度上限就是这些参数的可信度上限。**分级机制不会让材料变得更可信，它只能做到"把不可信的部分标出来"。**

解析本身也会损失信息：扫描件走 OCR，识别错一个字，按页反查就可能查不到，而查不到会被记成"出处无此内容"——这时报出来的**不是内容的问题，是解析的问题**，机制只能指出"这里对不上"。

最后必须强调：**查不到不等于编造**。片段不足 3 字符时 trigram 索引查不了，判不了就返回"通过"；这一页也可能确实没入库；FTS 查询本身异常时，检查工具出错不能成为指控内容的理由。所以"出处查不到"报出来的是**需要人确认的信号**，不是自动定论。反方向的错同样存在——库内删过数据而索引未同步（3.5 节那个 DELETE 触发器缺失），会造成"查得到其实已不存在"的**假阳性**，机制设计里刻意保留了这层人工复核。

### 9.4 三件不能保证的事

- **不能保证零幻觉**。这套机制降低的是"无依据的内容被当成事实交付"的概率，做不到零。
- **不能保证替代人做决策**。产出物是给解决方案架构师和决策者看的分析材料，判定权、采信权、决定权都在人手里。
- **不能保证全自动**。阶段 0（材料解析入库）和阶段 6（交付物组装）确实不调模型——一个是确定性解析，一个是按章节映射装配；但中间的分析阶段需要模型生成内容，也需要人看报告。

一句话总结：**这套机制的价值不在于它保证了什么，而在于它把"保证不了的部分"明确标了出来。**一份知道自己哪里不确定的分析材料，比一份看起来什么都很确定的材料有用得多。

## 十、结尾：5 条可执行清单

- **第一步：先把来源格式定死，再谈反查**。合法来源只允许两种形态（URL，或「文件名 + 定位符」），格式校验写成纯函数并配单测；格式不合法的条目作废，不是降级保留。这一步不做，"可回查"就是空话。
- **第二步：建按页存的 trigram 全文索引，并用触发器同步**。索引至少要有"行 id / 出处 / 内容 / 表号"四列，每条业务写入路径配 INSERT / UPDATE 触发器。**别忘了删除路径**——没有 DELETE 触发器，删掉的数据会在索引里留下假阳性。
- **第三步：把反查写成"只在该出处那一页做短语查"**。条件是"出处等值 + 该页短语匹配"，片段包成短语并转义；低于 3 字符的片段返回"判不了"，不许据此指控。这一步决定你的反查是"精确"还是"差不多"。
- **第四步：把分级和判定搬出提示词，写进纯函数**。权威性、证据级、夹带出处、字数超标、硬结论无依据、判定与底账矛盾、依据未落实——全部做成输入确定、输出确定的判定项；模型只能改内容列和核实说明，**不许自己把状态升为"已核实"**。
- **第五步：自检拆成三轮，并把成本上界写死**。第 1 轮全量三问只报告，第 2 轮只改被点名的行，第 3 轮复查仍存疑的行；每批设行数上限、单轮设超时、整体设总时长上限。改完**必须重新判定**——"改过"不等于"改对"；三轮仍改不掉的按实降级并留痕。

最后一句提醒：**这三件事的顺序不能颠倒**。没有来源格式，反查无从下手；没有反查，分级只能是猜；没有分级，自检就会退化成让模型自我批评。工程上的可信，是一层一层搭出来的。
