# 部署与二次开发：Electron 桌面壳、SQLite+FTS5 本地存储、模型接入与降级兜底

> 读完这篇文章你能：看清一个"给人做调研"的智能体为什么落成 Electron 桌面应用，搞懂它本机的数据是怎么组织的，把模型端点接上并且知道被供应商拒绝参数时会发生什么，最后照着步骤自己加一条判定规则、加一张信息表。

## 1. 引言：为什么做成桌面应用，而不是 Web 服务

先说结论：这个工具的产品形态是 **Electron 桌面应用（macOS / Windows 双平台），内嵌一个 Fastify 服务，数据全部存本机、不上传服务器**。

**第一条理由：数据不出本机。** 这个工具吃进去的是两类材料：我方产品资料（白皮书、规格表、介绍 PPT）和客户场景资料（调研纪要、需求文件）。后者几乎必然带着客户的名字、产线细节、内部口径。只要有一个"上传到我们服务器"的动作，售前就得先走一轮合规审查，甚至要客户书面同意——很多客户根本不会同意。做成桌面应用之后，材料落在用户自己机器的应用数据目录里，解析、建索引、写库全在本机完成，只有真正需要模型生成的那一段提示词会离开本机。这条边界要说清楚：**不是"什么数据都不出机器"，而是"材料原文、检索索引、结构化的信息表都留在本机"。**

**第二条理由：单机可离线分析。** 整套流程有 7 个阶段，其中阶段 0（材料解析与入库）是确定性解析、阶段 6（交付物组装）是按章节映射装配，**这两个阶段根本不调模型**。断网状态下材料照样能入库存档、交付物照样能装配导出，只有中间几个分析阶段需要模型端点。

**第三条理由：装完即用，不需要运维。** 目标用户是解决方案架构师和售前，他们不缺"部署服务"的技能，缺的是时间。做成 Web 服务意味着要有人管服务器、域名、证书、备份、升级窗口。

代价也得诚实说：

- **打包体积。** Electron 本体加 Node 运行时、SQLite、前端产物，安装包是几百 MB 量级。
- **跨平台差异是真要处理的。** Windows 上 Python 命令名是 `python` 而不是 `python3`，控制台默认走本地代码页会让中文报错变成转义串；macOS 上应用装到系统应用目录后安装目录不可写。
- **导出 PPT 需要本机 Python 3.10+。** 这是硬依赖。缺了它不影响分析，也不影响导出 Word 和 Markdown，但 PPT 那一档就是转不出来。

所以真正的问题不是"桌面还是 Web"，而是**"愿不愿意用一些工程麻烦，换掉用户的合规成本和运维成本"**。

## 2. 桌面壳：主进程、预加载脚本与内嵌服务

### 2.1 主进程 / 预加载脚本 / 渲染进程的分工

Electron 的三层权限模型是这套壳的地基，分工必须划死：

- **主进程**：管窗口与菜单、决定数据目录、拉起内嵌服务、跟操作系统打交道（打开文件夹、打开系统浏览器、可选地访问系统钥匙串）。它是唯一持有 Node 完整能力的地方。
- **预加载脚本**：只做一件事——把"这是一个桌面应用"以及几个必要的本地动作挂到渲染进程能看到的全局对象上。
- **渲染进程**：跑前端页面，**不能直接碰 Node、不能直接读写文件、不能自己起进程**，只能通过预加载脚本暴露的那几个接口访问本机能力。

窗口创建参数上，三个开关必须开：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`。任意关一个，那套"数据不出本机"就站不住。

预加载脚本暴露的接口刻意做到最小：一个布尔标记（说明自己在桌面壳里跑）、打开数据目录、打开导出目录、取应用信息。这里还有一条容易被忽略的纪律：**不为桌面版开第二套数据通道**，业务数据的读写全部走同一个 HTTP API——一旦开了"直接读数据库"的近路，就会出现"浏览器版能用、桌面版另走一路"的分叉，同一个 bug 要修两遍。

### 2.2 单实例锁：第二次启动只抬窗，不起第二个进程

做法是启动时申请单实例锁，申请不到就直接退出；已经拿到锁的实例会收到"第二次启动"事件，它的处理是：窗口被最小化了就恢复，然后聚焦。

为什么这几行重要？因为桌面应用最容易被用户这样操作：点了图标好像没反应，再点一次。如果没有这把锁，第二次启动会**再起一个内嵌服务、再打开同一个数据库文件**。SQLite 在同一个库文件上多进程写入，轻则报 `database is locked`，重则把 WAL 文件搞成需要人工介入的状态。用户看到的是"点两下之后开始报错"，根因是双击了图标两次。

### 2.3 内嵌 Fastify 服务与 APP_PORT

内嵌服务是一个标准 Fastify 应用，端口从环境变量 `APP_PORT` 读，**默认 46172**。

固定的 46172 是开发期口径，为的是多个并行开发实例能按约定分配端口；装到用户机器上，它可能被别的软件占着。所以桌面壳会把一个当前可用的端口通过 `APP_PORT` 交给子进程，服务端只管监听这个变量给的值，默认值 46172 只在"没人告诉它"时生效。

启动流程有两个防呆设计。一是**服务端跑在 Electron 自带的 Node 里**（把 `ELECTRON_RUN_AS_NODE` 设为 1，用 Electron 自己的可执行文件跑服务端入口），安装包因此不必额外背一个 Node 运行时；代价是 `better-sqlite3` 这类原生扩展必须按 Electron 的 ABI 重建，所以打包用的是一份**隔离的运行时副本**。二是**启动有上限**：拉起后轮询健康检查接口，超时（约 40 秒）就认为起不来，把原因和日志位置写在窗口里。

### 2.4 应用数据目录：三类产物分开放

数据落系统的应用数据目录下（由 Electron 提供，**不写安装目录**——macOS 装到系统应用目录后那地方不可写；**也不写用户当前工作目录**），分成三类：

- **数据库**：`data/scene-master.db`（开发口径的默认值，可用 `DB_PATH` 覆盖）。业务数据的唯一真身。
- **原始产出**：模型每次生成的原始输出。默认**只存解析失败的那些**，用 `SCENE_DUMP_RAW_DIR` 打开了才存全部。这是排障物料，不是业务数据。
- **交付物**：阶段 6 装配出来的文档，落 `data/deliverables`（可用 `DELIVERABLE_DIR` 覆盖）。用户导出到别处的文件走另一个导出目录（`EXPORT_DIR`）。

为什么分？三类产物的生命周期和备份策略完全不同：原始产出可以随便删，交付物要跟数据库一起备份，导出目录可以整个交出去。

## 3. 本地存储：better-sqlite3、18 张业务表与 FTS5

### 3.1 同步驱动加 WAL 模式

存储选的是 **better-sqlite3，同步 API，WAL 日志模式**。这个组合在"服务端"语境里看着反直觉，但对桌面应用是合适的。

**为什么用同步驱动：**

- **单用户桌面，并发量就是 1。** 异步驱动的吞吐收益在这里等于零。
- **避免回调地狱。** 同步 API 下"开事务 → 写三张表 → 提交"就是三行顺序代码，事务边界就是代码块边界，不用在脑子里跟踪 Promise 的挂起与恢复。
- **事务简单。** 信息表写入经常是"整批替换某阶段某表号下的所有行"，同步事务是一段直白的循环；异步事务还要处理"提交前另一个请求也来写同一批数据"的竞态。

**WAL 的作用**是让读不阻塞写、写不阻塞读：用户翻上一阶段的结论时，后台可以同时在写本阶段生成的行。代价是**同步驱动会阻塞事件循环**，所以纪律是"事务拆小"，不要把整个阶段几百行塞进一个事务。

### 3.2 18 张业务表

数据库里是 **18 张业务表**（FTS5 索引虚表另计），分两层：产品资料库 8 张、场景分析项目 10 张。

**第一层 · 产品资料库（8 张）**

| 表名 | 一行存什么 |
|---|---|
| `product_line` | 一条产品线（归属场景为空表示通用资料库，非空表示该场景专属资料库） |
| `product` | 一个产品型号（含在售状态、上市时间、曾用名、定位描述） |
| `spec_param` | 一个规格参数项（含参数分类、取值，以及"实测 / 宣称 / 未提及"三态） |
| `capability` | 一项能力（含能力域、成熟度、依赖条件、不适用场景） |
| `boundary` | 一条"我们不做的事"（含原因、有无计划、应对口径、责任人） |
| `limitation` | 一条已知限制（含影响程度、修复状态、对外可提性） |
| `cost_rate` | 一条成本费率（实施类或商务类，含费率、单位、标准工时、数据来源） |
| `optional_material` | 一条可选材料（O1 认证 / O2 案例 / O3 价格与授权 / O4 开发资料 / O5 路线图 / O6 交付与生态） |

`spec_param` 那一行写的"实测 / 宣称 / 未提及"三态值得展开，因为它决定了产品资料能不能被当证据用。库里一条真实的规格行长这样：

```text
product     = YS-EC3200 紧凑型边缘控制器
param_class = 软件
param_name  = 操作系统
value       = 云枢 OS（基于 OpenHarmony 5.0）
measured    = 宣称
source      = 云枢智控-产品与能力白皮书.docx:表格3
authority   = T3
evidence    = B
```

`measured` 里的"宣称"不是修饰词，是这一行能不能支撑结论的开关：白皮书里写的规格默认只是宣称，要升级成"实测"必须补测试数据。同一个型号上，"典型功耗 6W"那一条是实测，"操作系统"这一条是宣称——并排放着，差别一眼能看出来。如果只有 `value` 没有 `measured`，111 条参数会看起来一样可靠，产品资料的"可验证"这一维也就无从体检。

顺带说明一个容易误读的点：`source` 精确到"表格 3"，不是"参见白皮书"。这个精度是反查的前提——全文索引能直接回到那一页确认"这页确实有这句话"，来源抽查才不是走形式。

**第二层 · 场景分析项目（10 张）**

| 表名 | 一行存什么 |
|---|---|
| `scenario` | 一个分析场景（名称、描述、状态、当前阶段） |
| `scenario_linked_line` | 一条"本场景引用了哪条通用产品线"的记录（引用不拷贝，另有显式取消引用的标记） |
| `scenario_step` | 一条流程步完成记录（用户点"完成本步"才写入） |
| `scenario_brief` | 一个场景的诉求（含用户原文，作为对照基准保留） |
| `scenario_material` | 一条场景私有库材料（对某张表某行的覆盖值及理由） |
| `stage_data` | **一行信息表数据**（场景 + 阶段 + 表号 + 行内容 + 是否失效标记 + 来源与证据等级） |
| `stage_summary` | 一个阶段的总结文档（每场景每阶段一份） |
| `conversation` | 一个会话（场景下的对话容器，关联底层智能体会话） |
| `message` | 一条消息（角色、内容、所属阶段、关联表号） |
| `quality_gate` | 一条自检 / 质量检查项记录（检查项、结论、说明、证据引用、检查时间） |

这里要抓住一个设计点：**33 张信息表在库里不是 33 张物理表，而是 `stage_data` 一张表**，靠"表号"这个列区分——信息表的列**由契约层定义驱动**，写法只能是"行内容存成一个结构化字段，列语义由契约层解释"，这样加一张表不用改数据库 schema。反过来，只有列结构稳定、需要索引和约束的才单独建表：产品资料库那 8 张，枚举约束（成熟度四档、影响程度三档、可提性三档）直接写在表定义里，靠数据库兜住非法值。

`stage_data` 上还有一个 `is_stale` 标记，这是"上游改了、下游过期"的落地方式。依赖关系是一张显式维护的表，共 **15 条有效依赖**（上游表 → 受影响阶段）：

| 上游表 | 受影响阶段 | 业务含义 |
|---|---|---|
| M1 产品清单 | 阶段3、阶段4 | 匹配候选池（表4-3）、架构选型（表5-1） |
| M2 规格书 | 阶段3、阶段4 | 选型对照、选型 |
| M3 能力清单 | 阶段1、阶段3 | 环节角色、表4-1 能力底账 |
| M4 边界声明 | 阶段1、阶段3 | 环节能否参与、我方参与地图 |
| M5 已知限制 | 阶段4、阶段5 | 实施风险、验收约束 |
| O2 已交付案例 | 阶段3、阶段6 | 能力证明、对外材料 |
| O3 价格与授权 | 阶段4 | 定价 |
| 表1-2 场景环节地图 | 阶段1 | 要素清单范围 |
| 表1-3 门槛与合规 | 阶段4 | 约束与合规 |
| 表2-2 场景要素清单 | 阶段2、阶段4 | 竞品对照维度、方案架构选型 |
| 表2-5 物理与合规约束 | 阶段4 | 合规路径（跨阶段表：阶段1 填要求值、阶段4 填我方路径） |
| 表3-6 替代方案 | 阶段4 | 竞品价格对照、我方价格位置 |
| 表3-8 未被满足的需求 | 阶段3 | 痛点排序、匹配矩阵缺口 |
| 表4-3 需求-能力对照 | 阶段4 | 方案范围 |
| 表4-4 细分优先级 | 阶段4 | 先做哪个细分 |

另有 3 条指向已删除表的死条目仍挂在依赖表里，实际永不触发。上游改动后下游被标成失效，界面横幅提示"资料已更新，建议重算受影响阶段"并标出受影响表——**注意"建议"两个字**：标的是状态、不是动作，是否重算由用户决定。

### 3.3 FTS5 虚表 source_fts：trigram 分词加触发器同步

全文检索用的是一张 FTS5 虚表 `source_fts`，四列分别是"业务行 id、来源（形如 `文件名:页码`）、该页原文片段、表号"，分词器指定为 **trigram**。

**为什么是 trigram？** 中文没有天然的空格分词，常规 FTS 分词器对中文短语基本失效。trigram 把文本按三字符滑动切分建索引，中文短语因此能被直接命中。代价也一样明确：**少于 3 个字符的片段无法用 trigram 检索**。这一点被处理成"返回不确定"而不是"判定没这条来源"——检索不出来只说明"证明不了它有"，不能反过来指控内容造假。

**为什么用触发器同步？** `source_fts` 是 content-bearing 虚表，写入靠业务表上的 INSERT / UPDATE 触发器：产品、规格参数、能力、边界声明、已知限制、可选材料这 6 张来源型表，每次写入都顺手把索引写进去，应用代码不用关心索引。缺口是**没有 DELETE 触发器**：删掉一行业务数据，索引里会留下孤儿项，所以删行的地方必须显式清索引。

**为什么检索和业务表分开物理存储？** 因为两类数据形状本来就不同：业务表要的是**列语义、必填校验、枚举约束、外键**；全文索引要的是**短语匹配能力**。混在一起，业务表每次写入都要背上索引维护成本，索引一旦损坏还可能连业务数据一起弄脏；分开之后索引可以独立重建——删掉虚表重新灌一遍，业务数据一个字都不受影响。对"每条结论可回查"这个核心主张来说，这个独立性很重要：索引可以牺牲，业务数据不行。

### 3.4 为什么只读资产与任务写库要物理分离

**材料原文与来源索引这类只读资产，跟任务写库是物理分开的。**

「只读资产」指入库解析后基本不再变化的东西：原文片段、来源索引、按"文件名:页码"定位的出处。「任务写库」指每个场景、每个实例都在高频写入的东西：`stage_data`、`stage_summary`、`scenario_*`、`conversation`、`message`、`quality_gate`，特点是持续写入、按实例绑定、损坏了很难重建。

分开的好处有四条，每条都对应一个真实麻烦：

- **并行时不互相锁。** 多个实例各写自己的任务库，只读资产共享一份；只有一个库文件时，多进程写入就是前面说的锁冲突。
- **备份策略可以不同。** 只读资产备份一次就够（还能从原始材料重新解析生成），任务库要天天备。
- **损坏隔离。** 任务库写坏了，恢复方案是"重新解析材料生成资产 + 重跑分析阶段"，资产那一侧是干净的。
- **角色清晰。** 只有产出材料的模块能写资产，其余模块只能读；写库按场景归属，让"谁有权改这条数据"在代码结构上看得见。

对应到部署上有一条硬结论：**数据库必须按实例隔离，多实例写同一个库文件会冲突。**

## 4. 模型接入：直连兼容端点与三层容错

### 4.1 接入方式

接入方式很朴素：**直连 OpenAI 兼容的 `/chat/completions` 端点**。你可以填供应商的 API Key 走公有云，也可以指向自建的兼容服务。**每次调用都实时解析供应商登记表**，而不是启动时读一次缓存住——用户在设置页改完配置，下一次生成立刻生效，不用重启。

### 4.2 一个明确的设计取向：工具本身不带联网检索

这一条要写在最前面，因为它是后面所有容错设计的前提：

**工具本身不带联网检索。** 模型的行业常识来自它自己，加上你上传的材料。

这些话读起来像缺点，所以把另一面说清楚：**材料越全，结论越实。** 上传一份完整的产品白皮书、一份带实测数据的规格表，模型能写出来的东西跟"只给一个场景名称"完全不是一个量级。反过来，材料里没有的客户事实，模型**不可能知道**。

那系统怎么处理这个必然的空白？靠"每条结论可回查"这条铁律：来源必须能定位到"文件名:页码"，来源不存在则条目作废；自检环节还会用全文索引真去查那一页原文里到底有没有这句话。所以这不是"因为做不到所以没做"的缺口，而是**把不确定性摆到明面上**：与其生成一段读起来很确定、实际没有任何依据的文字，不如把它标成"无法核实"。

### 4.3 第一层容错：参数被拒 → 自动降级并记住

**它解决的真实问题：** 你事先不知道用户会接哪个供应商、用哪个模型。"OpenAI 兼容"这四个字在实践中兼容程度差很多——有的供应商不认 `thinking` 参数，思考型模型不接受强制 `tool_choice`，有的只认 `response_format`，还有的干脆不吃结构化输出参数。如果按"一套参数打天下"来写，用户换个模型就会看到一句英文报错，然后来问你；而桌面分发场景里你没法远程调试。

**做法是三层降级：**

- 结构化输出的档位按 `tools + tool_choice` → `response_format` → 纯提示词 依次降；
- 参数被拒后把结论**记进按「端点｜模型」为键的能力记忆**，同一进程内不再重复踩同一个坑（不会每次生成都先撞一次墙再降级）；
- 判定"是不是参数问题"靠错误信息的特征匹配——属于确定性层，不靠模型自述。

**两个必须知道的坑。** 一是降到"纯提示词"那一档时模型已经看不到 JSON Schema，它会自己发明字段名，所以降档时必须**把结构用文字写进提示词**；只降参数不补提示词，等于把"参数不兼容"换成"数据解析失败"。二是**思考模式默认关闭**：实测在思考模式下某一轮 91 秒只吐推理内容、正文一个字都没开始，随后连接被重置，整张表作废；同一提示词关掉思考后 10 秒出完 3000 字。生成任务本身就是"按给定结构把内容写出来"，判定逻辑全在确定性层，不需要思考模式。

### 4.4 第二层容错：传输失败 → 退避重试

**它解决的真实问题：** 网络抖动、连接被对端重置、连接中途被关闭。这类错误跟"参数不对"完全不同——参数不对时重试一百次结果一样；网络抖动时重试一次可能就过去了。

做法是区分错误类型：**可重试的传输类错误**（网络不可达、连接被重置、超时、连接被对端关闭等）退避重试，第 n 次等 n 倍基数，次数有上限；**其余错误照原样抛出**，不重试。

为什么不把所有错误都拿来重试？对参数类错误重试是纯粹浪费时间：用户多等一轮退避，最后还是失败；更糟的是它会把"参数不兼容"掩盖成"网络不稳定"，让人往完全错的方向排查。退避而不是立刻重试，是因为立刻重试正好撞在同一段网络抖动上。这里也不追求"无限重试直到成功"——**让用户看到真实失败，比让他等一个不会成功的重试要好。**

### 4.5 第三层容错：连接超时只盖"等响应头"

这一层看起来最细，但它防的是最难受的一类 bug。

**它解决的真实问题：** 供应商卡住不返回字节时，读流的操作会永远等下去，进度条就永远转，所以必须有超时；但超时加错了地方，会反过来杀死正常的请求。

真实踩过的坑是把超时信号**直接挂在请求上**：那个信号一到点就中止**整个流**，于是"连接超时"变成了"总时长上限"——单个分析阶段实测 2–5 分钟，超时信号一旦盖住整个流，长分析就会被自己掐死。现象还有迷惑性：短任务一切正常，越重要、越长的分析越容易失败。

正确做法是拆成两个互不重叠的超时：

- **连接超时**：只看"还没等到响应头"。取值相对短（默认 60 秒），而且**响应头一到就立刻摘掉定时器**。
- **空闲超时**：看"多久没有新字节"。取值相对长（默认 120 秒），覆盖"连上了但不吐字"这种卡死。

这两个超时还必须和"用户主动取消"区分开：用户取消静默收尾，超时中止必须报错——否则会被当成"分析完成但没有结果"，用户等半天等来一个空表。两者都可以用环境变量调大，给自建慢模型留空间。

顺带说一个相关的量：**单次生成的最大输出预算是显式给的**（默认 32768）。不给就等于交给供应商默认值，而默认上限偏小时，一次生成整步表格会在中途被截断，截断的 JSON 解析必然失败——真实事故是 30 行被清成 0 行。

### 4.6 SSE 流式返回与断线可续

生成过程用 SSE 推给前端，并且**断线可续**。

流式的理由很直接：单个分析阶段要 2–5 分钟，用普通请求等结果就是两到五分钟不动的转圈，绝大多数人会在 20 秒内认为程序死了；流式让用户看到行在一条条出来，直接决定他会不会在生成中途去点关闭。断线可续的价值则在长分析里：网络抖一下、用户切换网络，已经生成完的部分不该重来——生成结果是一条条落库的，重连之后接着往下，已经入库的行不重算。

三层容错的目标只有一个：**让一个必然会遇到各种不兼容和网络问题的模型接入，表现得像一个稳定的本地功能。**

## 5. 环境变量与配置

### 5.1 环境变量

服务端的所有部署差异都收敛到环境变量上，代码里没有硬编码的端口和路径。

| 变量 | 默认值 | 作用 |
|---|---|---|
| `APP_PORT` | `46172` | 内嵌服务监听端口；桌面壳会把当前可用端口交给它 |
| `APP_HOST` | `0.0.0.0`（桌面壳强制 `127.0.0.1`） | 监听地址；桌面版必须锁回环，否则无鉴权 API 暴露到局域网 |
| `DB_PATH` | `data/scene-master.db` | 业务数据库文件路径；**每个实例必须用不同值** |
| `SCENE_DUMP_RAW_DIR` | 未设置（只存解析失败的） | 设置后把模型原始输出全部落盘，用于排障 |
| `DELIVERABLE_DIR` | `data/deliverables` | 阶段 6 装配出来的交付物存放目录 |
| `EXPORT_DIR` | `exports` | 用户导出文件（Markdown / Word / PPT）的落地目录 |
| `WEB_DIST` | 未设置 | 前端构建产物目录；设置后单端口同时提供 UI 与 API |
| `LLM_CONNECT_TIMEOUT_MS` | `60000` | 连接超时，只覆盖"等响应头" |
| `LLM_IDLE_TIMEOUT_MS` | `120000` | 空闲超时，覆盖"连上了但不吐字" |
| `LLM_MAX_TOKENS` | `32768` | 单次生成的最大输出预算，太小会截断 JSON |
| `LLM_THINKING` | 关闭 | 设为 `1` 打开思考模式（默认关，原因见 4.3） |
| `SCENE_PROVIDERS_FILE` | `<工作目录>/data/providers.local.json` | 供应商登记表位置，测试 / CI 用来指向临时文件 |
| `SCENE_DEVTOOLS` | 关闭 | 设为 `1` 打开开发者工具 |

### 5.2 供应商配置：providers.local.json

模型供应商的登记信息从**工作目录下的 `data/providers.local.json`** 读取，里面放的是：供应商名称、接口地址、API Key、可用模型列表，以及默认使用哪个模型。

这个文件有几个明确的行为约定：

- **文件缺失或损坏，按"未配置"处理，不抛错。** 第一次打开应用时它不存在，这是正常状态；此时需要模型的操作会返回一条能照着做的提示（去设置页添加供应商并选默认模型）。
- **密钥永不回显。** 对外接口只给两个信息：是否已配置密钥、以及一个掩码后的展示串。
- **写入权限收紧**：按仅所有者可读写落盘。
- **可选地再加一层加密。** 桌面版可以从系统钥匙串取一个主密钥，用它把 API Key 加密后存储，这样单独把这个文件拷走也解不开。这个能力**默认关闭**，需要显式开启——免签名分发的应用在 macOS 上没法让系统稳定记住"始终允许"，每次访问钥匙串都会弹授权框、要用户输登录密码，还会阻塞启动。原则是**不伪造假的"安全"**：拿不到主密钥就如实按明文落盘并留痕。

### 5.3 配置不进代码、不进版本库

这条纪律有三条理由：**密钥轮换不该需要重新打包发版**（密钥编进代码，换一次就得重新构建、签名、分发一个几百 MB 的安装包，而用户的旧版本还在用旧密钥）；**一份代码要在多种环境下跑**（开发机接自建兼容服务、用户机器接公有云，同一个构建产物要适配两边，只能靠外部配置）；**版本库里永远不该有可用的密钥**（历史提交里的密钥删不掉，一旦进库就等于已经泄露）。

具体做法是四条：密钥只通过"本地配置文件 + 环境变量"注入；配置文件写进忽略清单；文件权限收紧；日志与接口响应做掩码，绝不打印密钥本体。

## 6. 导出与打包

### 6.1 三种导出格式

交付物有两份：《〈场景〉解决方案》和《〈场景〉建设工作方案》，可以导出 **Markdown / Word / PPT** 三种格式。

两个设计细节值得说。**第一，交付物是装配式的**：按"章节 ← 信息表"的映射把各步的阶段总结装配成完整文档，不是每阶段一个文件。**第二，篇幅有门禁**：解决方案要求在 1200–4500 字，建设工作方案要求在 2000–5000 字。门禁不是限制水平，是拦住两类典型失败——一份 500 字的"解决方案"显然没写透，一份 8000 字的方案客户不会读完。这类判定同样落在确定性层：它是个字数区间检查，不需要模型来判断。

### 6.2 PPT 导出的本机 Python 依赖

**导出 PPT 需要本机有 Python 3.10 或更高版本。缺了它不影响分析，也不影响导出 Word 和 Markdown。**

为什么需要 Python？PPT 这一档走本机 Python 转档脚本，复用成熟生态比用 Node 重写一遍划算。取舍很明确：**接受一个本机依赖，换掉一段容易出错的重复实现。**

跨平台有两个坑。**系统自带的 Python 往往太旧**：macOS 上系统自带的 `python3` 是 3.9.x，跑脚本会在较新的类型语法上直接报错，所以实现上按候选顺序探测，取第一个版本不低于 3.10 的解释器并缓存，一次导出只探测一轮。**Windows 上命令名不一样**：Windows 是 `python` 而不是 `python3`，更麻烦的是应用商店的占位符会"静默失败"——命令能执行，但什么都不做；所以候选列表按平台分开写，而且必须检查实际输出而不是只看退出码。另外 Python 子进程要强制 UTF-8 输出，否则 Windows 下中文报错会被转义成一串 `\uXXXX`。

还有一条原则：**附属功能失败不该拖垮主输出**——图标、样式这类附属步骤挂了，不该让用户拿不到 pptx。

### 6.3 打包与分发

打包产物是 **macOS 的 dmg 和 Windows 的 exe**；分发方式是**网盘和加群领取**——不走应用商店，也不依赖任何需要公开地址的渠道。

打包上只有一个关键做法值得记：**运行时用隔离副本，并且落到可执行的真实文件位置**——服务端要作为**子进程**被拉起，而塞在 asar 归档里的文件没法被系统当可执行目标加载。这就是"运行时"和"仓库里给开发用的那份"要分开的原因：一个按 Electron 的 ABI 构建、打进安装包，一个留给本地开发服务和单测。

## 7. 二次开发指南

这一节是全文最实用的部分。改动之前先回答一个问题：**这个改动落在哪一层？会不会碰公共契约？** 判断方法只有三条：只是展示问题（列宽、排序、空态）就改前端，不碰契约；是判定规则问题（某条门槛判错了、某个枚举值不对）就改领域层，加单测；是"多了一个字段 / 多了一张表 / 换了一种数据结构"，就先改契约层，再让上下游跟着走。

### 7.1 目录结构：pnpm monorepo 五包分层

| 位置 | 层 | 职责 |
|---|---|---|
| `apps/web` | 表现层 | React 18 + Vite + TypeScript 的三栏界面与表格组件 |
| `apps/server` | 应用层 | Fastify 用例编排：材料入库、阶段推进、单元格编辑、导出…… |
| `packages/contract` | 契约层 | 33 张信息表的列定义、枚举字典、前后端共享类型（**单一事实源**） |
| `packages/domain` | 领域层 | 纯 TypeScript、零 IO、可单测——所有判定规则 |
| `packages/infra` | 基础设施层 | 数据库仓储、模型客户端、文档解析、来源索引、Word/PPT 产出 |

依赖方向单向：`web → contract`、`server → contract`、`server → domain`、`server → infra`，`infra → domain`（基础设施实现领域层定义的端口，属于显式声明的依赖倒置）。**领域层不依赖任何一层**——这是最不能破的一条：领域层一旦依赖数据库或网络，就没法在纯单元测试里跑，"判定不交给大模型、可单测可审计"就变成了口号。

### 7.2 领域层加一条判定规则的完整步骤

假设你要加一条规则：某张表的某列，取值必须落在给定的几个枚举值之内。

**第一步：写纯函数（零 IO、参数注入）。** 函数签名里要出现它需要的一切：要比较的数据、判定依据、阈值，全部作为参数传进来。

- **坑一：函数里读了环境变量、当前时间或随机数。** 单测就没法复现；领域层里出现任何 IO 调用，这条规则就已经不可测了。
- **坑二：返回自由文本。** 返回"建议检查一下"这种话，调用方没法分支、前端没法显示、测试没法断言。**判定函数的返回值必须是有限枚举值。**
- **坑三：把"不知道"这一档省掉。** 真实数据里大量情况是"信息不足，判不了"；被迫二选一，函数就会开始猜。

**第二步：加单测。**

- **坑一：只测最顺的那条路径。** 返回 N 个枚举值的函数，至少保证每个取值都有一条用例被打到。
- **坑二：边界不测。** 空数组、零、缺字段、超长字符串，最容易在生产里炸出来，也最容易被跳过。
- **坑三：拿修复后的数据当测试数据。** 用例要用触发问题的那个输入，否则下次改回去你发现不了。

**第三步：在领域层的入口文件里导出。** 领域层只有一个对外面，其他模块只能从这里引。

- **坑一：只导出函数，忘了导出类型。** 调用方拿不到类型就只能写 `any`。
- **坑二：命名跟已有导出撞车。** 名字撞了通常说明你的规则该放进已有模块，而不是新开一个。
- **坑三：直接从模块文件深层引。** 绕过入口文件会把手写实现变成事实上的公共契约。

**第四步：在自检 / 阶段推进的调用点接上。**

- **坑一：把判定写进提示词让模型"顺便判一下"。** 最容易犯、后果最严重——它同时违反"判定不交给大模型"和"判定可单测"两条，规则从此没法审计。
- **坑二：参数没传全，被默认值兜住。** 漏传关键参数会让默认值静默生效，规则看起来在跑，实际按默认条件在判。
- **坑三：判定结果没落库。** 用户在前端看不到，下次进来又要重算，也没法解释"为什么这行被标了"。

**第五步：确认返回的是有限枚举值，并且全链路认它。**

- **坑一：前端显示的是英文 key。** 领域层返回枚举 key，展示层需要一份中文映射；少一处就会出现一列 `need_check` 之类的字符串。
- **坑二：新增枚举取值，但契约层的枚举字典没同步。** 校验层认不出新取值，会把合法数据判成非法。**枚举字典和判定函数必须一起改。**

记住一句话：**判定在领域层，形状在契约层，展示在前端，三者靠枚举值对齐。**

### 7.3 新增一张信息表的完整步骤

**第一步：先改契约层的表定义。** 一张表要写清楚：表号、表名、归属阶段、级别（重要 / 支撑 / 过程）、一行代表什么、每列什么语义、哪些列必填。

- **坑一：只写中文表头，不写列语义。** 后端提示词的字段说明、前端表格的列、数据契约的形状都从它派生；列语义不写，提示词里生成的字段说明就是空话。
- **坑二：必填列给多了。** 遵守"必填优先"：先填必填列，其余选填留空，**留空不阻断推进**。必填给多了等于逼模型硬编内容填满，编出来的值最后会变成"无法核实"。
- **坑三：该给枚举的列给成自由文本。** 取值有限就必须登记枚举，否则没法校验、没法做下拉。

```ts
  rowUnit: "一台待接入设备",
  columns: [
    { key: "device_name", label: "设备名称", slot: "中栏", required: true },
    { key: "protocol", label: "通信协议", slot: "中栏", enum: "protocol_kind" },
    { key: "evidence", label: "出处", slot: "右栏补充" },
  ],
}
```

**第二步：在阶段 / 流程定义里登记。** 表必须挂到正确的阶段和流程步上。

- **坑一：挂错阶段。** 阶段推进是**按"本步表集"过滤模型输出**的，挂错就会出现"漏掉"或"提前生成"。第 1 步和第 2 步同属一个阶段但表集不重叠，这类约束必须守住。
- **坑二：忘了它是"用户输入表"还是"模型分析表"。** 前者不跑模型、后者要跑，就绪判定方式不同。
- **坑三：表的展示顺序没定义。** 顺序和表号不一致时，流程读起来会很乱。

**第三步：前端表格自动跟随。** 因为表格的列是从契约派生的（中栏列 + 右栏补充列），登记正确的话**前端一行代码都不用改**，这是"单一事实源"的直接收益。

- **坑一：你发现必须手改前端。** 这通常不是"前端需要适配"，而是有人在前端硬编码了列名或表号。正确做法是回头把契约改干净，而不是补一句特判——补了第一次就会有第二次。
- **坑二：右栏归属放错。** 内容型列放中栏，出处 / 证明材料 / 核对过程放右栏补充。放错了会直接触发自检规则（中栏夹带出处、中栏太长），用户也会看到表格结构跟别的表不一致。

**第四步：登记下游依赖表。** 如果新表是别的表的输入，必须登记依赖关系。

- **坑一：忘了登记。** 上游改了行，下游不会被标成"待重算"，用户拿着过期结论去做判断——这类错误被发现时通常已经很晚了。
- **坑二：依赖表没同步清理，或者顺手多写。** 依赖表是显式维护的 15 条有效条目，改表 / 删表时必须同步清理——表里就有 3 条指向已删除表的死条目，正是没清理留下的后果；而顺手多加几条"看起来相关"的依赖，会让失效传播范围失控，每次改一行都要重算一大片。

**第五步：补一条自检规则。**

- **坑一：规则写成"让模型自己判断这条有没有问题"。** 自检里模型能改的只有内容列与核实说明，**不许把状态升为"已核实"**；能确定性判的（正则命中、枚举比对、跨表比对）就不要交给模型。
- **坑二：只加规则，不加"谁执行"。** 规则要落在确定性层，得有明确的调用点。

### 7.4 改公共契约的注意事项

契约层是"单一事实源"，改它的风险比其他层都高，纪律有三条：**契约先行**（先改契约定义再改代码；不要"先在实现里加个字段，回头补契约"，契约一旦滞后于实现，前后端就会各自长出一套理解）；**版本化**（契约变更必须登记并升级版本，下游按版本适配，因为导出物、历史数据、外部对接的口径都可能依赖旧版本）；**改公共层的分支优先合入**（功能分支都基于新契约，公共层合得越早，后面 rebase 冲突越少）。

两个具体的坑。一是**同时在多个分支加同一个字段，版本号撞车**，现象是出现两个"同版本不同内容"的契约，非常难排查，所以改契约前先确认没有并行分支在动同一处。二是**改了列的 key 却不做数据迁移**：列 key 是数据层的键，改 key 不会自动改历史行，旧行里那个 key 会变成孤儿数据，用户以为数据丢了。

### 7.5 单测与验收

质量门槛是明确的：**领域层核心逻辑覆盖率不低于 90%。** 验证链路分四层，从便宜到贵：

- **单测**：`pnpm test` 跑 vitest，覆盖 `packages/*/src` 与 `apps/server/src` 下的测试文件。领域层每个判定模块都有测试文件——这是"可单测"的落地证据。
- **端到端验证脚本**：`verify:m0` 到 `verify:m6`，按里程碑各一个，用真实服务 + 真实数据库 + 真实接口跑一遍，检查健康接口、非法路径的 404 语义，以及各阶段的推进与回滚。
- **E2E**：Playwright 跑界面流程。
- **打包冒烟**：发布脚本里内建一步"用构建产物起一个临时实例、打健康检查、验两条路由语义"，跑不过就不出包。**构建产物能起来**必须被自动验证，因为它跟开发态用源码起服务是两条路径。

建议的顺序是：**先跑单测，再跑端到端，最后才跑打包冒烟**——前面便宜且定位准，后面贵但在最后一道关上不可省。

## 9. 部署与运行的注意事项

**第一，模型端点的可用性与配额。** 工具直连你填的端点，稳定性、限流、配额都在你的配置里，不在工具里。建议先拿一个阶段试跑，确认端点在网络下稳定再推全流程；某个模型在思考模式下表现异常时，先用默认配置（关闭思考）排除这一项。

**第二，长分析要给它时间。** 单个分析阶段实测 2–5 分钟，行数越多越久。不要在生成中途关窗口或断网，那会让这一步的分析白跑（已落库的行不会重算，没落库的部分要重来）。

**第三，导出 PPT 需要一个可用的 Python 3.10+。** 缺了它，分析和导出 Word / Markdown 都不受影响，只有 PPT 转不出来。系统自带的是旧版本时，装一个较新的解释器即可。

**第四，数据库必须按实例隔离。** **多实例写同一个库文件会冲突**，表现是 `database is locked`、写入丢失，或 WAL 文件需要人工处理。所以：每个实例用自己的 `DB_PATH`；**不要把数据库放在网盘同步目录里**——同步客户端会在后台复制、加锁、产生冲突副本，这是活跃 SQLite 库最糟的环境；迁移数据就复制数据库文件本身（连同 WAL 相关文件，或先正常关闭应用）。

前三条是"能不能用"的问题，第四条是"会不会丢数据"的问题。

## 10. 行动清单

- **先确认本机环境三件事**：有没有可用的 Python 3.10+（决定 PPT 能不能导出）、有没有一个稳定的 OpenAI 兼容端点（决定分析阶段能不能跑）、数据库打算放在哪个目录（**不要放在网盘同步目录里**）。
- **投喂第一批材料后，抽三到五条入库结果去核对来源**，看"文件名:页码"能不能对上原文——这是判断材料质量最快的一步，也是"每条结论可回查"第一次被验证的地方。
- **用默认配置跑完一个分析阶段**（不改任何参数），先建立"一个阶段实测 2–5 分钟、行数越多越久"的时间感；确认稳定后再调超时、输出预算、思考模式这些变量。
- **要扩展功能时，先写判定函数再加单测，最后才接调用点。** 顺序反了就会出现"规则写进提示词、没法单测、口径漂移"的连锁问题；领域层核心逻辑覆盖率守住 90%。
- **要加字段或加表时，第一站永远是契约层。** 契约改对了，前端表格和数据结构会自动跟随；契约改错了，你会发现到处都要打补丁——这个信号本身就在告诉你改错了地方。
