# 四层架构与判定矩阵：质量关、门槛筛查、证据分级为什么必须落在确定性层

> 读完这篇文章你能：分清"哪些计算必须自己算"，把判定逻辑从提示词里搬进纯函数，用有限取值集合换来可单测、可审计、可解释三样东西。

## 一、先立问题：同一个场景问两遍，为什么得到两个判断

先做一个两分钟的试验。把一份客户场景调研纪要交给一个大模型，问它一句："这个场景里的技术准入门槛，我们过得了吗？"

第一次它回答：门槛不高，我们的能力基本覆盖，可以推进。

你不放心——这句话要发给销售，出错是要担责任的——于是把同一份材料、同一个问题原样再问一遍。这次它回答：门槛偏高，客户侧已有既定路径，建议先观察。

两段话都很专业，都像是认真读完了材料。它们甚至都引用了纪要里的句子。但它们的结论是相反的。

比结论相反更麻烦的是第二件事：你想知道它为什么改口。你把两段输出翻来覆去地看，找不到"哪一条判据导致了哪一句结论"。它写得像论证，可那段文字不是从判据推出来的，是跟着上下文语气生出来的。于是有三个最基本的问题，你一个都答不上来：

- 这个结论是从**哪一条材料**推出来的？
- 换一个同事、换一天、换一个模型版本再跑，会不会得到同一个结论？
- 如果结论错了，我改哪里能把它修好，并且保证别的地方不被改坏？

这三个问题都答不了的判断，在工程上等于没有判断。你手里拿到的不是一条结论，而是一段关于结论的文字。

### 1.1 工程本质：生成和判定是两类计算

把上面那件事拆开看，其实是把两类完全不同的计算混在了一个环节里。

| 维度 | 生成（generation） | 判定（judgement） |
|---|---|---|
| 在做什么 | 把已有信息组织成人能读的表达 | 把输入归类到有限的结论集合 |
| 正确性标准 | 通顺、贴切、信息密度高 | 同输入必须同输出 |
| 什么叫好输出 | 很多种写法都算好 | 只有一种算对 |
| 出错代价 | 读起来别扭，改一遍就行 | 结论错，下游全部错 |
| "解释"指什么 | 解释我为什么这么写 | 解释哪一条规则命中了 |
| 怎么验证 | 人来读 | 单测跑一遍 |

左列是大模型最强的领域，右列恰恰是大模型最不该碰的领域。原因很朴素：右列的核心要求是**可复现**，而大模型的输出在结构上就是不可复现的——采样、上下文窗口、模型版本、甚至同一句话里前后顺序的细微差别，都在影响它的输出。

很多人试图用工程手段把这件事按回去：把温度调到零、把提示词写成"你必须严格按以下规则判断、不得偏离"、加一句"回答必须简洁明确"。这些都有效，但有效的方式是"提高了概率"，不是"变成了确定"。而"概率更高"对一个要吃单测的模块来说没有意义——单测不接受 99%，它要么过要么不过。

### 1.2 一个类比：记账和审计

用一个类比把这个区别钉住。

记账是把发生的业务写进账本：需要表达、需要判断科目、需要处理模糊情况。有经验的会计比新手记得好，这很正常，也该由人来主导。审计是拿账本去对凭证：这一笔有没有凭证、凭证金额对不对得上、日期是不是落在本期间。审计员不需要"文笔好"，他需要的是**同一本账，谁来审都是同一个结论**。

现在设想一种安排：让会计自己审自己。他会告诉你"我记的账没问题"。他可能真的是这么认为的——这不是他在撒谎，而是他确实没有能力对自己的输出做独立复核。但这不叫审计，这叫自评。

把大模型放在判定位上，本质上就是让会计审自己。

所以回到工程本体：要做的不是"让大模型变得更可靠"，而是**把两类计算拆到两个地方**——生成留给模型，判定搬进一段纯函数。这个决定一旦做出，后面所有的架构选择几乎都是它的推论。

## 二、五包分层：给判定逻辑一个只属于自己的包

### 2.1 五个包各是什么

工程按包切成五个，每个包用一句话能说清自己是谁；其中四个落在依赖链上，构成四层。

| 包 | 层 | 职责与主要技术 |
|---|---|---|
| apps/web | 表现层 | 界面与交互，React 18 + Vite 6 + TypeScript，三栏骨架，表格组件渲染 33 张信息表 |
| apps/server | 应用层 | 用例编排：材料入库、阶段推进、单元格编辑、导出，Fastify 5 |
| packages/contract | 契约层 | 33 张表的列定义、JSON Schema、前后端共享类型——单一事实源 |
| packages/domain | 领域层 | 纯 TypeScript、零 IO、可单测——**所有判定规则住在这里** |
| packages/infra | 基础设施层 | sqlite 仓储、模型客户端、文档解析器、来源索引、docx 报告、ppt 生成 |

这里先交代一个措辞问题：所谓"四层架构"，指的是依赖链上的四个层次——表现层、应用层、领域层、基础设施层；契约层是第五个包，但它不占依赖链的位置，因为它是**被所有层依赖的共享内核**，没有任何一层是"通过契约层去依赖另一层"的。所以"五个包"和"四层依赖"说的是同一件事的两面。

### 2.2 依赖方向表

依赖方向是这套架构里最不能含糊的部分，一张表列清。

| 依赖方向 | 是否允许 | 说明 |
|---|---|---|
| web → contract | 允许 | 前端复用列名与枚举字典，不自己抄一份 |
| server → contract | 允许 | 应用层按契约组装用例、做入参校验 |
| server → domain | 允许 | 应用层调用判定函数 |
| server → infra | 允许 | 应用层调用仓储、模型客户端、文档解析 |
| domain → contract | 允许（领域层唯一的出边） | 领域层只用类型与枚举字典 |
| infra → domain | 允许（**显式声明的依赖倒置**） | 基础设施实现领域层定义的端口 |
| domain → infra / server / web | **禁止** | 领域层不依赖任何层 |
| infra → server | **禁止** | 基础设施不知道有"用例"这回事 |
| 跨模块直接引用内部函数或私有表结构 | **禁止** | 模块之间只走契约 |

`infra → domain` 这一条值得多说一句。按朴素的分层直觉，基础设施在最底下，领域层在它上面，怎么会有箭头从下往上？这里的方向不是"调用方向"，而是"实现方向"：领域层定义自己需要什么（端口），基础设施层实现这个端口。领域层不认识 SQLite，也不认识 HTTP；它只知道"我需要按表号读一批行"，至于这批行是从本地数据库来的还是从别处来的，是基础设施层的事。这条反向依赖是**显式声明**的，写在架构约定里，而不是某天某个人为了方便偷偷加的。

### 2.3 硬规则：领域层不碰任何外部资源

规则写起来只有两句，但必须是真的硬。

- 领域层不依赖任何层，只依赖契约层的类型与枚举。
- 领域层不碰数据库、不碰网络、不碰文件。它需要的一切——待判定的数据、要参照的底账、要查询的出处——全部通过函数参数注入。

第二句话是可测性的来源。一个函数如果自己会去连数据库，那测它就得先准备数据库；一个函数如果自己会去调模型，那测它就得等模型。把这两件事都推出去之后，判定函数剩下的形态就非常干净：给一组输入，返回一个结论。没有等待，没有状态，没有副作用。

### 2.4 为什么在依赖方向上这么较劲

三条收益，都不是"架构好看"，而是具体到能算账的。

**可单测。** 判定函数是纯函数，测试里不用起数据库、不用起服务、不用等模型。喂一千组输入跑完不到一秒，于是"这个改动会不会改坏别的结论"这个问题从"要靠人复核"变成"跑一遍就知道"。这一条的价值在长期：规则表会一直改，能不能安全地改，取决于回归成本有多低。

**可审计。** 同一个输入进去，同一个输出出来，昨天和今天一样，你和我一样。审计这件事的前提是"两次执行可比"，而可比的前提是"确定的"。这一条直接决定了结论能不能对外发。

**可解释。** 每一个结论都能回答"凭什么"。凭的是规则表里第几条命中了、哪个取值落进了哪个桶。解释不是事后编的一段话，而是判定过程本身留下的痕迹。这一点和第一条是互补的：可单测保证"改不坏"，可解释保证"改得准"。

## 三、领域层模块地图：谁判什么

领域层不是一个巨大的判定文件，而是按业务能力切成二十多个模块，每个模块对应一件能独立描述清楚的事。对外需要点名的，是下面这几个。

| 模块 | 一句话：它判什么 |
|---|---|
| `barrier-scan` | 一道门槛：过得了 / 绕道 / 借道 / 过不了 / 等窗口 / 不知道 |
| `capability-match` | 一条需求我方是真能解 / 条件能解 / 不能承诺；以及竞争力 5 维打分 |
| `value-verify` | ROI 算得对不对、试点判据立不立得住、指标能不能被验证 |
| `evidence` | 来源权威性 T1–T4、证据级 A–D、引用格式合不合法 |
| `material` | 材料质量六维达标情况、完成度检查 |
| `workflow` | 阶段状态机、风险继承链、上游改了谁要重算 |
| `postcheck` | 生成后三问自检的判定与确定性收口 |
| `completeness` / `flow` | 阶段信息完整度、流程能不能往下走 |
| `report-gate` | 交付物篇幅与结构门禁 |

这张表里有一个值得注意的设计：模块是按**业务能力**切的，不是按技术类型切的。没有 `utils`、没有 `common`、没有 `helpers`。理由是判定规则最怕"大家都往同一个抽屉里放东西"——一旦规则混进公共抽屉，就没人能说清某一条判定到底归谁负责、改动的边界在哪里。

## 四、判定矩阵：把判定写成有限取值集合

这一节是全文的核心。八类判定，逐类给出取值集合和判定口径。看的时候请注意一件事：**每一类的判定值都是有限集合，没有一类的判定值是自由文本。**

先对齐一下术语。标题里的"质量关"在代码里落地成两块东西：材料质量六维（量的是"材料够不够格"）和完成度检查（量的是"该填的表填了没有"），在界面上合起来呈现为信息完整度。它检查的是材料的完备程度，**不产出"这个场景进不进"的结论**——那是人的决定，不是判定函数的返回值。同理，下面的门槛判定回答的是"这一道门槛过不过得去"，也不是"要不要进这个市场"。

### 4.1 门槛判定：六值

门槛判定回答的是"这一道门槛，现状过不过得去"。它不回答"这个场景我们要不要进"——那是决策，不是判定。

| 判定值 | 含义 | 命中口径（有序规则表，先命中先判） |
|---|---|---|
| 过得了 | 现状满足判据 | 现状描述落在"满足 / 已具备 / 已认证 / 达标" |
| 绕道 | 门槛在，但存在替代路径 | 落在"绕道 / 绕过 / 替代" |
| 借道 | 借合作方过生态门槛 | 落在"借道 / 合作" |
| 过不了 | 现状不满足判据 | 落在"过不了 / 不满足 / 不具备 / 未认证 / 禁止 / 否决" |
| 等窗口 | 门槛本身可能变化 | 落在"等窗口 / 等政策 / 政策窗口 / 窗口期" |
| 不知道 | 未调研，判不了 | 落在"不知道 / 待确认 / 未调研 / 不清楚 / 待调研"，或全部规则都不命中时兜底 |

有四条口径设计是刻意的，值得单独说：

- **规则表有序，先命中先判。** 顺序不是随便排的，它本身就是产品判断。
- **"不知道"排在最前。** 未调研的状态要先被暴露出来，不能淹没在后面的规则里被误判成"过得了"。
- **负面规则排在正面规则之前。** 因为"不满足"这个词里含有"满足"两个字，如果正面规则先跑，"现状不满足"会被判成"过得了"——这是典型的字符串匹配陷阱，只能靠顺序解掉。
- **兜底是"不知道"，不是"过得了"。** 全部规则不命中时，宁可把它标成调研重点，也不做一个没有依据的判定。

判定之后还跟着一个处置策略的确定性映射：过得了对应直接进入，绕道对应找替代路径，借道对应找合作伙伴，过不了对应不进入，等窗口对应等政策变化，不知道对应列为调研重点。这里要强调一句：**策略只是建议，是否执行由用户决定。**判定和决策是两件事，产品只做前者。

顺带说一个容易被忽略的约束：门槛判据和现状描述都不能为空，空了直接抛错，不允许返回一个"猜"出来的结论。

### 4.2 能力匹配：三值，加一组 5 维打分

能力匹配回答的是"客户这条需求，我方到底能不能接"。返回值只有三个。

| 判定值 | 含义 |
|---|---|
| 真能解 | 有据可查，且能力已经交付或在组件层具备 |
| 条件能解 | 有据但能力尚未成熟，或能力具备但证据不足 |
| 不能承诺 | 能力不足且证据不足；或证据本身不成立 |

具体映射看这张二维表，横轴是能力成熟度，纵轴是证据级。

| | 能力已交付 / 组件具备 | 能力在研 / 规划 |
|---|---|---|
| 证据 A / B | 真能解 | 条件能解 |
| 证据 C | 条件能解 | 不能承诺 |
| 证据 D | 不能承诺 | 不能承诺 |

这个二维结构的价值在于：它把"能力不够"和"证据不够"两件事分开了。二者都会导致降级，但降级的方式不同——能力不够是产品问题，证据不够是取证问题，要补的东西完全不同。如果只有一个笼统的"匹配度百分比"，这两种情况会被糊成同一个数字，没人知道下一步该干什么。

另一条硬约束：需求缺口描述为空时直接抛错。没有缺口描述就没有匹配对象，这时候返回任何结论都是编的。

竞争力判断是另一套东西：5 个维度——技术、价格、生态、服务、品牌——每维 1 到 5 分整数，满分 25 分。综合等级按总分划档——20 分及以上为强，12 分及以上为中，12 分以下为弱。维度数量不等于 5、或者某一维分数不是 1 到 5 的整数，直接抛错，不做"容错处理"。理由很简单：一个维度缺失的评分表如果被容忍，那算出来的总分就是错的，而错的总分会安静地流进后面的优先级排序里。

### 4.3 证据：来源权威性 T1–T4 与证据级 A–D

这是两把不同的尺子，经常被混为一谈。第一把量来源，第二把量这一条内容本身。

来源权威性四级。

| 级 | 名称 | 判定口径 |
|---|---|---|
| T1 | 权威 | 一手信息（用户直接补充） |
| T2 | 较权威 | 已被用户确认过的事实 |
| T3 | 参考 | 从公开材料中提取、尚未确认 |
| T4 | 待验证 | 无来源佐证的推断 |

在材料入库时，还会按来源类目做一层细化：政府文件、标准、法规进 T1，官方文档与年报进 T2，行业报告与媒体分析进 T3；而兜底映射只看数据来源标记。两层是有分工的：类目层负责细化，来源标记层负责兜底，任何时候都不会出现"这条没有等级"的情况。

证据级四级，规矩更硬。

| 级 | 名称 | 判定口径 | 使用约束 |
|---|---|---|---|
| A | 直接可验证 | 用户补充的一手信息 | 可以写结论 |
| B | 间接有据 | 用户确认过；或 AI 提取且有可定位出处 | 可以写结论，必须带出处 |
| C | 架构推断 | AI 提取但给不出可定位出处；或 AI 推断 | **不写结论** |
| D | 过度宣称 | 无来源佐证且未经确认 | **必须删除** |

这里有一个不太容易被想到、但在工程上很关键的分叉：**"D 级必须删除"是材料入库的规则，不是所有行的规则。**

材料入库阶段（M1 到 M5 那几张表）提取的是"事实"——产品有几个型号、规格参数是多少、哪些事不做。这些内容如果无来源佐证，那就应该删掉，因为它是从材料里"抄"出来的东西，抄错了就是抄错了。

但分析阶段产出的行不是抄来的，是我们自己的推理产出。如果对分析行也用同一把尺子，就会得出"AI 推断 + 未核实 = D = 不许入库"的结论，这等于禁止系统写任何推理——而推理恰恰是分析阶段存在的理由。所以分析行只使用 A / B / C 三级，**结构上就产不出 D**：AI 提取且有可定位出处记为 B，出处给不出来记为 C，纯推断记为 C。

"推断不许写成客户事实"这件事不靠证据级这一列来管，它由自检里的独立判据负责。一把尺子量两件事，最后一定是两件都量不准。

### 4.4 材料质量六维

六维评估回答的是"这批材料够不够格支撑后面的分析"。每一维返回达标 / 存疑 / 不达标三个等级，并附一句说明。

| 维度 | 判什么 | 判据来源 |
|---|---|---|
| 状态可分辨 | 产品状态是否都已确认（不是"待确认"） | M1 产品清单 |
| 可追溯 | 每条记录是否标了来源 | M1 + M2 |
| 可验证 | 规格参数是否实测 | M2 规格书 |
| 有时效 | 产品是否有发布日期 | M1 产品清单 |
| 含边界 | 是否声明了"不做什么" | M4 边界声明 |
| 含反面 | 是否记录了已知限制 | M5 已知限制 |

每一维的三个等级不是拍脑袋定的，都有分子分母。举一个实跑的例子：一批材料里有 111 条规格参数，其中 10 条没有提及测试数据，这一维就判为不达标，整体六维结果是 5/6 达标。这个"10/111"就是判定痕迹——它告诉用户该去补什么，而不是只说一句"材料质量一般"。

后两维值得单独点出来。**含边界**和**含反面**检查的是"不做什么"和"哪里不行"。一个只讲自己能力的材料库，在后面的门槛扫描里会缺判据：你没有记录"不做哪些事"，就没法回答某道门槛是不是撞在自己的边界上。所以这两维在质量评估里不是礼貌性的一项，它们是下游判定的输入条件。

### 4.5 完成度检查：七项

完成度检查比质量六维更靠前一步，它检查的是"该有的表有没有数据"。

| 序号 | 检查项 | 不达标时记录的风险（会往下游传） |
|---|---|---|
| 1 | M1 产品清单已填写 | 能力匹配缺少候选池 |
| 2 | M2 规格书已填写 | 选型缺少参数依据 |
| 3 | M3 能力清单已填写 | 匹配矩阵缺少行 |
| 4 | M4 边界声明已填写 | 门槛扫描缺少判据 |
| 5 | M5 已知限制已填写 | 验收约束不完整 |
| 6 | 来源抽查 | 证据可信度未验证 |
| 7 | 质量六维已评估 | 材料质量未评估 |

第七项是"质量六维已评估"，也就是说六维评估本身是被检查的对象之一——评估没跑，也是缺失项。这种"把检查动作本身也纳入检查"的做法，是为了防止"因为没评估所以看起来没问题"。

最重要的是这一条：**这七项不阻断。**每一项不达标返回的是"状态 + 缺失风险"，而不是"通过 / 退回"。它不做通过判定，只记录当前状态和这个缺口会往哪个下游传。这样设计的原因在后面第八节会展开——阻断权不在检查环节手里。

这里要精确一点，免得把"有限枚举"讲成一句口号：这七项里真正属于判定值的是一个二值结果（有数据 / 空白），行数、单位、缺失风险是**跟着判定值一起返回的展示数据**，它们的用途是把结论说清楚，不参与任何下游判定。判断哪些字段是判定值、哪些是展示数据，标准只有一条：这个字段会不会被别的判定读走。会，它就必须是有限枚举；不会，它就可以是描述性的。

### 4.6 交付物篇幅门禁

最后一道判定在交付物上，量的是篇幅，但目的不是"控制字数好看"。

| 交付物 | 篇幅下限 | 篇幅上限 |
|---|---|---|
| 《〈场景〉解决方案》 | 1200 字 | 4500 字 |
| 《〈场景〉建设工作方案》 | 2000 字 | 5000 字 |

两份交付物的章节骨架不同，所以门禁一律**按口径**进行：章节定义、章节名的别名匹配、篇幅上下限，都随交付物类型变化。章名别名的匹配也要按口径隔离，否则会出现"建设工作方案里的某一章"被误认成"解决方案里的另一章"这种串台。

低于下限意味着内容没长出来（该讲的价值、指标、实施项没讲清楚）；高于上限意味着它变成了材料的堆砌，而堆砌的报告没有人会读完。这两个数都是根据真实定稿量出来的，不是拍出来的。

### 4.7 为什么每一类判定都必须是有限取值集合

现在回到本节的核心问题：为什么这些判定都必须是有限取值集合？因为它一次性买到五样东西。

- **可枚举。**有限集合可以写穷尽测试：六个门槛值各写一条用例，边界值单独覆盖。自由文本没法穷尽，你只能"抽几个看看"。
- **可单测。**判定函数是"纯输入 → 有限枚举"，测试断言写起来是一行等号，不需要任何模糊匹配或主观判断。
- **可审计。**每个结论能追到一条命中规则。审计对象从"一段文字"变成"一次函数调用"，这才谈得上复核。
- **可校验。**有限枚举能进契约的枚举字典，模型一旦写出字典外的值，入参校验立刻拦下。如果取值是开放的，模型写什么都是合法的，校验就失效了。
- **可聚合。**只有枚举才能做统计——这批场景里有多少道门槛"过不了"、多少条需求"不能承诺"。自由文本统计出来的只是词频。

反过来说，如果判定返回值是"描述一下当前门槛状况"，上面五条一条都做不到。你会得到一个读起来更丰富的输出，和一个既不能测、也不能审、更不能回归的系统。

### 📎 源码速览：判定纯函数的形状

下面这段是形状示意，不是实现——它要说明的是判定函数长什么样：纯输入、有限枚举、无 IO、空输入直接抛错、兜底值有明确取向。

```ts
// 判定纯函数形状示意：纯输入 → 有限枚举；无 IO、无自由文本
type Judgment = "过得了" | "绕道" | "借道" | "过不了" | "等窗口" | "不知道";

export function judge(input: JudgmentInput): Judgment {
  assertComplete(input);                       // 判据/现状为空 → 抛错，不返回"猜"
  const hit = ORDERED_RULES.find((r) => r.keywords.some((k) => input.status.includes(k)));
  return hit?.judgment ?? "不知道";              // 兜底 = 不知道，不是"过得了"
}
```

看这个签名就够了：参数全是数据，返回值是六个字符串之一，函数体里没有 await、没有查询、没有写入。这就是"领域层不碰外部资源"落到代码上的样子。

## 五、模型与规则的衔接：三个卡点，加一条硬规则

架构图好画，难的是模型和确定性层交界处那几行。这一节讲三个真实存在的卡点，它们比"分层架构"更能说明这套做法到底在防什么。

### 5.1 卡点一：核实状态不许模型自封

模型很愿意在输出里写"已核实"。你把一条内容交给它，它会在核实说明那一列写下"已核实：这一页写了算力参数"。这句话看起来很负责任，实际上它什么都没证明。

所以入库前有一道处理：**模型写的核实状态会被剥掉，由代码按来源重算。**重算的依据是可定位的出处——出处那一条能不能在材料库里查到、那一页到底有没有这句话。

如果一个判定性结论挂着"已核实"，但出处栏是空的，或者引用的出处（形如"文件名:页码"）在材料库里查不到，确定性校验直接判为"结论与证据矛盾"，严重度是硬伤。它的口径很直白：挂着"已核实"却查不到出处，等于把编造的来源当事实交付。

三轮自检之后仍然改不掉的硬伤，会**按实降级**——不允许继续挂着"已核实"，同时把降级原因写进核实说明。降级不是惩罚模型，而是让这一行的可信度回到它真实的位置上：你可以保留这条内容，但它不能再宣称自己已被核实。

### 5.2 卡点二：自检环节模型只能改内容列与核实说明

生成后三问自检的流程是这样的：第一轮对全部行问三问（真实吗、客观吗、有价值吗），只报告不改；第二轮只改被点名的行；第三轮复查仍然存疑的行。三轮的成本与真问题数成正比，不与全量行数成正比。

关键在于第二轮里模型到底能改什么。

- **能改**：内容列的措辞、核实说明、出处。
- **不能改**：判定列。像"能不能碰""我方角色"这类列，模型碰不到。
- **绝对不行**：把状态升成"已核实"。

第三条不是提示词里的一句叮嘱，而是代码里的一道判断：如果某个字段的值是"已核实"，直接跳过，不落库。前者是"请求模型配合"，后者是"模型不配合也没用"——这两者在生产环境里的可靠性差得很远。

为什么判定列不能让模型碰？因为自检环节的任务是"改措辞、改口径"，而"改档位"实质上是改判定。如果模型在自检时把一个"不能碰"改成"只能配合"，那前面确定性层做的判定就被绕过去了——判定权从纯函数手里漏回了模型手里。这跟整个架构的初衷是相反的。

### 5.3 卡点三：一头一尾根本不调模型

七个阶段里，两端各有一个阶段完全不调用模型。

- **阶段 0（材料解析与入库）**：确定性解析。四种文档格式各自解析；扫描件按固定规则识别——去掉空白后的文本不足 10 个字符而页数大于 0，就判为扫描件，转走 OCR。这里没有模型。
- **阶段 6（最终交付物）**：按"章节 ← 表"的映射装配。交付物不是每个阶段各出一个文件拼起来的，而是按章节去取对应的表数据来组装。

这两个决定的价值容易被低估，所以说清楚它挡住了什么。

阶段 0 是**所有下游的输入**。如果入库阶段调模型，那么"这批材料被理解成了什么样"就带了随机性——同一批材料今天能入出 8 个型号，明天可能漏认一个。这个不确定性会顺着后面六个阶段一路放大，而且**无法定位**：到底是解析错了，还是分析错了？现在一头一尾都不调模型，定位就变得干净：入库结果不对，是解析规则的问题；装配结果不对，是映射表的问题；只有中间那几个阶段的结果不对，才需要考虑模型的因素。

阶段 6 不调模型还有第二个理由：装配是"按映射取数"这种确定性动作。让模型来"总结一下前面所有阶段的产出"，得到的会是一份看起来很顺、但和表格数据对不上的文档——而交付物恰恰是最不能有偏差的那一份。

### 5.4 一条规则的具体形态：硬否定结论的两道门槛

前面讲的都是机制。这一节给一条完整的规则，看看一条"硬"规则长什么样。规则的名字可以叫"硬结论必须有依据"，它管的是最重的那类判定：写"不能碰""不参与""无某种能力"。

写这种话是重话，等于告诉客户"这块别找我们"。所以它必须过两道门槛。

**门槛一：逐条对照能力底账。**写"无 X 能力"之前，先在能力底账里搜 X。搜索不只是搜字面，还要带上同义词和产品系列名。如果底账里能找到这个能力，那就得改判。核心口径是一句话：**一个型号的限制不能当公司级结论。**某个型号的规格页上写着"无某类加速单元"，这只说明那个型号没有，不说明公司没有——账上另一条能力写着同类算力已在别的产品形态上交付。

**门槛二：依据必须立得住。**如果这一行自己的核实结论是"无法核实"或"有反证"，那就不许下硬否定结论，只能写"只能配合"或"辅助"。理由回到证据级的规矩：C 级不写结论。自己都承认没核实过，却下了最重的结论，这是自相矛盾。

还有一个限定条件，它防的是误伤：只有**这一行自己下了硬否定结论**时，才去查底账。同一行里出现的"某型号无某加速单元"如果只是补充说明（这一行判的是"只能配合"），不该被点名。判定要看这一行的档位，不是看这一行里出现过什么词。

最后是一条容易被忽略的技术约束：**跨表校验只比能力名，不比限制条件。**

为什么？因为能力底账里的"限制条件"正是"我方缺什么"的记录。拿限制条件去证否"无 X 能力"，会得出"底账自己都说无 X"的荒唐结论。实测中按错误口径比对，一轮下来命中的问题全是误报，没有一条是真的。误报的代价不只是浪费一次复核，更严重的是它会让用户不再相信这套校验——一条总在喊狼来了的规则，等于没有规则。

顺带记一条口径：缺算法或专业模型，和缺硬件或平台，要分开写。这两类缺口的补齐路径完全不同，糊在一句话里，下游就不知道该去谈合作还是该去立项。

### 📎 源码速览：两道门槛的顺序

```ts
// 硬否定结论的判定顺序：先查底账（能不能这么说），再查依据（有没有资格这么说）
function gateHardNegation(row: Row, ledger: Ability[]): Verdict {
  if (!hasHardNegative(row)) return "不查";                       // 没下硬否定结论就不查
  if (findInLedger(row.negatedAbility, ledger)) return "改判";     // ① 底账里有 → 型号限制≠公司结论
  if (row.verificationVerdict === "无法核实") return "只能配合";    // ② 自认没依据 → 不许下硬否定
  return "放行";
}
```

## 六、契约层：给模型画的框

### 6.1 一份列定义，三种用途

契约层里躺着 33 张信息表的列定义。这些定义写了一份，同时在三个地方生效。

- **它是前后端共用的类型。**前端渲染表格时的列、后端读写的字段，来自同一份定义，不存在"前端以为是这个字段名、后端写的是另一个"。
- **它是模型输出的模板。**提示词里要告诉模型"这张表有哪些列、每列是什么意思、什么值合法"，这些内容直接从契约生成，不是手写在提示词里的。
- **它是校验规则。**表号在不在这个阶段的清单内、必填列有没有值、枚举值在不在字典内，都按同一份定义判。

一份定义三种用途，消灭的是一类特别难查的 bug：提示词里说要填"能力名称"，契约里字段叫"ability"，前端读的是"capability_name"——三个地方各写各的，跑起来就是字段丢失，但谁看自己的代码都没错。契约先行之后，这类问题在结构上不可能发生，因为根本只有一份定义。

### 6.2 校验失败怎么处理

模型产出的行进入系统前会过一道本地校验，检查这几件事：表号是否属于当前阶段、必填列是否有值、枚举是否落在字典内、重要表和支撑表是否带了来源、以及有没有自称"用户确认"。

其中"自称用户确认"这一类值得单独提。模型有时会把一条自己提取的内容标成"用户确认"——这个标签在系统里的含义是"用户确认过的事实"，它直接决定证据级能不能到 B。模型给自己贴上这个标签，等于自己给自己发证据等级。所以这一类违规在代码里的处理是必须降级，不是提示。

处理流程是这样：

- **第一次不过**：字段名不对、类型不对、必填为空——带着具体的违规清单打回重写一次。
- **重写仍不过**：这一部分降级成"待人工"，在界面上明确标出来。

降级这个动作很重要。它既不静默丢弃（那样用户不知道数据少了），也不硬编一个值填进去（那样错误会被藏起来）。它把不确定性显式地交回给唯一有决定权的人。

### 6.3 为什么"重写一次"是上限，而不是无限重试

这是本节最值得展开的一个决策。

直觉上，重试越多成功率越高。但在这里，第一次失败和第二次失败传递的信息不一样：**第一次失败通常说明模型没注意到约束；第二次还失败，通常说明问题不在注意力上。**

可能的原因有三类：契约里的某条约束模型在结构上就做不到；输入本身缺东西（材料里确实没有这个信息，重写多少次都编不出来）；或者这张表的列语义和这次的场景不匹配。这三种情况下，再重试十次只是把同一个错误付十次钱，而且每一次都在拉长用户的等待。

所以上限是"一次"，代价是有界的、可预期的。这也和整篇的基调一致：不确定的事情不要靠"多试几次"去糊，把它显式标出来。

另外一个相关的设计是重试的**粒度**。单张表解析不出行时，只对这张表原样重试一次，而不是把整个阶段重跑——成本只与真正失败的张数成正比。这个原则和自检环节"三轮的成本与真问题数成正比"是同一条：**重试的成本必须跟着问题走，不能跟着数据量走。**

## 七、反例推演：把这些判定交给模型会怎样

前面讲的都是正面的设计。这一节做反面推演：如果把这些判定交回给模型，生产上具体会发生什么。四个场景，每个都落到具体的后果上。

### 7.1 场景一：语气即结论

**发生了什么。**一份客户调研纪要里，客户措辞客气，但对某个环节其实说得很明确：这块已有既定供应商。纪要的语气整体是积极的。模型读完，判定这道门槛"过得了"。

模型的错误不是随机的，它有明确的因果：它是在读**整份材料的语气**，不是在读**某一列的取值**。材料写得热情，结论就偏乐观；材料写得克制，结论就偏悲观。而这两种写法可能描述的是同一个事实。

**生产后果。**售前按这个结论往下配方案、排资源、约技术交流。两周之后，客户在交流会上第一次说出"你们不用做这块"。两周的投入归零，而且客户会顺带认为你们没读懂他的意思——因为他明明说了。

**确定性层为什么不同。**门槛判定的输入是"现状"这一列的取值，取值的判定是字符串规则命中。现状写的是"已具备"，无论整份材料多热情，判出来都是"过不了"。判定不认识语气。

### 7.2 场景二：同输入不同输出

**发生了什么。**同一份材料、同一个问题，两个人各跑一遍，得到两个不同的结论。两个人都是认真跑的，都没有操作失误。

**生产后果。**评审会上两版方案摆在一起，谁也说服不了谁——因为双方都拿不出判据，只能互相说"我这份是这么分析的"。更麻烦的是对客户：客户问"上次不是说可以吗，这次怎么变了"，你没法解释，因为差异确实没有来源。信任的损耗比一次返工更大。

**确定性层为什么不同。**同输入同输出是结构性的，不是调参调出来的。你可以把温度调到最低来"降低"模型输出的随机性，但那是概率层面的改善；纯函数是逻辑层面的保证。这两者的区别，在要签字的场合是决定性的。

### 7.3 场景三：不可审计

**发生了什么。**结论错了，你要改。可你不知道该改哪里——所有的话都在同一段文字里，改一句会影响整段。你只能整段重写。

**生产后果。**重写之后，原来错的地方可能改对了，原来对的地方可能改错了。你没有办法验证这次修改有没有引入新错误，因为判定逻辑不在这段文字之外，做不了回归测试。一个不能做回归的判定系统，每次修改都是一次赌博——而且随着系统变复杂，赌输的概率只会上升。

**确定性层为什么不同。**判定错了，去改规则表里那一条，或者补一条测试用例。改完跑一遍单测，其他所有结论一个都不会变。这就是前面说的"可单测"的真正价值：它不是一个技术指标，它是修改的许可证。

### 7.4 场景四：自封的"已核实"

**发生了什么。**模型给一条内容标上"已核实"，并在核实说明里补了一句体面的解释。这条内容顺着分析、总结、装配一路进到交付物。

**生产后果。**交付物发到客户手里。客户拿放大镜问"这一条在第几页第几段"，你发现页码对不上，或者那一页根本没有这句话。丢掉的不是这一条内容，是整份材料的可信度——客户会合理地质疑"其他条目是不是也一样"。重建信任的成本远高于补一条数据。

**确定性层为什么不同。**核实状态在入库前被剥掉重算，出处能不能查到由代码判；写"已核实"却查不到出处，直接判为硬伤。模型可以写任何话，但它写的话改变不了这一列的取值。

## 八、代价与边界：这套架构不便宜，也不万能

如果文章到上一节就结束，会给人一个错误的印象：好像只要把判定都搬进纯函数，问题就解决了。不是的。这一节诚实讲四个代价。

### 8.1 四个代价

**代价一：规则只能覆盖已经想到的情况。**门槛判定用的是有序关键词匹配，材料里出现一个没进词表的说法，兜底结果是"不知道"。这不是 bug，是刻意的取向——宁可标成调研重点，也不做一个没有依据的判定——但它的含义是：规则表必须跟着真实材料长。第一批材料跑完，一定会发现词表要补。

**代价二：规则管不住"这话虚不虚"。**确定性层能判出"判了不能碰，可这一行的核实结论是无法核实"，因为这是两个枚举值之间的矛盾；但它判不出"这段话有没有信息量""这个表述是不是等于没说"。所以自检环节仍然需要模型按问题清单改写措辞和口径。两者不能互相代劳：判定归确定性层，改写归模型。想让规则去管文风，会发现规则表迅速膨胀而且永远追不上；想让模型去管判定，就回到了第一节那个问题。

**代价三：跨表校验只能比能力名。**这一条上面讲过，但它的局限要说透：底账里命中一个能力名，只能说明"这个能力可能有"，不能说明"这个场景真的用得上"。所以底账命中只把结论从"不能碰"抬到"要补依据"，不会直接抬成"真能解"。从"不能碰"到"真能解"之间，必须由人补上依据。

**代价四：规则需要长期维护。**每一条规则背后都是一次真实误判，或者一个真实的业务口径。这意味着规则表是活的资产，得有人负责它——补词表、改口径、加用例。没有人负责的规则表，半年后会变成一份没人敢动的遗产。

### 8.2 什么情况下这套做法不划算

反过来说清楚边界，比只说好处有用。

- **一次性的、低风险的、没人会复核的问答。**直接问模型更省事。花两天写判定规则去回答一个明天就没人记得的问题，是浪费。
- **结论不需要被追溯的场合。**比如内部头脑风暴的素材整理，错了也就是重来一次，那"可审计"这个收益就兑现不了。
- **领域规则本身还没稳定的时候。**如果判断口径一天一变，写规则表就是在给自己造债——今天写死一条规则，明天业务改了，你还得回来改，而改的成本比不写还高。更稳的路径是先用模型跑一段，把口径跑稳定，再把稳定的部分固化下来。
- **判定频次远低于维护成本。**一年用两次的判定，养一套规则表加一套单测，经济上不成立。

那什么时候必须做？把这四条反过来说就是答案：结论要发给外部、要被人复核、要在多人之间保持一致、要能回归测试、判定频次足够高。这五条里命中三条以上，这套架构就开始划算了。

## 九、可执行清单

- 把判定函数的签名收敛成"纯输入 → 有限枚举"。参数全是数据，返回值是枚举里的一个值，函数体里不许出现 `await`、查询、写入。返回值里出现自由文本的那一刻，可测试性就没了。
- 给每一条硬否定结论加一道依据门禁。写"不能碰""不参与""无某种能力"之前，先证明依据存在且可定位；依据给不出来时，只能写"只能配合"。
- 把模型的自我标记当作不可信输入。核实状态在入库前重算，模型写的"已核实"剥掉；自检环节只允许改内容列与核实说明，判定列碰不到。
- 把"重写一次"写进契约。第一次不过带着违规清单重写，第二次不过降级成"待人工"；重试的粒度按单张表，不整阶段重跑。
- 给每个判定函数配穷尽式单测。每个枚举值至少一条用例，边界值单独覆盖——比如总分刚好 20 分、刚好 12 分这两档，是最容易写错的地方。

一句话总结这篇文章：大模型负责"写"，确定性层负责"判"。判定之所以必须落在确定性层，不是因为不信任模型的能力，而是因为判定这件事要求的不是"通常对"，而是"每次都对、且说得出凭什么"。
