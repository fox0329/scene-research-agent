## 一、产品是什么

| 项 | 内容 |
|---|---|
| 产品名 | 场景通 |
| 一句话 | 把「这场景能不能进、怎么进、值不值」的调研，从几周压到几天的桌面智能体 |
| 形态 | Electron 桌面应用（macOS / Windows 双平台），内嵌 Fastify 服务，**数据全部存本机，不上传服务器** |
| 用户 | 主用户：解决方案架构师 / 售前。次用户：读交付物做决策的部门负责人 |
| 输入 | 我方产品资料（白皮书/规格表/PPT）+ 客户场景资料（调研纪要/需求文件） |
| 输出 | 33 张结构化信息表 + 阶段总结 + 两份交付物（《解决方案》《建设工作方案》），可导出 Word / PPT / Markdown |
| 版本 | 0.2.1 |
| 分发 | 网盘 / 加群领取（**正文里不放任何仓库或 Releases 链接**） |

**三条核心设计主张**（每期文案都不许与之矛盾）：

1. **调研要结构化**——把"调研"拆成有行粒度、有必填列、有列语义的表，能填、能校验、能复算。
2. **判定不交给大模型**——LLM 只做内容生成与表达组织；门槛、证据分级、质量关、能力匹配、价值验证全部落确定性层（可单测、可审计）。
3. **每条结论可回查**——来源必须能定位到「文件名:页码」；来源不存在则条目作废。

## 三、技术架构

### 五包分层（依赖单向）

```
apps/web       表现层    React 18 + Vite 6 + TypeScript
apps/server    应用层    Fastify 5（用例编排：ingest / advance-stage / edit-cell / export…）
packages/contract  契约层  33 张表的列定义、JSON Schema、前后端共享类型（单一事实源）
packages/domain    领域层  纯 TS、零 IO、可单测——所有判定规则
packages/infra     基础设施层  sqlite-repo / dsh-client / doc-parser / source-index / docx-report / ppt-svg
```

依赖方向：`web → contract`、`server → contract`、`server → domain`、`server → infra`、`infra → domain`（基础设施实现领域层定义的端口，属显式声明的依赖倒置）。**domain 不依赖任何层**。

### 前端技术栈（可对外讲）

- React 18 + Vite 6 + TypeScript
- Tailwind + Shadcn/ui + Radix
- TanStack Table v8（33 张表的表格组件）
- TanStack Query（服务端状态）+ Zustand（UI 状态）分离
- 三栏骨架：左栏（场景 / 产品资料库 / 设置）＋ 中栏（流程进度轴 + 本步信息表 + 对话抽屉）＋ 右栏（来源与证据 / 风险与缺口 / 信息完整度）；左右栏可拖宽、可收起
- 视觉值全部走 Token（颜色、间距、圆角、动效时长），无硬编码

### 后端与存储

- Node 22 + Fastify 5，SSE 流式推送生成过程（断线可续）
- better-sqlite3（同步 SQLite + WAL）
- 全文检索：FTS5 虚拟表 + **trigram 分词**，INSERT/UPDATE 触发器同步

### 领域层判定模块（20+ 个按业务能力划分的模块，对外点名这几个）

| 模块 | 判定能力 |
|---|---|
| `barrier-scan` | 门槛判定：过得了 / 绕道 / 借道 / 过不了 / 等窗口 / 不知道 |
| `capability-match` | 需求-能力匹配：真能解 / 条件能解 / 不能承诺；竞争力 5 维 1–5 分（满分 25，强 ≥20 / 中 ≥12 / 弱 <12） |
| `value-verify` | ROI 计算、试点判据校验、指标可验证性校验 |
| `evidence` | 来源权威性 T1–T4、证据级 A–D、引用校验 |
| `material` | 材料质量六维评估、完成度 7 项检查 |

| `postcheck` | 生成后三问自检的判定与确定性收口 |
| `completeness` / `flow` | 阶段完成度、流程就绪判定（ready / readyHint） |
| `report-gate` | 交付物篇幅与结构门禁（解决方案 1200–4500 字；建设工作方案 2000–5000 字） |

### LLM 与确定性层的分工（每期都可以用的一句话）

> 大模型负责"写"，确定性层负责"判"。
> 判定类逻辑全部出自领域层——可单测、可审计；模型只做内容生成与表达组织。

代码上的三个证据（对外可以讲，但不贴真实文件名以外的内部细节）：

1. 来源权威性（T1–T4）与证据级（A–D）是**服务端算完再入库**的，模型自封的核实状态会被剥掉。
2. 自检环节里，模型能改的只有"内容列"与"核实说明"，**不许把状态升为"已核实"**。
3. 阶段 0（材料入库）和阶段 6（交付物组装）**根本不调模型**——一个是确定性解析，一个是按章节←表映射装配。

### 模型接入（实测口径，照实说）

- 接入方式是**直连 OpenAI 兼容的 `/chat/completions` 端点**（供应商 API Key 或自建兼容服务）
- 工具**本身不带联网检索**；模型的行业常识来自自身与上传材料
- 因此"材料越全，结论越实"——这是设计取向，不是缺陷
- 兼容性做了三层容错：参数被拒（不认 thinking / tool_choice / response_format）→ 自动降级并记住；传输失败 → 退避重试；连接超时只盖"等响应头"，不盖整个流（否则长分析会被自己掐死）

## 四、可信机制（第 4 期的核心）

### 材料入库

- 支持格式：`.pdf`、`.docx`、`.xlsx`、`.pptx` 四种
- PDF 扫描件识别规则：去掉空白后文本 < 10 字符且页数 > 0 → 判为扫描件，走 macOS Vision OCR（超时 180 秒）
- 入库分类：模型把每份材料归到 M1–M5 / O1–O6，校验表号白名单 + 来源必须含「文件名:页码」
- 全文索引：`source_fts`（FTS5 + trigram）；反查时**只用 MATCH 短语查该出处那一页**（最短 3 字符），不是全库模糊匹配

### 生成后三问自检（G-R8）

每条信息连问三轮「这真实吗？客观吗？有价值吗？」——**但三轮的成本必须与真问题数成正比，不与全量行数成正比**：

- 第 1 轮：全量三问，**只报告、不改**
- 第 2 轮：**只改被点名的行**
- 第 3 轮：**复查仍存疑的行**

约束：每批 ≤ 60 行、单轮 180 秒、自检总时长上限 10 分钟。三轮后仍改不掉的硬伤，按实降级为「无法核实」。

### 确定性收口（不靠模型自觉）

- **中栏夹带出处**：7 条正则识别（`文件名:页码`、`ingest-*`、「来源：」、「（M5）」、`M1_xxx`、`第N页`、「按白皮书」…）——命中即判定
- **中栏太长**：> 60 字即超标（表1-1 的正文列除外）
- **三轮后仍夹带**：由确定性逻辑把引用搬进右栏，**正文一字不删**
- **硬结论无依据**：写"不能碰"且核实结论是"无法核实/有反证" → 判硬伤
- **判定与能力底账矛盾**：跨表比对能力底账，只比**能力名**、不比限制条件（一个型号的限制不能当公司级结论）
- **依据未落到事实**：依据列复述结论或命中行业套话正则（"通常/一般/大多/普遍/往往…由…承载"）→ 判定

### 中栏说结果、来源归右栏（G-R9）

中栏内容格只写结论与结果，一格一句话（建议 ≤40 字，>60 字算超标）；文件名、页码、`ingest-*`、「来源：」一律不进中栏——出处写右栏 `source`，证明材料写右栏 `proof`，核对过程写右栏核实说明。

### 交付物

- 两份：《〈场景〉解决方案》《〈场景〉建设工作方案》
- **装配式**：不是每阶段一个文件，而是按章节 ← 表映射装配，正文取各步阶段总结
- 篇幅门禁：解决方案 1200–4500 字；建设工作方案 2000–5000 字
- 导出：Markdown / Word / PPT。**导出 PPT 需要本机有 Python 3.10+**，没有时不影响分析与导出 Word/Markdown

### 为什么要选"工业物联网 + OpenHarmony"这个品类来演示（可以直接讲）

这是老李自己的技术背景：做的是工业物联网和 OpenHarmony 落地。拿这个品类做演示有三个好处，都是真话：

1. **门槛类的问题最典型。** 工业场景的门槛不是"功能有没有"，而是认证、协议、数据出域、交付窗口这类"过不去就什么都别谈"的东西——正好是这套工具最擅长的那类问题。
2. **"能力底账"最容易被高估。** 工业物联网厂商的能力清单往往写得很满，但一到具体场景就发现"参数是可选的""这个型号没有 NPU""老机取数还没勘察"。这套工具的价值就是把这类话挑明白。
3. **OpenHarmony 是真实的技术底座，不是贴上去的标签。** 边缘控制器跑基于 OpenHarmony 5.0 的自研 OS，这类事实在资料库里是**带出处的一行**，可以点开看到它出自白皮书哪张表——而不是一句宣传语。
